# 지수대별 신용융자 누적과 반대매매 진행률 추정 — 방법론

## 1. 목적

두 가지를 수치로 답한다.

1. 코스피 지수대별로 신용융자가 얼마나 쌓였는가
2. 그중 반대매매(마진콜)가 얼마나 진행되었고, 얼마가 남아 있는가

비교 대상은 삼성자산운용 투자리서치센터의 House View 점검 자료
「7.29일 급락 코멘트: 신용매수 반대매매 추정」(2026-07-29)이다.
그 자료는 Quantiwise(유료 단말)를 썼으나, 여기서는 공개 소스만으로 같은 결과를 만든다.

## 2. 원 자료 방법론의 역설계

원 자료에는 계산식이 없다. 본문 서술과 차트 값을 제약조건으로 두고 규칙을 맞춰나갔다.

### 2.1 버킷 폭 = 500p

본문 "코스피 5,000-6,000p 사이 신용융자 매수 7.2조원"과
차트의 인접한 두 막대(4.00 + 3.23 = 7.23)가 일치한다. 따라서 막대 하나는 500p다.

### 2.2 마진콜 계수 = 0.84

신용융자는 매수한 주식 전체가 담보다. 자기자금 40 + 융자 60으로 100을 매수했다면,
평가액 `P`에 대해 담보평가비율은 `P / 60`이다. 담보유지비율 140%를 만족하는 하한은

```
P / 60 >= 1.40   ->   P >= 84
```

즉 매수 지수 대비 **-16%**에서 마진콜이 발생한다. 계수는 `담보유지비율 × 융자비율 = 1.40 × 0.60 = 0.84`.

원 자료의 서술 세 곳이 모두 이 계수로 설명된다.

| 원 자료 서술 | 계산 |
|---|---|
| 7.27 종가 6,756 → "7,500-8,000대 신용 매수분까지 청산 추정" | 8,000 × 0.84 = 6,720 |
| 7.28 종가 6,024 → "약 -1.1조원이 금일 청산" | 7,500 × 0.84 = 6,300 이 깨짐 → 7,000-7,500 버킷 |
| 7.29 종가 5,663 → "추가 -1조원 반대매매 위험" | 7,000 × 0.84 = 5,880 이 깨짐 → 6,500-7,000 버킷 |

차트의 우축 「상단기준 마진콜 레벨」은 각 버킷 **상단** 지수에 계수를 곱한 값이다.

### 2.3 배분 규칙 = 양(+)의 순증만 누적 (gross)

세 가지 후보를 실측으로 대조했다.

| 규칙 | 설명 | 결과 |
|---|---|---|
| LIFO | 잔고 감소일에 높은 지수 버킷부터 차감 | 고지수 버킷이 0이 되어 원 자료(7,500-8,000 = 1.28조)와 불일치 |
| signed | 감소일 델타를 그날 버킷에서 차감 | 고지수 버킷이 음수가 되어 불일치 |
| **gross** | **증가일 델타만 그날 버킷에 적립** | **일치** |

`gross`가 맞다. 따라서 막대는 "**그 지수대에서 일어난 신용매수 규모**"이고,
"현재 그 지수대에 남아 있는 잔고"가 아니다. 이 구분이 해석에서 중요하다(§5 참조).

### 2.4 기간 = 연초 이후

버킷 4,500p 이상은 코스피가 2026년에 처음 도달한 구간이라 기간을 어떻게 잡아도 값이 같다.
반면 4,000-4,500 버킷은 기간에 민감하다. 시작일을 훑어 원 자료 값(0.36조)에 맞춘 결과:

| 시작일 | 4,000-4,500 버킷 |
|---|---|
| 2025-01-01 | 3.19조 |
| 2025-12-01 | 1.27조 |
| **2026-01-01** | **0.34조** ← 원 자료 0.36조 |
| 2026-02-01 | 0.00조 |

따라서 기간은 **연초 이후**다. 2025-12-31 잔고를 기준선으로 삼아 그 다음 영업일부터 델타를 잡는다.

### 3.1 엔드포인트를 찾은 과정

FREESIS 통계 화면은 eXBuilder6 SPA다. 브라우저 창을 띄우지 않으면 레이아웃 측정값이 0이라
앱이 렌더되지 않고, 각 통계 서비스가 쓰는 제네릭 서브미션
(`/CommSubmit/egovXbuilder.do`)은 `MAPPER`/`QRY` 값을 알 수 없어 호출이 불가능했다.

대신 '크로스 통계' 앱은 지표별 전용 엔드포인트를 쓴다.

- `POST /crossStatsCustom/STATCRSIDXIDINFOBO.do` — 지표 카탈로그(코드 + sqlKey)
- `POST /crossStatsCustom/STATCRS0600000011BO.do` — 지표 시계열 조회

요청 DataMap 이름이 `data`이므로 평범한 JSON 바디로 그대로 호출된다.

```json
{"data":{"serviceId":"STATCRS0600000011","tmpV1":"D",
         "tmpV45":"20260101","tmpV46":"20260729",
         "tmpV108":"OS0026,OS0025","sqlKey":"STATCRS0600000010VM021,STATCRS0600000010VM020"}}
```

`tmpV1`은 자료주기로 일별은 `D`다(`RD`를 넣으면 빈 배열이 온다).
미공표 구간은 `"null"` 문자열로 내려오므로 숫자로 읽히는 값만 취한다.

검증: `20260728` 신용융자 = 33,194,040 백만원 — FREESIS 메인 화면 표기와 일치.
코스피 종가는 네이버 금융 일별 시세와 교차 확인했다(7/27 6,755.75 / 7/28 6,023.66 / 7/29 5,663.24).

## 4. 사이클 분할

코스피 레벨이 국면마다 완전히 달라서, 전 기간을 같은 절대 지수 버킷으로 묶으면 의미가 없다.
2021년 고점은 3,305p, 2026년 고점은 9,115p다. 그래서 적립과 청산을 사이클 단위로 끊는다.

| | 2020–21 사이클 | 2025–26 사이클 |
|---|---|---|
| 적립 구간 | 2019-12-31 ~ 2021-12-31 | 2024-12-31 ~ 최신 |
| 청산 판정 | ~2023-01-31 | ~최신 |
| 버킷 폭 | 100p | 500p |
| 지수 고점 → 저점 | 3,305 → 2,155 (-34.8%) | 9,115 → 5,663 (-37.9%) |
| 신용융자 고점 | 25.65조 (2021-09-13) | 38.63조 (2026-06-24) |
| 실측 청산 | -9.84조 (-38.4%) | -5.96조 (-15.4%) |
| 상태 | **완결** | 진행 중 |

버킷 폭은 고정하지 않고 사이클의 지수 범위에서 자동으로 고른다.
버킷이 20개를 넘지 않는 가장 촘촘한 값을 쓴다(`pickWidth`).
2020–21은 범위 1,847p → 100p(19칸), 2025–26은 6,821p → 500p(15칸)가 선택된다.
후자가 원 자료의 500p와 일치한다.

2020–21 사이클은 청산까지 끝났으므로 **모델의 검증 사례**가 된다(§6).

## 5. churn 보정

양의 순증만 누적하면(원 자료 방식) 같은 자금이 들어왔다 나갔다 할 때 두 번 세어진다.
창이 길수록 심하다. 2020–21 사이클은 gross 합계가 35.40조인데 신용융자 고점은 25.65조로,
약 10조가 중복 계상이다. 원 자료는 창이 7개월(연초 이후)이라 이 문제가 작았다.

버킷이 알려주는 것은 지수대별 **분포**이므로, 분포는 그대로 두고 합계만 실제 순증에 맞춰
균등 스케일한다.

```
순증        = 신용융자 고점 - 적립 기준선 잔고
보정계수    = 순증 / gross 합계
보정 버킷   = gross 버킷 x 보정계수
```

| | gross 합계 | 순증 | 보정계수 |
|---|---|---|---|
| 2020–21 | 35.40조 | 16.44조 | 0.46 |
| 2025–26 | 39.16조 | 22.82조 | 0.58 |

보정 전후를 리포트 표에 함께 싣는다. 원 자료 재현 검증(§2.5)은 조건을 맞추기 위해
보정 없는 gross 기준을 그대로 쓴다.

## 6. 계산 절차

```
for 각 사이클 (적립구간, 청산판정구간):
    폭 = pickWidth(적립구간 지수 범위)

    for 각 영업일 d (적립 기준선 다음 날 ~ 적립 종료일):
        delta = 신용융자[d] - 신용융자[d-1]
        if delta > 0:
            버킷[floor(지수[d] / 폭) * 폭] += delta

    보정계수 = (신용융자 고점 - 기준선 잔고) / 버킷 합계
    판정지수 = 청산판정구간의 최저 지수

    for 각 버킷 b:
        마진콜레벨(상단기준) = b.상단 * 0.84
        마진콜레벨(전량)     = b.하단 * 0.84
        진입 = 판정지수 < 마진콜레벨(상단기준)
```

판정지수는 **그날까지의 최저 지수**를 쓴다. 반대매매는 한 번 발생하면 되돌아오지 않으므로,
지수가 반등해도 이미 터진 물량은 복구되지 않는다. 그날 종가로 판정하면
지수 반등 구간에서 누적 노출이 줄어드는 잘못된 결과가 나온다.

### 6.1 완결된 사이클에서의 검증

2020–21 사이클은 청산이 끝났으므로 모델 추정과 실측을 직접 대조할 수 있다.

| | 값 |
|---|---|
| 보정 모델 마진콜 진입 추정 | 8.85조 |
| 실측 청산 (25.65조 → 15.81조) | 9.84조 |
| 오차 | 1.00조 (실측의 10%) |

보정 전 gross 기준은 19.05조로 실측의 두 배 가까이 나온다. 보정이 필요한 이유이자,
보정 후에는 마진콜 기반 추정이 실제 청산의 대부분을 설명한다는 근거다.

## 7. 해석상 주의점

### 7.1 버킷 값은 '잔존 잔고'가 아니다

`gross` 누적이므로 이미 청산된 물량도 버킷에 남아 있다.
버킷 합계는 그 사이클에 **신용매수가 일어난 규모**이고, 현재 잔고와는 다른 개념이다.
"마진콜 진입 4.72조"는 "그 지수대에서 매수된 4.72조가 마진콜 조건을 만족하는 상태"라는 뜻이다.

### 7.2 결제일 기준 시차

신용융자는 결제일 기준이라 급락 당일 청산이 즉시 반영되지 않는다.
실제로 급락일 7/28 잔고는 전일 32.74조 → 33.19조로 **증가**했다.
모델과 실측의 차이는 (a) 결제일 시차, (b) 투자자의 추가 담보 납입,
(c) 마진콜을 피하려는 자발적 축소에서 온다.

### 7.3 두 벤치마크가 다른 방향을 가리킨다

현 사이클에서 마진콜 모델은 노출을 4.72조로 보는데 실측 청산은 이미 5.96조다.
강제 청산으로 설명되는 몫보다 실제 감소가 크다는 뜻이고, 자발적 축소가 섞여 있다고 읽는 게 자연스럽다.

반면 2021 사이클의 청산률(-38.4%)을 현 사이클 신용 고점(38.63조)에 적용하면
총 -14.82조가 풀려야 하고, 현재까지 -5.96조이므로 **잔여 -8.86조**가 남는다.

두 벤치마크는 근거가 다르므로 한쪽만 취하지 않고 병기한다.

### 7.4 반대매매금액(OS0025)은 검증값이 아니다

금투협이 공표하는 반대매매금액은 **위탁매매 미수금**(미수거래)에 대한 반대매매다.
7/28 기준 139억원 수준으로, 신용융자 청산 추정치(조 단위)와 자릿수가 다르다.
**신용융자 반대매매는 공표되지 않는다.** 원 자료가 이를 *추정*한 이유도 같다.
따라서 이 지표는 추정치의 검증값이 아니라 독립적인 스트레스 축으로만 쓴다.

### 7.5 그 외

- 공표되는 것은 일별 **순증감**뿐이어서 같은 날의 총매수와 총청산을 분리할 수 없다.
- 담보유지비율은 증권사·계좌·종목별로 130~170%로 다르다. 리포트의 민감도 표를 함께 볼 것.
- 종목별 신용잔고는 지수와 독립적으로 움직일 수 있어, 지수대 배분은 시장 전체 근사다.

## 8. 유가증권/코스닥 분리 — 적용됨

금투협은 신용거래융자를 **전체 / 유가증권 / 코스닥**으로 나눠 공표한다
(`신용공여 잔고 추이` 서비스의 그리드 헤더 H002/H003/H004로 확인).
프로그램으로 뚫린 크로스통계 API에는 '전체'(OS0026)만 노출되어, 분리 계열을 프로그램으로
받으려 여러 방식을 시도했으나 전부 막혔다.

| 시도 | 결과 |
|---|---|
| `POST /meta/getMetaDataList.do` + `{"dmSearch":{"OBJ_NM":"STATSCU0100000070BO",...}}` | 날짜 골격은 정상, 값 컬럼 전부 `null` |
| 자료주기 코드 6종(`D`/`RD`/`RM`/`00`/`01`/`1`) | 모두 동일하게 `null` |
| 세션 쿠키(JSESSIONID) 확립 후 재시도 | 동일 |
| `unit` 파라미터 최상위/중첩 5종 | 응답이 항상 `"unit":""` 로 회신, 동일 |
| `/{모듈}/{BO}.do` 패턴 12종 | 오류 페이지 |
| 통계 화면을 브라우저로 렌더 | eXBuilder6 앱이 `document.hidden` 상태에서 렌더를 미뤄 실패 |

(2026-08-19 재시도 기록은 §45.)

결국 통계 화면에서 직접 내려받는 경로로 확보했다.
FREESIS > 주식 > 신용공여현황 > 신용공여 잔고 추이 에서 자료주기 `일`, 2010-01-01~최신으로
내려받은 xlsx(`data/신용공여 잔고 추이.xlsx`, 1,623행)를 `scripts/ingest-split.mjs` 로 파싱했다.

파서는 의존성 없이 세 형식을 자동 판별한다 — 진짜 xlsx(zip), HTML 표에 `.xls` 확장자가 붙은 형식,
CSV/TSV. 컬럼 위치는 `전체 = 유가증권 + 코스닥` 이 성립하는 조합을 60행 투표로 찾으므로
헤더 줄 수나 컬럼 위치가 밀려도 잡힌다.

**zip 압축 해제에서 한 번 막혔다.** 이 환경의 `tar`(Git Bash 기본, PATH 우선순위 상단)는 GNU tar라
gzip/xz 압축만 읽고 ZIP 컨테이너 포맷(xlsx는 zip이다) 자체를 못 연다. 게다가 `C:\Users\...` 형태의
경로를 `host:path` 원격 문법으로 오인해 `--force-local` 없이는 그 단계에서도 막힌다.
Windows 내장 `tar.exe`(`%SystemRoot%\System32\tar.exe`, bsdtar 기반)는 zip을 그대로 읽으므로
절대경로로 그걸 명시 호출해 해결했다.

**교차검증**: 파싱한 '전체' 컬럼과 기존에 크로스통계로 받아둔 OS0026 을 1,618영업일 전부 대조 —
**불일치 0일, 최대 오차 0백만원**. 완전히 일치한다.

코스닥은 지수가 세 자리라 버킷 폭이 자동으로 50p 근처로 잡힌다.

### 8.1 분리 후 드러난 것 — 두 시장의 청산 진행률이 다르다

| | 2020–21 사이클 청산률 | 2025–26 사이클 청산률 |
|---|---|---|
| 유가증권 | -41.9% | **-13.5%** |
| 코스닥 | -36.9% | **-38.3%** |

코스닥은 이미 직전 사이클과 거의 같은 비율로 청산이 진행됐다(보정 모델의 잔존 물량도 1.03조로 작다).
반면 유가증권은 2021년의 3분의 1도 못 미쳤다. '전체'로 뭉쳐 보면 15.4%로 나와서 두 시장이
비슷하게 덜 풀렸다고 오독하게 되는데, 실제로는 코스닥이 유가증권보다 훨씬 빠르게 반응했다.

코스닥 지수 자체도 2026-04-27 고점 1,226.18 → 662.68로 **-46.0%**, 코스피(-37.9%)보다 깊게 빠졌고
고점 시점도 두 달 빠르다. 낙폭도, 청산 속도도 유가증권과 다른 시장으로 다뤄야 한다.

이 관찰을 "코스닥은 끝났고 코스피는 남았다"까지 밀고 나가려면 청산률 하나로는 부족하다 —
기준선이 다른 지표 셋을 더 놓고 넷이 같은 방향일 때만 그렇게 말한다. **§25** 에서 다룬다.

## 9. 실행

```bash
node scripts/fetch-index.mjs    # 네이버 코스피·코스닥 일별(장중 최신)  -> data/{kospi,kosdaq}-daily.json
node scripts/fetch-kofia.mjs    # 금투협 FREESIS 일별 11개 지표      -> data/kofia-daily.json
node scripts/ingest-split.mjs   # (선택) 신용공여 분리 계열 xlsx     -> data/credit-split.json
node scripts/fetch-lending.mjs  # 대차거래추이(공매도 프록시)         -> data/lending-balance.json
node scripts/analyze.mjs        # 사이클 x 시장 배분 + 마진콜 판정    -> data/analysis.json
node scripts/selfcheck.mjs      # analysis.json 불변식 검사 (선택)
node scripts/build.mjs          # 웹 리포트                          -> index.html
node scripts/build-email.mjs    # 메일 클라이언트용 리포트           -> email.html
```

`ingest-split.mjs` 만 xlsx 가 있을 때 돌리면 된다(§8). 원본이 그대로면 다시 돌릴 필요가 없고,
`analyze.mjs` 가 결과 json 이 없으면 해당 분석을 조용히 건너뛴다.
대차거래추이는 예전에 xlsx 였으나 지금은 `fetch-lending.mjs` 가 API 로 받는다(§16.2.1).

`index.html`은 데이터와 차트(SVG)를 모두 품고 있어 외부 의존성이 없다. `file://`로 열어도 그대로 보인다.
`email.html`은 같은 데이터를 메일 렌더러가 견디는 방식(전부 inline style, table 레이아웃, SVG 없음)으로 다시 굽는다.

리포트는 방향이 반대인 두 축으로 나눠 놓았다.

| 탭 | 질문 | 내용 |
|---|---|---|
| PART 1 신용잔고 | 얼마나 더 **하락**할 수 있나 | 반대매매 잔여(§10~15, §17, §18) |
| PART 2 공매도·숏커버링 | 얼마나 더 **상승**할 수 있나 | 대차 되갚기 잔여(§16, §20) |
| ALL 전체 | 둘 다 | 두 파트를 이어서 표시 |

PART 1 안에서 **사이클별 상세는 다시 탭으로 나뉜다.** 두 사이클은 지수 레벨이 3,305p 와 9,115p 로
완전히 달라(§4), 세로로 이어 붙이면 어느 쪽 숫자를 보고 있는지 헷갈린다.
진행 중인 사이클이 기본 선택이고, 탭 라벨에 각 사이클의 지수·신용 고점→저점을 같이 적어
전환하지 않고도 규모 차이를 알 수 있게 했다.

`index.html` 의 탭은 라디오 버튼 + 형제 선택자만 쓴다 — 스크립트가 없어 `file://` 에서도 그대로 동작하고,
인쇄할 때는 모든 탭이 펼쳐진다. 메일에는 탭이 없으므로 `email.html` 은 PART 1 / PART 2 머리말로 나눈다.
배분·판정 로직은 `scripts/lib/buckets.mjs` 에 모여 있어 사이클과 시장에 상관없이 같은 코드를 쓴다.

### 9.0 자동 갱신

`.github/workflows/update.yml` 이 평일 19:30 KST(장 마감 후)와 다음날 08:30 KST 에
위 파이프라인을 그대로 돌린다. `workflow_dispatch` 로 수동 실행도 되고,
`scripts/**` 나 워크플로 파일이 바뀐 push 에서도 돈다 — 파이프라인을 고치면 바로 결과가 나온다.
문서만 고친 커밋으로는 돌지 않는다.

받아오는 계열은 `fetch-kofia.mjs` 의 11개 지표(지수·시총·거래대금·신용융자·반대매매금액·
위탁매매미수금·투자자예탁금·예탁증권담보융자) + 네이버 코스피 + 대차거래추이로, 전부 자동이다.

두 가지가 이 워크플로의 핵심이다.

- **selfcheck 가 게이트다.** `analyze.mjs` 다음에 `selfcheck.mjs` 가 실패하면 커밋도 push 도 하지 않는다.
  계산이 조용히 깨진 채 배포되는 경로를 막는다.
- **바뀐 게 있을 때만 커밋한다.** `git status --porcelain` 이 비면 그냥 끝낸다.
  이걸 성립시키려고 `fetch-kofia.mjs` 의 `fetchedRange` 를 '요청 종료일'이 아니라
  '실제 데이터 범위'로 바꿨다 — 요청 종료일을 적으면 새 데이터가 없는 날에도 파일이 매일 달라져
  빈 커밋이 쌓인다.

남은 수동 구간은 **유가증권/코스닥 분리 신용공여 xlsx**(§8) 하나뿐이다. 사이클 단위로만 쓰이는
계열이라 자주 갱신할 필요가 없고, 파일을 갱신해 커밋하면 다음 실행부터 자동으로 반영된다.
대차거래추이는 §16.2.1 에서 API 경로를 찾아 자동화에 들어왔다.

**상태 확인 경로.** 저장소가 private 이라 Actions 로그를 URL 로 열 수 없다.
그래서 `scripts/status.mjs` 가 배포되는 `status.json` 에 실행 날짜·계열별 반영일·selfcheck 결과를 남긴다.
`ranOn` 이 며칠째 그대로면 워크플로가 멈춘 것이다.
시각이 아니라 날짜만 적는 이유는 실행할 때마다 파일이 달라져 의미 없는 커밋이 쌓이는 것을 막기 위해서다.
데이터가 그대로이고 `status.json` 만 바뀐 날은 커밋 메시지를 `Refresh status (no new data ...)` 로 구분한다.

### 9.1 조회 종료일은 '오늘'이다

## 11. 청산 국면의 지수대별 분포

적립과 대칭으로, 일별 **감소분**을 그날 지수대에 배분한다(`accumulateOutflow`).
"어느 지수대에서 실제로 청산이 일어났는가"를 본다. 적립과 같은 폭을 쓰므로 같은 축에 나란히 놓을 수 있다.

적립 쪽과 달리 churn 보정을 하지 않는다. 감소분 합계는 실측 잔고 변화와 직접 대응하기 때문이다.

### 2020–21 사이클의 청산 (2021-09-13 ~ 2023-01-11)

총유출 **22.00조**, 순감소 **9.84조**. 차이는 청산 국면에도 신규 매수가 계속 섞였기 때문이다.
청산 국면 자체가 churn을 크게 동반한다는 뜻이고, "신용잔고 감소분 = 반대매매 규모"로 읽으면 안 되는 이유다.

| 코스피 구간(p) | 청산액(조) | 비중 |
|---|---|---|
| 2,100–2,200 | 1.68 | 8% |
| 2,200–2,300 | 2.77 | 13% |
| 2,300–2,400 | 2.93 | 13% |
| 2,400–2,500 | 3.31 | 15% |
| 2,500–2,600 | 0.79 | 4% |
| 2,600–2,700 | 2.19 | 10% |
| 2,700–2,800 | 2.00 | 9% |
| 2,800–2,900 | 1.16 | 5% |
| 2,900–3,000 | 4.03 | 18% |
| 3,000–3,100 | 0.64 | 3% |
| 3,100–3,200 | 0.51 | 2% |

청산이 특정 지수대에 몰리지 않고 2,100~3,000p 전 구간에 퍼져 있다.
가장 큰 덩어리(2,900–3,000p, 4.03조)는 하락 초기 구간이고, 그 다음이 2,400–2,500p(3.31조)로 바닥 근처다.
즉 고점 직후의 1차 이탈과 바닥에서의 투항이 양쪽에 있다.

금액가중 평균은 매수 2,656p → 청산 2,585p로 -2.6%다.
다만 적립 창(2020~2021)이 코로나 저점부터 시작해 낮은 지수대 적립을 많이 포함하므로,
이 숫자를 평균 손실률로 읽으면 안 된다.

## 12. 잔여 청산 규모 추정

근거가 다른 벤치마크 네 개를 놓는다. 하나로 수렴하지 않으므로 점 추정 대신 범위로 본다.
이미 청산된 양은 5.96조(신용 고점 38.63조의 15.4%)다.

| 벤치마크 | 근거 | 총 청산 | 잔여 |
|---|---|---|---|
| 2021 청산률 대입 | -38.4% × 38.63조 | 14.82조 | **8.86조** |
| 지수 낙폭 대비 탄성 | 탄성 1.10 × 현 낙폭 -37.9% | 16.14조 | **10.18조** |
| 마진콜 모델(보정) | 지수 5,663p 기준 진입 4.72조 | 4.72조 | 이미 충족 (1.24조 초과) |
| 신용/시총 비율 정상화 | 2023 저점 0.720% × 현 시총 5,326조 | 0.28조 | 이미 충족 (5.68조 초과) |

**잔여 추정 범위 0 ~ 10.18조.**

### 12.1 범위가 넓은 이유 — 레버리지 강도

위쪽 두 벤치마크는 직전 사이클과 레버리지 강도가 같다고 가정한다. 신용/시총 비율은 그렇지 않다고 말한다.

| 시점 | 신용융자 | 시가총액 | 비율 |
|---|---|---|---|
| 2021-09-13 (신용 고점) | 25.65조 | 2,698조 | **0.951%** |
| 2022-09-30 (지수 저점) | 17.16조 | 2,007조 | 0.855% |
| 2023-01-11 (신용 저점) | 15.81조 | 2,196조 | **0.720%** |
| 2026-06-24 (신용 고점) | 38.63조 | 7,439조 | **0.519%** |
| 2026-07-28 (현재) | 33.19조 | 5,326조 | **0.623%** |

시가총액은 코스피+코스닥 합계(FREESIS OS0008 + OS0009, 억원 → 백만원 환산).

현 사이클은 신용 고점에서도 0.519%로 2021년 고점 0.951%의 절반 수준이었다.
지금 0.623%로 올라온 것은 신용이 늘어서가 아니라 **시가총액이 더 빨리 줄었기 때문**이다.
그리고 현재 0.623%는 이미 2023년 저점 0.720%보다 낮다.

따라서 "2022년처럼 -38% 풀려야 한다"는 전제는 이 사이클에 그대로 적용되지 않는다.
절대 금액(38.63조)은 사상 최대지만 시장 규모 대비로는 과열이 아니었다.

### 12.2 잔여 위험은 시간이 아니라 지수 경로에 달려 있다

마진콜 모델 기준으로 현재 지수(5,663p)에서는 추가 노출이 열리지 않는다.
지수가 더 내려가야 새 구간이 마진콜에 들어온다.

### 12.3 한계

- 네 벤치마크 모두 과거 한 사이클(2020–21)에 기댄 외삽이다. 표본이 하나다.
- 시가총액 비율은 상장사 구성 변화(신규 상장, 대형주 편입)에 영향을 받는다.
- 마진콜 모델은 강제 청산만 센다. 현 사이클에서 실측 청산(5.96조)이 모델 노출(4.72조)을
  이미 넘은 것은 자발적 축소가 섞였다는 신호이며, 이 몫은 모델로 예측되지 않는다.
- 어느 벤치마크도 투자 판단의 근거로 쓰기에 충분하지 않다. 규모의 자릿수를 잡는 용도다.

## 13. 마진콜 사다리

"지수대가 얼마로 가면 얼마가 풀리는가"를 직접 답하는 표다. 시나리오 테이블(§12.2)이
0.95/0.90/0.80... 같은 임의의 상대 하락률로 지수를 골랐다면, 사다리는 실제 버킷 경계(marginHigh)
그 자체를 문턱으로 쓴다. 더 정확하고, 이미 계산해둔 값이라 추가 가정이 없다.

### 13.1 계산

안 터진 버킷(`triggered=false`, 즉 판정지수 >= marginHigh)만 골라 `marginHigh` 내림차순으로 정렬한다.
정의상 안 터진 버킷은 `marginHigh <= 판정지수` 이므로, 지수가 더 떨어질 때 가장 먼저 터지는 것은
`marginHigh` 가 판정지수에 가장 가까운(=가장 큰) 버킷이다. 그 다음, 그 다음... 순서로 사다리를 이룬다.

```
remaining = buckets.filter(안터짐).sort(marginHigh 내림차순)
cum = 0
for b in remaining:
    cum += b.보정된_금액
    사다리.push({ 문턱: b.marginHigh, 증가: b.보정된_금액, 누적: cum })
```

## 14. 거래대금 대비 규모

조원 단위 금액은 그 자체로는 크기 감이 안 온다. "그 시장이 평소 하루에 사고파는 돈의
몇 배/몇 %인가"로 바꿔야 시장이 그 물량을 얼마나 부담스러워할지, 청산이 주가를 얼마나
더 밀어낼 잠재력이 있는지 가늠할 수 있다.

### 14.1 데이터와 기준선 두 개

FREESIS 크로스통계에서 KOSPI/KOSDAQ 거래대금(OS0011/OS0012, 억원, 일별)을 추가로 받았다.
억원 → 조원은 `/10000`. '전체' 시장은 코스피+코스닥 거래대금 합계로, 신용융자 '전체'가
유가증권+코스닥 합계인 것과 기준을 맞춘다.

기준선을 하나가 아니라 **두 개** 쓴다.

- **그 시대 정상 평균(baseline)**: 청산 국면이 시작되기 직전 20거래일 평균. 2021년의
  사건을 2026년 거래대금 규모로 재단하면 시장이 그사이 커진 몫까지 섞여 "그때 그 사건이
  그때 기준으로 얼마나 컸는가"를 왜곡한다. 실제로 코스피 전체 기준 그 시대 정상 평균은
  2021년 26.85조/일, 2026년 64.69조/일로 2.4배 차이가 난다. 사이클은 각자 자기 시대와
  비교해야 한다.
- **오늘 기준(current)**: 데이터 마지막 날 기준 최근 20거래일 평균. 앞으로 남은 사다리는
  '오늘' 시장이 그 물량을 받아낼 수 있는지를 봐야 하므로 이건 항상 최신값을 쓴다.

이미 벌어진 청산(§14.2)은 baseline과, 아직 안 벌어진 사다리(§14.3, 앞의 §13)는 current와 대조한다.

### 14.2 과거 청산이 거래대금에서 차지한 비중

| | 2020–21 사이클 | 2025–26 사이클(진행 중) |
|---|---|---|
| 청산 국면 총유출(gross) | 22.00조 | 6.83조 |
| 그 국면 총거래대금 | 6,091.84조 | 1,041.93조 |
| 총유출 / 총거래대금 | **0.36%** | **0.66%** |
| 그 시대 정상 하루 대비 배수 | 0.82배 | 0.11배 |
| 그 국면 거래대금, 정상 대비 | **65%** | **70%** |

두 가지가 눈에 띈다.

1. **강제 청산이 거래대금에서 차지하는 비중 자체는 작다.** 총유출이 그 기간 전체 거래대금의
   1%도 안 된다. 신용융자 청산은 총거래량 관점에서는 작은 흐름이고, 가격을 직접 짓누르는
   주된 힘이라기보다 하락의 방아쇠나 촉매에 가깝다고 보는 게 근거에 맞다.
2. **청산 국면의 거래대금은 정상보다 오히려 줄어 있었다(65~70%).** 패닉으로 거래량이
   폭증한 게 아니라 유동성이 마른 채로 하락이 진행됐다는 뜻이다. 유동성이 얕을 때는
   같은 매도 물량도 가격에 더 크게 부딪힌다 — 총유출 비중은 작아도 실제 가격 충격은
   표면 수치보다 컸을 수 있다.

### 14.3 남은 사다리가 오늘의 유동성에서 차지하는 비중

| 시장 | 남은 사다리(보정) | 오늘 하루 평균 거래대금 | 배수 |
|---|---|---|---|
| 전체 | 18.10조 | 41.54조 | 0.44배 |
| 유가증권 | 15.04조 | 35.66조 | 0.42배 |
| 코스닥 | 1.03조 | 5.88조 | 0.18배 |

남은 물량 전부가 터져도 하루 거래대금의 절반이 안 된다. 시장이 하루 만에 소화할 수 있는
규모라는 뜻이지, 가격 영향이 없다는 뜻은 아니다 — 실제 매도는 하루에 분산되지 않고
급락 며칠 사이에 몰리며, §14.2 가 보여주듯 그런 국면엔 유동성 자체가 이미 얇아져 있다.

### 14.4 한계

- 거래대금은 매수·매도 양측을 어떻게 집계하는지(편도/양도) 명확히 공표되지 않는다.
  이 비율은 근사치이며, 실제 매도 대금만 따로 뽑은 값보다 분모가 크게(비율이 작게)
  잡혔을 가능성이 있다.
- 청산 물량이 그 거래대금 중 얼마가 실제로 매도 주문이었는지는 관측할 수 없다.
  총유출(gross)은 신용융자 잔고 감소분이지 체결된 매도 주문 금액이 아니다 — 담보
  추가납입으로 신용을 상환한 경우도 잔고 감소로 잡히지만 시장에서 매도가 일어나지 않는다.
- '오늘 기준' 평균은 지금 이미 급락·고변동성 국면의 거래대금이라, 평상시보다 높게
  잡혀 있을 수 있다(§14.2 처럼 반대로 낮게 나올 수도 있다 — 방향은 국면마다 다르다).
  사다리의 배수는 그 시점 유동성 상태에 따라 오차가 크다.

## 15. 월별 지수·거래대금 비교

두 사이클의 신용 고점이 속한 해(2021 / 2026)를 골라, 그 해 1~12월(2026은 데이터가 있는 달까지)
평균 지수와 평균 거래대금을 나란히 그린다.

### 15.1 왜 지수를 1월=100으로 지수화하는가

코스피(2021년 2,964~3,259 / 2026년 4,780~8,484)와 코스닥(2021년 934~1,043 /
2026년 794~1,156)은 원 지수 그대로 겹치면 코스닥이 코스피 대비 4~7배 눌려서 거의
평평한 선으로 보인다. 두 시장의 **등락률**을 비교하려는 목적에는 절대 수치가 아니라
"그 해 1월 대비 몇 %인가"가 맞는 축이다. 이는 §14 에서 거래대금과 지수처럼 스케일이
다른 두 지표를 억지로 이중축(그래프 하나에 y축 두 개) 에 우겨넣지 않고 차트를
나누거나 공통 기준으로 지수화하는 것과 같은 원리다 — 이 프로젝트의 다른 차트(예:
신용융자 잔고 vs 코스피)는 이미 만들어 둔 이중축 구성을 그대로 쓰지만, 이번처럼
같은 성격의 두 시계열(지수 대 지수)을 비교할 때는 이중축보다 지수화가 왜곡이 적다.

거래대금은 두 시장 모두 조원 단위로 스케일이 비슷해(2021년 코스피 9.9~26.1조 /
코스닥 9.4~15.7조, 2026년 코스피 26.4~51.2조 / 코스닥 6.2~15.6조) 원 단위 그대로
한 축에 놓아도 왜곡이 없다.

### 15.2 결과 요약

| | 2021년 | 2026년(1~7월) |
|---|---|---|
| 지수 등락(월평균 기준) | ±8%p 이내에서 완만한 등락 | 1월 100 → 6월 177.5(코스피) → 7월 148.1로 급락 |
| 거래대금 추이 | 1월부터 12월까지 꾸준히 우하향(26.1조→9.9조, 코스피) | 6월 정점(51.2조) → 7월 급감(35.9조) |
| 지수-거래대금 관계 | 따로 움직임(거래대금이 지수보다 먼저·독립적으로 감소) | 동행(같은 달에 정점, 같은 달에 급락) |
| 코스닥 전환점 | 대체로 코스피와 유사한 시점 | 코스피보다 한 달 빠른 5월에 선행 정점 |

2026년 7월(하락월) 거래대금이 6월(정점월) 대비 코스피 -30%, 코스닥 -39% 급감한 것은
§14.2 "청산 국면 거래대금이 정상 대비 65~70%"라는 계산을 월 단위로 눈으로 보여준다 —
패닉으로 거래량이 폭증한 게 아니라, 마니아가 꺾이면서 유동성 자체가 함께 빠진 것이다.

코스닥이 5월에 먼저 정점을 찍고(코스피는 6월) 거래대금도 5월 15.56조에서 7월 6.16조로
반토막난 것은 §8.1(코스닥 청산률 -38.3%, 유가증권 -13.5%)과 시점이 정확히 들어맞는다 —
코스닥은 유가증권보다 한 달 먼저 무너지기 시작해 더 빨리, 더 깊게 청산됐다.

### 15.3 한계

- 월평균은 그 달 안의 일별 변동을 뭉갠다. 특히 6월처럼 정점과 급락이 겹친 달은
  월평균 하나로 "정점"과 "무너지는 중"이 섞여 대표값의 해석력이 떨어진다.
- 2026년은 7개월치뿐이라 2021년(12개월)과 계절성 비교는 할 수 없다.
- 지수화는 등락률 비교에는 적합하지만 절대 수준(코스피가 코스닥보다 몇 배 큰 시장인지)은
  가려 버린다. 절대 수치는 표에 원 지수·원 거래대금으로 같이 실었다.

## 16. 공매도(대차잔고) 추이와 숏커버링

### 16.1 왜 대차잔고를 프록시로 쓰는가

한국은 공매도가 거의 전량 '차입 후 매도' 구조라(무차입 공매도는 원칙적으로 금지),
공매도 잔고와 대차잔고(주식 대차거래 잔고)는 사실상 같은 풀을 가리킨다.
그런데 KRX는 **종목별 순보유잔고**(대량보유자 신고 의무 기준, 지분 0.5% 이상만 공표)만
공표하고, **시장 전체 합계 공매도 잔고는 공표하지 않는다**. 그래서 대차잔고를 표준 프록시로 쓴다.

한계도 명확하다: 대차거래는 공매도 외에 ETF 설정/환매, 차익거래, 배당락 대비, 의결권 확보 등
다른 목적으로도 일어난다. 대차잔고 변화 전부가 공매도 포지션 변화는 아니다.

### 16.2 데이터 확보

FREESIS `대차거래추이`(STATSCU0100000140)도 신용융자 분리(§8)와 같은 이유로
크로스통계 API에는 없고, `getMetaDataList.do` 직접 호출도 날짜 골격만 오고 값은
전부 `null`이었다(같은 증상, 같은 결론 — 그리드 값은 이 경로로 못 받는다).
통계 화면에서 일별·2010-01-01~최신으로 내려받은 xlsx(`대차거래추이.xlsx`, 4,102행)를
`scripts/ingest-lending.mjs`로 파싱했다.

파일 구조: 헤더 4줄 + 데이터, 컬럼은 `일자 | 체결(주수) | 상환(주수) | 잔고 주수 | 잔고 금액`,
단위는 `[단위 :백만원, 일주]`(금액=백만원, 주수는 그대로). `구분` 컬럼 없이 이미 시장
전체 1행/일이었다(내려받을 때 '전체' 기준으로 조회됨).

파싱 로직은 신용융자 분리 때 만든 xlsx 리더를 `scripts/lib/xlsx.mjs`로 뽑아내 재사용했다
(zip 해제·HTML표·CSV 세 형식 자동판별, `pickFile()`이 `data/`와 프로젝트 루트를 모두 뒤진다 —
사용자가 다운로드 파일을 프로젝트 루트에 두는 경우가 많아서다).

### 16.2.1 API 경로를 찾아냈다 — 파라미터 누락이 원인이었다

2026-07-31 에 다시 파고들어 자동화에 성공했다. 결론부터: **엔드포인트는 처음부터 맞았고,
파라미터가 모자랐다.**

먼저 막힌 길을 전부 확인했다.

| 시도 | 결과 |
|---|---|
| 크로스통계 지표 카탈로그 88개 전수 조회 | 대차거래 **없음** (신용대주 OS0028 은 있음) |
| `/stat/FreeSIS.do` 에 쿼리스트링 GET | WAF 차단. 네비게이션은 POST 전용 |
| 엑셀 다운로드 엔드포인트 | 존재하지 않음 — `download()` 은 **이미 렌더된 HTML 표**를 `excelexport.jsp` 로 재직렬화한다 |
| 앱 정의 파일 `/ui/app/*` | WAF 차단 |
| `document.visibilityState` 패치 후 SPA 부팅 | 실패. eXBuilder6 는 실제 페인트 프레임을 요구한다 |

그래서 헤드리스 브라우저(Playwright)로 `/stat/main.do` 에 직접 들어가
`goPage('MSIS10040000000000','STATSCU0100000140')` 를 호출했더니 앱이 정상 렌더됐다
(프레임셋을 거치지 않는 것이 요령이었다). 그 상태에서 앱이 보내는 **요청 본문을 그대로 캡처**했다.

```json
POST /meta/getMetaDataList.do   (application/json)
{"dmSearch":{"tmpV40":"1000000","tmpV41":"1","tmpV1":"D",
             "tmpV45":"20260430","tmpV46":"20260730","tmpV72":"",
             "OBJ_NM":"STATSCU0100000140BO"}}
```

이전 시도가 값 대신 `null` 만 받은 이유가 여기서 드러난다 — `OBJ_NM` 만 보내고
`tmpV40`(최대 행수)·`tmpV41`(페이지)·`tmpV72`(종목, 빈 값=전체)를 빠뜨렸다.
세 개를 채우자 평범한 `fetch` 한 번으로 전 구간이 온다. **브라우저는 규격을 알아내는 데만 필요했고,
알아낸 뒤로는 필요 없다** — Playwright 의존성은 제거했고 프로젝트는 다시 외부 패키지 0 이다.

응답 형태:

```
{ unit:"", dsmHeader:"",
  ds1:[ {TMPV1:일자, TMPV2:구분, TMPV3:체결주수, TMPV4:상환주수,
         TMPV5:잔고주수, TMPV6:잔고금액(백만원)}, ... ] }
```

최신일이 먼저 오는 내림차순이고, **마지막 두 행은 '합계'/'평균' 요약**이라 일자가 숫자가 아니다.
`/^\d{8}$/` 로 걸러낸다.

검증: API 산출물과 기존 xlsx 산출물을 대조했더니 **4,096행 전부 일치, 불일치 0**이었다.
`scripts/ingest-lending.mjs` 와 커밋된 xlsx 는 규격이 바뀔 때를 대비한 폴백으로 남겨 두었다.

덧붙여 대차거래는 **T+1 공표**라, 당일 장중에 그날 잔고를 받을 수는 없다.
2026-07-31 시점의 최신 관측일은 07-30 이었다.

### 16.3 숏커버링 판정 방법

날짜별로 지수 등락률(Δidx%)과 대차잔고 등락률(Δbal%)을 계산해 네 조합으로 나눈다.

| 조합 | 해석 |
|---|---|
| 지수↑ 잔고↓ | 숏커버형 — 숏이 밀리며 사서 갚는 압력이 지수를 밀었을 수 있다 |
| 지수↓ 잔고↓ | 동반 청산 — 신용융자처럼 위험자산 전반이 축소되는 국면 |
| 지수↓ 잔고↑ | 신규 숏 추정 — 하락에 베팅하는 물량이 늘고 있다 |
| 지수↑ 잔고↑ | 리스크온 — 대차잔고 증가가 반드시 약세 베팅은 아니다(차익거래 등) |

숏커버링 후보일은 '지수↑ 잔고↓' 날짜 중 `Δidx% × (-Δbal%)`(두 등락폭의 곱, 둘 다 클수록
점수가 커진다)로 순위를 매긴다. 판정 구간은 신용융자 분석과 같은 사이클 창을 쓰되,
잔고 자체의 지역 고점(이번 사이클은 2026-06-15)부터 시작한다 — 잔고가 실제로
꺾이기 시작한 지점이라야 '거기서부터 풀렸다'는 서술이 맞는다.

### 16.4 결과 (2026-07-30 기준)

- 대차잔고 역대 최고 195.30조(2026-06-15) → 현재 133.41조(2026-07-30), **-31.7%**
- 같은 창에서 신용융자(전체)는 -15.4% — **대차잔고가 신용융자보다 두 배 가까이 빠르게 풀렸다**
- 잔고 고점(6/15)은 신용융자 고점(6/24)보다 9일, 지수 고점(6/22)보다도 7일 더 일찍 왔다 —
  대차잔고가 신용융자·지수보다 먼저 꺾인 선행지표였을 가능성
- 잔고 고점 이후 하루 단위 조합: 동반 청산이 압도적으로 많고, 숏커버형(지수↑잔고↓)은
  전부 6월 중(급락 시작 전)에 몰려 있다 — **급락이 시작된 6/22 이후로는 뚜렷한 숏커버링 랠리가 아직 없다**

### 16.4.1 금액이 아니라 주수로 봐야 한다 (2026-08-03 추가)

위 16.4 의 '-31.7%' 는 **금액** 기준이다. 그런데 대차잔고 금액 = 주수 × 주가라,
지수가 빠지면 **한 주도 갚지 않아도 금액이 줄어든다.** PART 3 에서 ETF 를 AUM 이 아니라
좌수로 봐야 했던 것과 정확히 같은 함정인데, 이쪽에서는 한동안 놓치고 있었다.

로그로 쪼개면 갈린다: Δln(금액) = Δln(주수) + Δln(단가).

| 구간 | 금액 | 주수 | 가격이 설명하는 몫 |
|---|---|---|---|
| 금액 고점(2026-06-15) → 2026-07-31 | **-20.2%** | **+1.9%** | **108%** |

즉 '되갚아진 39.44조' 는 되갚음이 아니다. 감소분 전부가 가격이고 빌린 주식은 오히려 늘었다.

**주수 기준의 실제 그림은 이렇다.**

- 주수 고점 31.91억주(2026-04-03) — 금액 고점(6/15)보다 **두 달 이르다**
- 고점 이후 최저 29.08억주(2026-07-16), 고점 대비 **-8.9%**
- 현재 30.47억주(2026-07-31), 고점 대비 -4.5%. 최저 대비 **+4.8%**

그래서 '1차 숏커버' 라고 부를 만한 구간은 4월 초 ~ 7월 중순이고 규모는 **-8.9%** 였다.
7/16 이후로는 되갚기가 아니라 **다시 쌓이는 국면**이다 — 급락일(7/28~7/30)에도, 지수가 +17.9%
급등한 7/31 에도 주수는 매일 늘었다. 숏커버 랠리의 모습이 아니다.

카드·요약·차트를 전부 주수 기준으로 바꾸고, 금액 카드에는 '되갚음이 아니다' 를 명시했다.

### 16.5 한계

- 대차잔고는 공매도 전용이 아니다(§16.1). 변화 전부를 숏 포지션 변화로 읽으면 과대해석이다.
- "오늘 시장이 급등한다"는 실시간 장중 정보는 이 데이터에 없다. FREESIS는 EOD 공표라
  하루 이상 지연되고, 이 분석의 마지막 관측일(2026-07-30)도 여전히 하락일이었다.
  다음에 데이터를 갱신하면 이 판정 로직이 그날을 자동으로 잡아낸다.
- 대차잔고와 신용융자는 서로 다른 시장 참여자(기관/외국인 vs 개인 신용거래)가 주로
  쓰는 통로라, 두 지표의 디레버리징 속도 차이를 곧바로 '누가 더 급했는가'로
  해석하기는 이르다.

## 17. 예탁금과 2차 레버리지 채널

### 17.1 왜 신용융자만 보면 안 되는가

§1~16 은 전부 **신용융자(OS0026)** 한 채널만 봤다. 원 자료가 그 채널을 다뤘기 때문이다.
그런데 금투협은 같은 크로스통계에서 두 계열을 더 공표한다.

| 계열 | 코드 | 성격 |
|---|---|---|
| 투자자예탁금 | OS0021 | 증권계좌에 들어와 있으나 아직 주식이 아닌 **대기자금** |
| 예탁증권담보융자 | OS0027 | 보유 주식을 담보로 받은 대출. 신용융자와 별개의 **2차 레버리지 통로** |

셋을 같이 놓아야 "레버리지가 감당 가능한가"를 볼 수 있다. 단위는 셋 다 백만원이라 `/1e6` 하면 조원이다.

### 17.2 결과 (2026-07-29 기준)

| 기준점 | 예탁금 | 신용융자 | 담보융자 | 총 레버리지 | 커버리지 |
|---|---|---|---|---|---|
| 2021 신용 고점 (2021-09-13) | 70.41조 | 25.65조 | 19.36조 | 45.01조 | 2.74배 |
| 2023 신용 저점 (2023-01-11) | 44.35조 | 15.81조 | 18.58조 | 34.39조 | 2.81배 |
| 2026 신용 고점 (2026-06-24) | 136.55조 | 38.63조 | 26.35조 | 64.98조 | 3.53배 |
| **현재 (2026-07-29)** | **109.59조** | **33.00조** | **25.52조** | **58.51조** | **3.32배** |

커버리지 = 투자자예탁금 ÷ 신용융자. 낮을수록 '빚 대비 실탄이 없다'는 뜻이다.
역대 최저 2.08배(2018-10-10), 최고 7.13배(2020-04-01, 코로나 폭락 직후 현금이 몰린 시점).

두 가지가 드러난다.

**(1) 디레버리징은 신용융자 채널에서만 일어났다.**
신용 고점(6/24) 이후 신용융자는 -14.6% 줄었는데 예탁증권담보융자는 **-3.2%** 에 그쳤다.
합친 총 레버리지로는 64.98조 → 58.51조, **-10.0%** 다.
신용융자만 보면 청산이 꽤 진행된 것처럼 보이지만 개인 레버리지 전체로는 그 절반 수준밖에 풀리지 않았다.
담보융자는 담보유지비율 기준이 신용융자와 달라 같은 지수 하락에도 강제 청산이 늦게 걸린다.
**§13 의 마진콜 사다리는 이 25.52조를 세지 않는다** — 사다리는 신용융자 채널의 하한이다.

**(2) 이 사이클은 2021년보다 실탄이 두껍다.**
커버리지는 2021년 신용 고점에서 2.74배였는데 이번 고점에서는 3.53배였고 지금도 3.32배(역대 78백분위)다.
§12.1 의 신용/시총 비율 결론("이번 사이클은 2021년만큼 과열된 적이 없다")과 방향이 같다.

### 17.3 한계

- 커버리지가 높다는 것이 **그 예탁금이 실제로 매수에 쓰인다**는 뜻은 아니다. 대기자금은 관망 자금이기도 하다.
  급락 국면에서 예탁금이 늘어나는 것은 오히려 '주식을 팔고 현금으로 앉아 있다'는 신호일 수 있다.
- 예탁증권담보융자의 담보유지비율·청산 트리거는 공표되지 않는다. 신용융자와 같은 0.84 계수를 적용할 근거가 없어
  이 채널에 대한 마진콜 사다리는 만들지 않았다. 그래서 §17 은 규모만 제시하고 청산 추정은 하지 않는다.
- 예탁금은 주식·채권·파생 전체의 대기자금이라 전액이 주식 매수 여력은 아니다.

## 18. 미수금 → 반대매매 전이

### 18.1 기계적으로 기대되는 것

위탁매매미수금(OS0024)은 결제하지 못한 외상 매수다. 결제일 D+2 까지 채우지 못하면
증권사가 반대매매(OS0025)로 처분한다. 그렇다면 미수금은 반대매매의 **2영업일 선행지표**여야 한다.
실제로 그런지 상관계수로 확인했다 — 미수금`[t]` 대 반대매매`[t+시차]`.

### 18.2 결과 — 선행하지 않는다

| 시차 | 전 구간(2010~) | 2025년 이후 |
|---|---|---|
| **0일** | **0.220** | **0.731** |
| 1일 | 0.210 | 0.730 |
| 2일 | 0.190 | 0.624 |
| 3일 | 0.176 | 0.592 |

상관은 **시차 0일**에서 가장 높고, 시차가 늘수록 단조 감소한다. D+2 규칙과 어긋나 보이지만,
금투협이 두 계열을 같은 **공표일** 기준으로 싣기 때문으로 읽는 것이 자연스럽다 —
미수금 잔고와 그에 대한 반대매매가 같은 날짜 라벨에 붙는다.

**결론: 이 데이터로 "미수금을 보고 이틀 뒤 반대매매를 예측"할 수 없다. 둘은 같은 날의 동시 지표다.**

전 구간 상관 0.220 이 낮은 것은 국면마다 절대 규모가 달라서다(2010년대와 2026년의 미수금 스케일이 다르다).
최근 구간(2025년 이후)만 보면 0.731 로 뚜렷하다.

### 18.3 전이율과 현재 수준

전이율 = 반대매매`[t]` ÷ 미수금`[t]`. 이상치에 끌려가지 않게 중앙값을 쓴다.

- 전이율 중앙값 **4.2%** — 미수금 대부분은 반대매매까지 가지 않고 결제된다.
- 현재 미수금 **1.20조**(2026-07-29), 최근 60일 평균 1.34조의 **90%**. 경보 수준이 아니다.
- 역대 상위: 2.15조(2026-03-05), 2.10조(2026-03-06), 2.07조(2026-06-25), 1.92조(2026-05-19), 1.83조(2026-06-04).
  상위 5일이 전부 2026년이다 — 이번 사이클의 거래 규모 자체가 과거와 다른 수준이라는 뜻이다.

### 18.4 한계

§7.4 를 다시 강조한다. 이것은 **미수거래**에 대한 반대매매다.
**신용융자 반대매매는 공표되지 않는다.** §1~13 의 추정치를 검증하지 않는다.

## 19. 공표 시차와 장중 지수

FREESIS 는 EOD 공표라 최신일이 하루 이상 늦다. 신용융자는 결제일 기준이라 지수보다 또 1~2일 늦는다(§7.2).
그래서 리포트 맨 위에 교차검증 소스(네이버 금융 일별 시세)의 최신 지수를 같이 싣는다.

2026-07-31 실행 시점 기준:

- FREESIS 최종 공표 **5,594p**(2026-07-30)
- 네이버 **6,361p**(2026-07-31) — **+13.73%**

본문의 모든 계산은 FREESIS 최종 공표일 기준이다. 장중에 돌리면 네이버 계열의 마지막 행은 종가가 아니라
진행 중인 값이므로 그렇게 표시한다.

**반등은 이미 터진 물량을 되돌리지 않는다.** 마진콜 판정은 그날까지의 **최저 지수** 기준이라(§6),
지수가 되돌아와도 이미 청산된 신용은 돌아오지 않는다. 반등이 막는 것은 **추가** 청산뿐이다 —
§12.2 에서 말한 "잔여 위험은 시간이 아니라 지수 경로에 달려 있다"의 반대 방향 사례다.

§16.5 에 적어둔 "다음에 데이터를 갱신하면 판정 로직이 그날을 자동으로 잡아낸다"는 아직 유효하다.
7/31 은 FREESIS·대차거래 공표 전이라 §16 의 숏커버링 판정에는 아직 들어오지 않았다.

## 20. 숏커버 여력 — 얼마나 더 되갚아져야 하는가

### 20.1 왜 이 계산이 §12와 대칭인가

대차잔고가 줄어든다는 것은 빌린 주식을 **사서 갚는다**는 뜻이다. 곧 매수 압력이다.
§12에서 신용잔고를 두고 "얼마나 더 팔려야 하나"를 벤치마크 범위로 봤다면,
여기서는 대차잔고를 두고 "얼마나 더 사야 하나"를 같은 방식으로 본다.
벤치마크가 하나로 수렴하지 않는 것도 §12와 같아서, 점 추정이 아니라 범위로 제시한다.

### 20.2 벤치마크 네 개 (2026-07-30 기준, 잔고 133.41조)

| 벤치마크 | 목표 잔고 | 잔여 커버 | 일거래대금 대비 |
|---|---|---|---|
| 사이클 시작 잔고로 복귀 (2024-12-31, 47.18조) | 47.18조 | **+86.24조** | 2.06배 |
| 사이클 시작 **비율**로 복귀 (2.05% × 현 시총 4,970조) | 101.79조 | **+31.62조** | 0.75배 |
| 직전 사이클 감소율 대입 (-25.1% × 이번 고점 195.30조) | 146.36조 | -12.95조 (소진) | -0.31배 |
| 잔고/시총 비율 정상화 (직전 저점 2.91% × 현 시총) | 144.62조 | -11.21조 (소진) | -0.27배 |

- 이미 되갚은 양: 고점(195.30조, 2026-06-15) → 현재 133.41조, **61.89조(-31.7%)**.
  최근 20영업일 평균 거래대금 41.95조 기준 **하루 거래대금의 1.5배**에 해당하는 매수가 이미 지나갔다.
- 잔여 범위: **-12.95조 ~ +86.24조** (음수 = 이미 소진)

### 20.3 읽는 법 — 비율로 보면 되돌림은 이미 끝났다

대차잔고/시총은 현재 **2.68%** 로 직전 사이클 저점 **2.91%** 보다 **이미 낮다**.
비율 기준 벤치마크 두 개가 모두 '소진'으로 나오는 이유다.

양(+)으로 남는 두 벤치마크 중 **절대 잔고 복귀(86.24조)** 는 상단 과대추정으로 봐야 한다 —
시가총액이 그 사이 배 가까이 커졌는데 잔고만 옛 절대 수준으로 돌아가라는 계산이기 때문이다.
시총 성장을 감안한 **사이클 시작 비율 복귀(31.62조, 하루 거래대금의 0.75배)** 가 더 현실적인 상단이다.

§12에서 신용잔고를 두고 내린 결론("2022년처럼 풀려야 한다는 전제가 이 사이클에는 그대로 적용되지 않는다")과
**구조가 같은 결론**이다. 양쪽 모두 직전 사이클 대비 정상화가 이미 상당히 진행됐다.

### 20.4 한계

- **지수 상승폭으로 환산하지 않는다.** 매수 물량 몇 조가 지수 몇 %가 되는지는 이 데이터로 알 수 없다.
  거래대금 대비 배수까지만 제시한다.
- §16.1 대로 대차잔고 감소 전부가 숏커버가 아니다. ETF 환매·차익거래 청산도 같은 방향으로 잡힌다.
  실제로 잔고 고점 이후 숏커버형(지수↑ 잔고↓) 날은 4일뿐이었다.
- '목표 잔고'는 되돌아갈 **수준**이지 되돌아갈 **시점**이 아니다. §12.2와 마찬가지로
  경로(지수가 어디로 가느냐)가 속도를 결정한다.
- 잔고/시총 비율 벤치마크는 시총이 지수와 함께 움직인다는 점에서 순환적이다 —
  지수가 오르면 목표 잔고도 같이 올라가 잔여가 줄어든다.

스트립은 현황 표시이지 계산 입력이 아니다.

### 21.2 한 점짜리 변화는 오해를 부른다

"전일 대비 -0.6%" 만 보면 그게 추세인지 잡음인지 알 수 없다. 그래서 지표를 누르면
최근 1년 추세가 펼쳐지고, 기간 고점·저점과 1년 등락률을 같이 보여준다.

`<details>`/`<summary>` 를 쓴다. 브라우저 기본 기능이라 스크립트가 없고, `file://` 로 열어도
동작하며, 탭(§9)과 같은 이유로 인쇄에도 문제가 없다. 차트는 빌드 시점에 SVG 문자열로 구워 넣는다.

메일 버전에는 접기가 없다(메일 렌더러가 `<details>` 를 대부분 지원하지 않는다).
`email.html` 은 같은 지표를 표 하나로 펼쳐 싣는다.

## 22. 자동 갱신을 러너에서 성립시키기까지

로컬에서 되는 스크립트가 GitHub 러너에서 안 되는 경우가 있었다. 저장소가 private 이라
Actions 로그를 URL 로 볼 수 없어, **진단 자체를 배포되는 `status.json` 에 실어** 원인을 좁혔다.
같은 상황이 다시 오면 이 순서를 그대로 쓰면 된다.

### 22.1 진단 경로를 먼저 만든다

1. 소스 하나가 실패해도 나머지는 갱신되게 한다(`|| ERR="$ERR <이름>"`). 전부 죽이면 아무것도 안 남는다.
2. 실패한 소스 이름을 `status.json` 에 싣는다 → **어느 소스인지** 확정.
3. 실패 메시지를 한 줄(`LENDING_FAIL ...`)로 찍고 `grep` 으로 집는다.
   노드 기본 예외 출력은 코드 프레임과 스택이 앞에 붙어, 잘라 담으면 정작 필요한 부분이 날아간다.
4. 메시지에 status·본문 길이·content-type·**파싱 실패 이유와 그 위치의 실제 글자**를 넣는다.

### 22.2 실제로 나온 답 — `######`

대차거래추이 응답에서 서버가 **자릿수를 넘는 값을 `######` 로 내보낸다**. 엑셀식 오버플로 표기이고
유효한 JSON 토큰이 아니라 `JSON.parse` 가 깨진다.

```
Expected ',' or '}' after property value in JSON at position 25675
부근: "TMPV4":2113695464,"TMPV5":112685######,"TMPV6":5695820084
```

걸린 곳은 연도별 **합계/평균 요약 행**이었고, 그 행들은 어차피 일자가 숫자가 아니라 버린다.
그래서 값 자리의 `###...` 만 `null` 로 바꿔 파싱한다(문자열 안의 `#` 은 건드리지 않는다).

이 값이 로컬에서는 안 나오고 러너에서만 나온 이유까지는 확인하지 못했다.
서버 쪽 포맷 결정에 요청 환경이 섞여 들어가는 것으로 보이나 근거가 없어 단정하지 않는다.
어느 쪽이든 무해화가 맞는 대응이다 — 요약 행은 쓰지 않기 때문이다.

### 22.3 그전에 걸렸던 것

- **응답 크기**: 16년치를 한 번에 요구하면 424KB 다. 연 단위로 끊어 받는다(`fetch-kofia.mjs` 와 같은 이유).
- **워크플로 YAML**: 한 줄 `run:` 안의 `': '` 를 YAML 이 키 구분자로 읽어 워크플로 전체가 파싱 실패했다.
  블록 스칼라(`|`)를 쓴다. `selfcheck.mjs` 가 이 패턴을 잡는다(§9.0).

### 22.4 확인된 최종 상태

```json
{ "ranBy": "github-actions", "fetchErrors": null, "selfcheck": "passed",
  "dataThrough": { "지수·거래대금": "20260730", "신용융자·예탁금": "20260730",
                   "대차잔고": "20260730", "교차검증 지수(네이버)": "20260731" } }
```

러너가 스스로 FREESIS 신규 공표분(신용융자·예탁금 07-29 → 07-30)을 받아 반영했다.

**정정 (2026-08-03) — KRX 는 봇 차단이 아니라 로그인 벽이다.** 다시 확인해 보니
`data.krx.co.kr` 이 **KRX Data Marketplace** 로 바뀌었고, 브라우저로 열면 **로그인 페이지**가 뜬다.
세션 쿠키를 붙여도, 실제 브라우저 안에서 같은 오리진으로 호출해도 똑같이 400 `LOGOUT` 이 온다 —
그 응답은 말 그대로 "로그인 안 됨" 이었다. 여러 수집기 주석에 "봇 차단" 이라고 적어 둔 것을 전부 정정했다.

실무적으로 달라지는 것:

- **익명 수집은 불가.** 헤더를 아무리 흉내 내도 안 된다. 우회를 시도할 문제가 아니다.
- 계정이 있으면 받을 수는 있다. 다만 **자격증명을 파이프라인에 넣지 않는다** — 사람이 직접 로그인해
  CSV/엑셀을 내려받아 `data/` 에 두고 `ingest-*.mjs` 가 읽는 방식이 이 저장소의 기존 패턴이다
  (§8 의 `신용공여 잔고 추이.xlsx` 와 동일).
- "Marketplace" 로 바뀐 만큼 **이용약관·재배포 조건**을 먼저 확인해야 한다. 이 리포트는 공개 배포 중이라
  더 그렇다.
- 이걸 받으면 얻는 것: **종목별 실제 공매도 잔고(순보유잔고)** — §16.1 에서 대차잔고를 프록시로 쓴
  이유가 사라진다. 그리고 투자자별 매매동향을 §27 의 20거래일 창 제약 없이 받을 수 있다.

좌수가 왜 결정적인가: AUM 은 좌수 × 가격이다. AUM 이 줄어도 좌수가 그대로면 **환매가 아니라 값이 빠진 것**이다.
"정리되었는가" 는 좌수로만 답할 수 있다.

### 23.2 AUM 분해

```
Δln AUM  =  Δln 좌수  +  Δln 가격
            (유출입)      (가격효과)
```

좌수 ↓ = 실제 환매(디레버리징). 좌수 → 이고 가격 ↓ = 물량은 남아 있음.
좌수 ↑ 이고 가격 ↓ = 하락 중 유입, 가장 위험한 조합.

`selfcheck.mjs` 가 세 항의 항등식과 `AUM = 좌수 × 종가` 를 매 실행 검사한다.

**AUM 은 순자산총액이 아니라 종가 × 좌수다.** 일별 NAV 소스를 못 구했다.
괴리율(시장가 vs NAV)만큼 오차가 있고, 레버리지 상품은 급변동 구간에서 이 괴리가 커진다.

### 23.3 리밸런싱 요구액

레버리지 배수 L 상품은 목표 노출을 유지하려고 매일 방향성 매매를 한다.

```
필요 매매액(t) = L(L − 1) × AUM(t−1) × r(t)        r = 기초자산 당일 수익률
  2X  : 계수 2   (오르면 사고 내리면 판다)
  -2X : 계수 6   (인버스가 3배 크다)
```

둘 다 부호가 r 과 같다 — **둘 다 추세를 증폭한다.** 인버스라고 반대로 작용하지 않는다.
규모가 작다고 인버스를 빼면 안 되는 이유다. `selfcheck.mjs` 가 부호 일치를 전 행에서 검사한다.

기초자산 수익률은 삼성전자·SK하이닉스 실제 종가에서 잡는다. 그래서 리밸런싱 계산은
**단일종목 상품만** 센다 — 섹터·지수형은 기초지수를 따로 받아야 하는데 그 소스가 없다.
빠진 만큼 아래 숫자는 하한이다.

### 23.4 지수 영향 — 무엇을 말하고 무엇을 말하지 않나

말하는 것 두 가지.

1. **거래대금 대비 비율** — 리밸런싱 필요액이 그날 그 종목 거래대금의 몇 %인가
2. **산술 기여** — 코스피 등락 중 두 종목이 설명하는 몫 = 시총비중 × 종목수익률

말하지 않는 것: **가격충격 계수.** 1조를 사면 지수가 몇 p 오르는지는 이 데이터로 알 수 없다.
PART 2 에서 숏커버 여력을 지수 상승폭으로 환산하지 않은 것과 같은 이유다(§20.4).

### 23.5 반증

"레버리지 ETF 때문이었다" 를 주장으로 두지 않으려면 아래를 같이 봐야 한다.

- **대조군**: 지수형 레버리지(예전부터 있던 물량)와 섹터형을 같은 창에서 비교한다.
  단일종목형만 좌수가 급증했고 섹터형은 오히려 환매됐다면, 그건 '레버리지 일반'의 이야기가 아니다.
- **상장 전후**: 삼성전자·SK하이닉스의 평균 일중 진폭을 2025년 / 2026년 상장 전 / 상장 후로 나눠 본다.
  진폭 상승이 상장 전에 이미 시작됐다면 ETF 는 유일한 원인이 아니다.
- **리밸 수요 ~ 진폭 상관**: 상위 20% 날과 나머지 날의 평균 진폭을 비교한다.

리포트는 이 셋을 전부 싣는다. 상관이 약하게 나오면 약하다고 쓴다.

### 23.6 홍콩(CSOP) — 자동화되기까지

`7709`(SK Hynix 2x)·`7747`(Samsung 2x)·`7347`(Samsung -2x)은 상품 페이지가 값을 JS 로 채워
정적 fetch 로는 빈 `<span>` 만 온다. 내부 API(`website-api.csopasset.com/cmsApi/NAV/product`)에
`fundCode`·`productCode`·slug 등 짐작 가는 파라미터를 다 넣어 봤지만 전부 500 이었다.
처음에는 브라우저로 열어 읽은 시점 스냅샷으로 때웠다.

풀린 경로는 파라미터 추측이 아니라 **페이지가 로드하는 상품 전용 JS 를 읽는 것**이었다.
상품 페이지는 `asset/lai/js/hk-skhy-2l.js` 같은 전용 스크립트를 `$.getScript` 로 불러오고,
그 안에 요청이 통째로 있다:

```js
url: webApi + "/cmsApi/NAV/product",  method: "POST",
data: JSON.stringify({ "productName": FundName })
// FundName = 'CSOP SK Hynix Daily Max (2x) Leveraged Product'  ← 상품 전체 영문명
```

키가 코드가 아니라 **상품 전체 영문명 문자열**이라 추측으로는 맞출 수 없었던 것이다.
이 바디로 POST 하면 통화별(HKD/USD) 행에 `NAV`(1좌)·`AUM`(총순자산)·**`Shares`(좌수)**·
`ContractValue`(스왑 명목 익스포저)·기준일이 온다. Node 에서 Origin 헤더만 붙이면 그대로 동작한다.

`scripts/fetch-csop.mjs` 가 이걸 매일 받아 두 파일을 쓴다.

- `data/csop-snapshot.json` — 최신 스냅샷. analyze 가 읽는다. **자동 생성이므로 손대지 말 것.**
- `data/csop-daily.json` — 기준일별 히스토리. CSOP 의 과거 API(ChartData)는 403 이라
  운용사 쪽 백필은 불가능하다 — CSOP 행은 2026-08-02 수집 시작 이후부터 쌓인다.

**과거 좌수는 다른 문에서 열렸다 — HKEXnews CCASS 조회(SDW).** 홍콩 상장 종목은
`www3.hkexnews.hk/sdw/search/searchsdw.aspx` 가 과거 12개월까지 날짜별 보유내역을 열어 두고,
응답 요약의 "Total number of Issued Shares/Warrants/Units" 가 **그 날짜 기준 발행좌수**다
(날짜별로 실제로 변하는 것을 7/31=829M, 7/26=840M, 6/16=707.5M 로 확인했다).
ASP.NET 폼이라 GET 으로 `__VIEWSTATE` 를 받고 날짜·종목코드로 POST 한다. 휴장일을 요청하면
서버가 날짜를 바꿔 돌려주므로, 응답에 박힌 날짜가 요청과 다르면 버린다.
`scripts/backfill-csop-units.mjs` 가 상장일(2025-10-16)부터 이 방법으로 백필했다(재실행하면 갭만 채운다).

**좌수의 기준이 셋이라는 것을 알고 읽어야 한다.** 7/31 하루에서 실측한 값:

```
등록기관 발행좌수(SDW)   829M   ← 백필 행(src:hkex-sdw)이 쓰는 값
CSOP 신고좌수(딜링일)    984M   ← 일별 수집 행이 쓰는 값
CCASS 보유총량          1,048M
```

창출·환매가 T+2 로 결제되는 동안 세 값이 벌어진다(평시엔 1% 안쪽: 6/16 은 707.5 vs 716.4).
그래서 히스토리에는 2026-08-01/02 이음새에 단차가 있을 수 있다. 5일 변화율 같은 추세 판정에는
지장이 없지만, 하루 단위 창출·환매량을 이 계열의 인접일 차분으로 읽으면 안 된다.

남은 한계 둘. (1) 조회 키가 상품명 문자열이라 **상품이 개명되면 조용히 깨진다** — 실제로
2026 년에 'Daily' → 'Daily Max' 개명이 있었다. `selfcheck.mjs` 의 NAV×좌수≈AUM 항등식과
워크플로의 `fetchErrors=csop` 가 그때의 경보다. (2) SDW 는 12개월 창이라, 이번에 백필해 둔
구간은 다시 만들 수 없는 기록이 된다 — csop-daily.json 을 지우면 복구 못 하는 날이 생긴다.

## 24. PART 4 — 다음 주 수급 전망

### 24.1 이 절이 답하는 질문과 답하지 않는 질문

답하는 것: **지수가 X% 움직이면 어떤 물량이 기계적으로 따라 나오는가.**
답하지 않는 것: **지수가 어디로 갈 것인가.**

수급은 방향을 만들지 않는다. 방향이 정해진 다음에 그 방향을 얼마나 증폭하느냐를 정할 뿐이다.
그래서 이 절은 예측이 아니라 **사전 기록**이다. 다음 주 숫자를 미리 적어 두면, 실제 움직임이
나온 뒤에 "수급이 원인이었나" 를 사후에 판정할 수 있다. 그게 이 절의 용도다.

### 24.2 세 축

| 축 | 계산 | 출처 |
|---|---|---|
| 레버리지 ETF 강제 매매 | 상품별 `L(L−1) × AUM × 시나리오 수익률` 합계 | PART 3 |
| 아래로 열리는 물량 | 마진콜 사다리 문턱까지의 거리(%)와 그때 열리는 금액 | PART 1 |
| 위로 나오는 물량 | 대차잔고 수준과 직전일 변화, 잔여 커버 여력 | PART 2 |

시나리오는 **지수 등락률을 종목 등락률의 대용치**로 쓴다. 삼성전자·SK하이닉스가 코스피 등락의
60~80% 를 설명하므로(§23.4) 쓸 만한 근사지만, 두 종목이 지수와 따로 놀면 어긋난다.
`selfcheck.mjs` 가 시나리오의 대칭성(±X% 에 부호만 반대인 같은 금액)과 부호를 검사한다.

### 24.3 과거 유사 국면(base rate)

2010년 이후 코스피 일별에서 조건을 만족한 날의 **다음 5거래일 수익률 분포**를 낸다.
조건은 낙폭(20거래일 −15%/−20%)과 급등일(+3%/+8%), 그리고 둘의 교집합이다.

표본이 10개 미만인 줄은 리포트에서 흐리게 표시한다 — **그건 근거가 아니라 일화다.**
실제로 이번 데이터에서 조건부 분포는 전 구간 기준선과 크게 다르지 않았다.
즉 "급락 뒤 반등" 이라는 조건만으로 다음 주 방향은 갈리지 않는다. 그렇게 쓴다.

### 24.4 제도 일정

계산으로 나오지 않는 유일한 입력이다. 외사 리포트에서 옮겨 적고 `analyze.mjs` 의 `EVENTS`
상수에 날짜와 함께 둔다. 세 건 모두 레버리지 재축적을 어렵게 만드는 방향이라, 하방 증폭기를
약화시키는 동시에 상승 탄력도 같이 줄인다 — **방향보다 진폭에 먼저 영향을 준다.**

### 24.5 외사 수치와의 대조 (`data/street-anchors.json`)

원문 PDF 는 제3자 저작물이라 저장소에 넣지 않는다(`.gitignore` 의 `*.pdf`, §2.5 와 같은 처리).
대조에 필요한 수치만 출처·발간일과 함께 옮겨 적는다. 사람이 새 리포트를 읽고 갱신한다.

여기서 **우리 계산과 갈리는 지점이 하나 있고, 그게 이 절에서 가장 중요한 관찰이다.**

세 하우스 모두 레버리지 ETF AUM 반토막(US$50~53bn → US$26bn)을 디레버리징의 진척으로 읽는다.
그런데 PART 3 의 좌수 분해로는 그 감소가 거의 전부 **가격효과**이고 좌수는 오히려 늘었다.
J.P. Morgan 도 같은 관찰을 적어 두었다 — 자금 유입은 계속 플러스라는 것이다(21 Jul 2026, Figure 9).

```
AUM 기준  : 고점 대비 반토막  ->  "정리가 끝나간다"
좌수 기준  : 오히려 증가       ->  "물량은 그대로 남아 있다"
```

두 척도가 반대 방향을 가리킨다. 어느 쪽을 보느냐가 다음 국면의 판단을 가른다.
이 리포트는 좌수를 기본으로 본다 — AUM 은 가격이 섞여 있어 수급 지표로 쓰기에 부적절하기 때문이다.

### 23.7 매일 보는 지표 하나 — 좌수가 꺾였는가

PART 3 에서 나온 결론이 하나로 줄면 이것이다: **AUM 이 아니라 좌수를 봐라.**
AUM 은 가격이 섞여 있어 "정리됐는지" 를 못 알려준다. 좌수가 꺾이는 날이 진짜 환매의 시작이다.

그래서 이 지표는 리포트를 열자마자 보이는 자리(핵심 요약 맨 위)에 고정으로 올렸고,
`status.json` 에도 실었다 — 사이트를 열지 않고도 확인할 수 있게.

판정 규칙은 5거래일 변화율 하나다. 단순하게 둔 이유는, 규칙이 복잡하면 매일 볼 수 없기 때문이다.

| 5일 변화 | 판정 | 뜻 |
|---|---|---|
| > +1% | `building` 아직 쌓이는 중 | 디레버리징은 시작되지 않았다 |
| −1% ~ +1% | `flat` 정체 | 증가가 멈췄다. 꺾이는 길목일 수 있다 |
| < −1% | `rolling` 꺾였다 | 여기서부터가 진짜 환매다 |

같이 싣는 보조 숫자: 전일/5일/10일 변화, 최대 좌수 대비, 그 최대가 며칠 전인지, 연속 감소일.
**연속 감소일을 따로 세는 이유**는 하루 반짝 감소를 꺾임으로 읽지 않기 위해서다.

`selfcheck.mjs` 가 판정과 5일 변화율이 어긋나지 않는지, 최대값이 최신값보다 작지 않은지를 검사한다.

## 25. 시장별 되돌림 진척 — 합계가 가리던 결론

**§8.1** 에서 두 시장의 청산 진행률이 다르다는 것까지 확인했다. 여기서는 그것을 판정으로
밀고 나간다 — 그리고 그 판정이 방법론 문서에만 있고 리포트에는 없어서, 이번에 리포트로 옮겼다.

PART 1 의 청산률은 유가증권+코스닥 **합계**다. 그런데 이번 사이클에서 두 시장은 정반대로 움직였고,
합계는 그 둘을 평균 내 어느 쪽 이야기도 하지 못한다. 실제로 합계 청산률 −16.8% 는
코스닥의 −38.3% 와 코스피의 −13.5% 를 섞은 값이다. 그래서 시장별로 따로 계산해 리포트에 실었다
(`analysis.json` 의 `divergence`, PART 1 "같은 사이클을 두 시장이 다르게 지나고 있다").

### 25.1 왜 청산률만으로는 부족한가

고점 대비 청산률(`unwindPct`)은 **고점**을 기준선으로 잡는다. 고점이 얼마나 비정상이었는지를
묻지 않으므로 "원래대로 돌아왔나" 에는 답하지 못한다. 그래서 기준선이 다른 지표를 셋 더 놓았다.

| 지표 | 기준선 | 답하는 질문 |
|---|---|---|
| `unwindPct` 고점 대비 청산률 | 사이클 고점 | 고점에서 얼마나 빠졌나 |
| `retracedPctOfBuild` 쌓은 것 대비 되돌림 | **사이클 시작 잔고** | 이번에 쌓은 것을 얼마나 토해냈나 |
| `multipleOfStart` 현재/시작 배수 | 사이클 시작 잔고 | 시작 수준으로 돌아왔나 |
| `ratioVsPrevTrough` 신용/시총 ÷ 직전 저점 비율 | **직전 사이클 저점** | 지난번 바닥만큼 내려왔나 |

네 지표가 같은 방향을 가리킬 때만 "끝났다" 고 말한다. 코스닥은 넷 다 같은 쪽이다 —
쌓은 것의 95% 반납, 잔고가 시작의 1.04배, 청산률 −38.3% 가 직전 사이클 완주치 −36.9% 를 넘음,
신용/시총이 직전 저점의 0.80배. 코스피는 넷 다 반대쪽이다(17%, 2.83배, 완주치의 32%, 1.27배).

### 25.2 시장별 신용/시총 — 두 시장을 서로 견주지 않는다

분모는 시장별 시가총액이다(`OS0008` 유가증권, `OS0009` 코스닥. 억원 단위라 ×100 하면 백만원).
전체 비율(§8)은 두 시장이 섞여 이 질문에 답하지 못하므로 따로 만들었다.

**수준을 시장 간에 직접 비교하면 안 된다.** 코스닥은 평시에도 코스피의 서너 배다
(직전 저점끼리 2.304% vs 0.440%). 그래서 각 시장을 **자기 과거**와만 견줬다.

두 가지 편향을 알고 읽어야 한다.

1. 분모인 시가총액이 급락으로 빠르게 줄어 비율이 실제보다 **높게** 보인다. 즉 코스피가 저점 비율
   위에 있다는 판정은 그만큼 **보수적**이고, 코스닥이 저점 아래라는 판정은 그만큼 **더 강하다**.
2. 신용융자는 결제일 기준이라 잔고 기준일이 지수보다 하루 늦다. 급등락 직후에는 이 하루가 크다.

### 25.3 남은 여지

`toPrevTroughJo` = 현재 잔고 − (직전 저점 비율 × 현 시총). 음수면 0 으로 자른다.
코스피 5.63조, 코스닥 0조다. 이것은 **강제 청산 예측이 아니라 정상화 기준선까지의 거리**다 —
마진콜 사다리(§13)와 달리 트리거가 없고, 지수가 더 빠지면 새 물량은 별도로 열린다.

`selfcheck.mjs` 가 항등식(쌓은 것 = 고점 − 시작, 되돌린 것 = 고점 − 현재, 비율 = 잔고 ÷ 시총)과
판정 일관성(저점 비율 아래 ⇔ 남은 여지 0 ⇔ `doneMarkets` 포함)을 검사한다.

## 26. 종목별 대차잔고와 외국인 지분율 (PART 2 보조)

시장 전체 대차잔고(§16)는 "얼마나 더 오를 수 있나" 를 묻는다. 이 절은 **그 잔고가 어디에 붙어
있나** 를 묻는다. 코스피 등락의 상당 부분을 삼성전자·SK하이닉스가 설명하므로(§23.4), 지수의
상방 여력을 볼 때 이 둘의 잔고가 시장 평균과 같이 움직이는지가 중요하다.

### 26.1 종목별 대차잔고 — 같은 엔드포인트의 숨은 파라미터

`fetch-lending.mjs` 가 쓰는 FREESIS 대차거래추이(STATSCU0100000140)에 이미
`tmpV72`(종목) 파라미터가 있었다. 빈 값이면 시장 전체이고, **6자리 종목코드**를 넣으면
종목별 계열이 그대로 온다. 표준코드(`KR7005930003`)나 종목명을 넣으면 합계 행만 돌아온다 —
6자리 숫자여야 한다. 새 엔드포인트를 찾을 필요가 없었다.

**금액 컬럼은 쓰지 않는다.** 잔고금액(TMPV6)은 시장 전체와 같은 백만원 단위이고
주수 × 종가 / 1e6 과 정확히 일치하는 것을 384일 전부에서 확인했지만, 표시 금액은
**주수 × 종가로 다시 계산한다.** 주수는 단위 모호성이 없고, PART 3 에서 ETF 를 AUM 이 아니라
좌수로 본 것과 같은 이유다. 원본 금액은 파일에 남겨 두고 `selfcheck.mjs` 가 둘이 1% 넘게
어긋나는지 감시한다 — 어긋나면 소스가 컬럼 의미나 스케일을 바꾼 것이다.

### 26.2 두 종목을 한 축에 놓는 법

주수 그대로는 비교가 안 된다(삼성전자 94.7백만주 vs SK하이닉스 13.6백만주, 7배). 금액도 안 된다 —
주가가 6.5배 차이라 24.9조 vs 23.4조로 **거의 같아 보이는 착시**가 생긴다. 그래서 차트는
**상장주식수 대비 비중**으로 그린다. 두 종목을 같은 자로 잰 유일한 값이다.

### 26.3 외국인 지분율

네이버 금융 `item/frgn.naver`(EUC-KR, 한 페이지 20행)에서 외국인 보유주식수와 지분율을 받는다.
KRX 정보데이터시스템에도 있지만 로그인이 필요해 익명으로는 못 받는다(§23.1).

차트는 0 기준이 아니라 값 범위에 맞춰 그린다. 46~56% 구간을 0부터 그리면 직선으로 보여
움직임이 사라진다. `levelChart` 에 `zeroBase:false` 를 주면 된다.

### 26.4 이 두 계열을 섞어 읽으면 안 된다

- **대차잔고는 공매도의 프록시일 뿐이다.** 빌린 주식이 전부 공매도로 나가지 않는다
  (차익거래·ETF 설정·의결권 대차가 섞인다). 되갚기가 전부 숏커버 매수인 것도 아니다.
- **외국인 지분율은 보유 기준**이라 대차로 빌려준 주식도 그대로 잡힌다.
  두 계열을 더하거나 빼면 안 되고, 각각의 방향만 읽는다.
- 종목별 **실제 공매도 잔고**(순보유잔고)는 KRX 가 따로 공표하지만 로그인이 필요해 익명으로는 못 받는다.
  받을 수 있게 되면 프록시 대신 그것을 쓰는 게 맞다.

## 27. 투자자별 순매수 — "개인이 항복했나" 에 답하는 조각

§23 은 좌수로 디레버리징을 판정한다. 그런데 좌수가 늘었다는 사실만으로는 **누가 샀는지** 를 모른다.
개인이 대량으로 팔아도 기관이 그만큼 받으면 좌수는 안 움직인다. 항복(자발적 투항) 판정은
투자자별 순매수가 있어야 선다.

### 27.1 소스 — 개인을 직접 주는 곳은 하나뿐이었다

| 소스 | 개인 순매수 | 히스토리 | 판정 |
|---|---|---|---|
| KRX 정보데이터시스템 | 있음 | 김 | **로그인 필요**(§23.1) |
| 네이버 `item/frgn`, 다음 `investor/days` | **없음**(기관·외국인만) | 384일+ | 근사만 가능 |
| **네이버 모바일 `m.stock.naver.com/api/stock/{code}/trend`** | **`individualPureBuyQuant` 직접** | 최근 20거래일 | **채택** |

**결정적 제약: 모바일 API 는 `page` 를 무시하고 20행만 준다.** page=1,2,3 이 전부 같은 20행이고
`pageSize=100` 은 실패한다. 과거를 만들 수 없으므로 **매일 받아 누적**한다 —
홍콩 CSOP 좌수(§23.6)와 같은 방식이고, 워크플로에 넣어 하루도 거르지 않게 했다.

근사(`개인 ≈ −(기관 + 외국인)`)의 정확도도 재 봤다. 잔차(=기타법인)는 **총량 대비 2.4~2.9%** 로
작지만, 개인 순매수가 작은 날은 **상대오차가 26~194%** 로 부호가 뒤집힌다.
그래서 긴 히스토리를 근사로 채우더라도 추세에만 쓰고 하루 단위 판정에는 쓰지 않는다.

### 27.2 읽을 때의 함정 셋

1. **수량(주)이지 금액이 아니다.** 1좌 가격이 상품마다 달라 종목 간 절대량 비교는 의미가 없다.
2. **순(net)이다.** 같은 개인 안에서 사는 쪽과 파는 쪽이 상쇄된다.
   "개인 전체가 샀다" 가 아니라 "개인 합계가 순매수였다" 로 읽어야 한다.
3. **창이 20거래일이다.** 지금의 판정은 그 창 안에서의 판정이다.

### 27.3 결과 (2026-07-06~08-03)

- 22종목 중 **19종목**에서 개인 순매수. 단일종목 레버리지 14종 중 13종 순매수, 합계 **+102.1백만주**
- 그 사이 해당 상품들은 **−50~−63%** 였다
- 인버스 상품에서는 개인이 **순매도**(그 상품은 +13.7% 상승) — 오른 걸 팔고 빠진 걸 샀다

같은 기간 반대매매는 역대 상위 0.3%, 위탁매매미수금은 역대 6위였다(§17·§18). 두 사실이 상충하지 않는다.

> **신용으로 산 개인은 강제로 털렸고, 현금·ETF 로 산 개인은 오히려 사들였다.**

즉 지금 나온 것은 **강제 청산 + 물타기**의 조합이지 항복이 아니다. 자발적 투항이 아직 없다는 것은
팔아야 할 물량이 남아 있다는 뜻이라, 바닥 신호로 읽으면 안 된다.

## 28. 예탁금 대비 신용융자 — 그리고 "정상 수준" 을 어떻게 정할 것인가

§17 의 예탁금 커버리지(예탁금 ÷ 신용융자, 배)를 뒤집으면 **신용융자 ÷ 예탁금(%)** 이다.
같은 정보인데 "빚이 대기자금의 몇 % 인가" 로 읽혀서 과열 여부를 묻기 쉽다.
`analysis.json` 의 `channels.creditToDeposit` 이 이 계열을 담는다.

### 28.1 고점 대비로만 보면 안 된다

"고점보다 낮으니 정상화됐다" 는 그 고점이 **비정상이었을 때만** 성립한다. 고점 자체가 평범했다면
그 비교는 아무것도 말해주지 않는다. 그래서 기준선을 중앙값으로 따로 만든다.

| 기준선 | 값 |
|---|---|
| 전 구간(2010~) 중앙값 | 33.6% |
| 최근 3년 중앙값 | 32.7% |
| 2024년 중앙값 | 34.5% |
| 사이클 직전(2024-12) 중앙값 | 30.4% |

### 28.2 결과 — 5~6월도 과열이 아니었다

- **현재 27.8%** (2026-07-31, 신용 28.93조 ÷ 예탁금 104.1조). 역대 **16분위**
- 역대 최고 **48.0%** (2018-10-10) 의 58% 수준
- 이번 사이클 고점은 35.7%(2025-03-18)이고, **신용융자 절대액이 사상 최대 38.63조를 찍은
  2026-06-24 조차 이 비율은 28.3%** 였다 — 예탁금이 136.6조로 같이 불어났기 때문이다
- 그 달 최대치 30.7% 도 최근 3년 중앙값 32.7% 보다 낮다

즉 **"정상까지 내려왔나" 가 아니라 애초에 이 지표로는 과열인 적이 없었고, 지금은 정상보다 아래다.**
신용 절대액(§12)과 결론이 갈리는 지점이라, 둘을 같이 봐야 한다.

### 28.3 담보융자를 더하면 방향이 뒤집힌다

| | 신용 고점달(2026-06) | 현재 |
|---|---|---|
| 신용융자 / 예탁금 | 30.7% | **27.8%** ↓ |
| (신용+담보융자) / 예탁금 | 51.6% | **52.2%** ↑ |

담보융자 25.45조가 거의 안 줄어드는 사이 **예탁금이 더 빨리 빠져서**, 총 레버리지 기준으로는
지금이 6월보다 높다. §17 의 "마진콜 사다리가 안 세는 레버리지" 가 비율에서도 똑같이 나타난다.
`divergesFromTotal` 플래그가 이 역전을 잡아 리포트 문구를 바꾼다.

### 28.4 이 비율의 구조적 한계

**분모가 분자와 같은 방향으로 움직인다.** 예탁금은 2026-06-24 136.6조 → 07-31 104.1조로 24% 빠졌다.
급락 국면에서는 빚도 줄지만 대기자금도 같이 나가므로, 이 비율은 위험을 **과소평가**한다.
역대 최고 48.0%(2018-10-10)가 지금보다 훨씬 높은 것도 그 시절 예탁금 규모가 전혀 달랐기 때문이지,
당시 레버리지 절대액이 지금보다 컸다는 뜻이 아니다.
그리고 예탁금은 **대기자금**이지 반드시 매수에 쓰이는 돈이 아니다(§17 과 같은 단서).

`selfcheck.mjs` 가 항등식(비율 = 신용 ÷ 예탁금, 커버리지의 역수), 총 레버리지 ≥ 신용 단독,
역전 판정과 실제 값의 일치를 검사한다.

### 27.4 좌수로 항복을 판정하면 3거래일 늦다 (검증)

개인이 판다고 좌수가 그날 줄지 않는다. 개인의 매도는 **유통시장** 거래라 소유자만 바뀌고,
좌수는 LP/AP 가 **환매(redemption)** 를 걸어야 줄어든다. 이 구조를 데이터로 확인했다.

단일종목 레버리지 14종에 대해 `개인 순매수[t]` 와 `좌수 변화[t+lag]` 의 상관을 쟀다.
종목 규모가 제각각이라 **둘 다 전일 좌수 대비 %로 정규화**하고, 풀링이 아니라 **종목별로** 계산했다
(원단위로 풀링하면 큰 종목 몇 날이 상관을 지배해 r=0.90 같은 허수가 나온다 — 실제로 처음에 그렇게 나왔다).

| lag | 상관 중앙값 | 양(+) 종목 |
|---|---|---|
| 0일 | **-0.04** | 6/14 |
| 1일 | -0.19 | 3/14 |
| 2일 | -0.03 | 5/14 |
| **3일** | **+0.72** | **13/14** |
| 4일 | +0.31 | 11/14 |
| 5일 | -0.01 | 6/14 |
| 6일 | +0.08 | 7/14 |

**당일 상관이 사실상 0이고 3일에서 봉우리를 이룬 뒤 감쇠한다.** 봉우리가 하나이고 뒤로 사그라드는
모양이라 주기성 착시가 아니라 결제 시차로 읽는다. 표본이 20거래일뿐이라 종목당 관측이 16개다 —
상관계수 자체보다 **13/14 종목이 같은 부호**라는 점(부호검정 p≈0.001)이 근거의 중심이다.

**결론: 항복 판정의 1차 지표는 개인 순매도이고, 좌수는 3일 지연된 확인용이다.**

### 27.5 수량이 아니라 금액으로 봐야 한다

순매수 수량(주)만 보면 20거래일 내내 순매수다. 그런데 1좌 가격이 상품마다 달라 14종을 더할 수 없고,
무엇보다 "얼마나 팔았나" 는 금액이라야 답이 된다. `순매수액 = 순매수 수량 × 종가` 로 환산하면
그림이 갈린다.

- 누적 순매수 2026-07-30 **23,291억** → 08-03 **11,232억** (고점 대비 **51.8% 반납**)
- **2026-07-31 하루에 11,599억 순매도** — 지수가 +17.9% 급등한 날이다
- 최근 5일 합계 **-771억** vs 그 이전 15일 **+12,003억** — 부호가 갈린다

수량 기준 판정("물타기")과 금액 기준 판정("매도 전환")이 어긋날 때는 **금액이 최신 신호**다.
`summary.recentTurn` 이 이 전환을 잡아 리포트 문구를 바꾼다.
그리고 §27.4 에 따라 이 매도는 **아직 좌수에 안 나타났다** — 며칠 뒤 좌수가 꺾이는지가 확인 절차다.

## 29. 신용잔고는 왜 하루 늦나 — 네이버로 바꿔봤자다

"네이버가 매일 알려주니 래깅을 없애자" 는 제안을 실측으로 검토했다(2026-08-05).
**결론: 바꾸면 오히려 하루 더 늦어진다.**

| 소스 | 최신일 | 신용잔고 |
|---|---|---|
| FREESIS (지금 쓰는 것) | **2026-08-04** | 27.40조 |
| 네이버 `sise/sise_deposit.naver` | 2026-08-03 | 27.05조 |

**투자자예탁금은 두 소스가 소수점까지 같다.** 신용잔고만 네이버가 일정하게 0.39~0.48조 낮은데,
이 차이가 날짜와 무관하게 거의 고정이라 정의가 다른 것으로 본다(포함 범위 차이).

지연의 정체는 소스 선택이 아니라 **공표 주기**다. 신용융자 잔고는 결제일 기준으로 확정돼
다음 날 공표된다. 그래서 지수가 T일이면 신용융자는 T-1 일이 최선이고, 지금 리포트가 정확히
그 상태다(지수 08-05 / 신용융자 08-04). 워크플로가 하루 두 번(19:30·08:30 KST) 돌아
공표되는 즉시 받아 오므로 더 줄일 여지가 없다.

리포트의 "데이터 최신일" 줄이 계열별 날짜를 각각 보여주는 이유가 이것이다 — 한 화면에 섞인
숫자들의 기준일이 다르다는 것을 숨기지 않기 위해서다.

## 30. 좌수만 보면 안 된다 — AUM 은 다른 질문에 답한다

§23.2 는 "AUM 이 아니라 좌수" 를 강조한다. 그 자체는 맞지만, **좌수만 보면 놓치는 것이 있다.**

- **좌수**: 환매가 있었나 = 포지션이 청산됐나
- **AUM**: 그 포지션이 시장에 주는 **충격의 크기**

리밸런싱 필요액(§23.3)은 `계수 × AUM × 수익률` 이라 **AUM 에 비례**한다. 거래대금이 시장에서
차지하는 몫(§23.8)도 마찬가지다. 그래서 좌수가 그대로여도 AUM 이 반토막이면
**물량은 남았지만 그 물량이 밀어내는 매매는 그만큼 작아진다.**

두 지표가 정반대를 말할 때가 이번 사이클이다 — 단일종목 레버리지 좌수는 사상 최대인데
합계 AUM 은 고점 대비 -46%다. 어느 하나만으로 "정리됐다/안 됐다" 를 말하면 틀린다.
그래서 핵심 요약에 좌수 박스와 **AUM·거래대금 박스를 나란히** 뒀다.

## 31. 외사 리서치 차트 세 개를 우리 데이터로 재현

외사 리포트의 차트 형식을 참고해 같은 질문을 우리 원천 데이터로 다시 계산했다.
숫자가 그쪽과 정확히 같을 필요는 없다 — 정의와 표본이 다르다. 중요한 건 **결론이 같은 방향인가**다.

### 31.1 레버리지 ETF AUM 분해 — 자금이냐 가격이냐

일별 유출입 `flow_t = Δ좌수 × 그날 종가` 로 잡아 누적하고, AUM 에서 그걸 뺀 나머지를
가격 기여분으로 본다. 항등식 `AUM = (시작규모 + 누적 유출입) + 가격 기여분` 이 성립하며
`selfcheck.mjs` 가 전 구간에서 이를 검사한다.

- 고점 **37.9조**(2026-06-22) → 현재 **20.3조**, 감소 **17.6조**
- 그 감소의 **149%가 가격**이고, 자금은 오히려 **49%만큼 순유입**이었다

차트는 **쌓은 면적**으로 그린다 — 누적 유출입(자금)과 가격 기여분이 합쳐져 AUM 이 되는 구조라,
선 세 개보다 면적이 구성비를 바로 보여준다. AUM 은 그 위에 선으로 겹친다.

**시장 대비 익스포저.** 레버리지 익스포저 = `Σ(AUM × |배수|)` 로, ETF 가 실제로 기초자산에
걸고 있는 명목 규모다. 시가총액으로 나누면 "이 상품군이 시장의 몇 %를 흔들 수 있나" 가 된다.

- 고점 **75.7조**(2026-06-22) = 시총의 **1.02%**
- 현재 **40.6조** = 시총의 **0.75%**

**분모가 자유유통(free float)이 아니라 전체 시가총액**이라는 점을 유의해야 한다. 외사는 free float
기준을 쓰는데, 유통주식만으로 나누면 이 비율은 더 커진다. 자유유통 비율은 이 파이프라인에 없다.

즉 AUM 이 반토막 난 것은 환매가 아니라 값이 빠진 결과다. §23.2 의 좌수 관찰과 같은 이야기가
금액 축에서 다시 확인된다. 외사 차트가 "누적 유입은 계속 늘었다" 고 적은 것과 방향이 같다.

### 31.2 마진콜 스트레스 — 반대매매 ÷ 미수금

절대액은 시장 규모에 끌려다니므로 비율로 본다. 하루치는 튀어서 **5일 이동평균**을 쓴다.

- 현재 **4.5%**(2026-08-04), 평시 중앙값 **4.15%** → **1.08배**
- 급락기 고점은 6.79%(2026-06-11)

**평시 수준으로 돌아왔다** — 급락기에 터진 강제 청산은 대체로 소화됐다는 뜻이고,
외사가 "deleveraging stress has been absorbed" 라고 쓴 것과 같은 결론이다.
다만 이 비율은 **미수거래 기준**이라 신용융자 반대매매는 안 센다(§18). 그쪽은 공표되지 않는다.

### 31.3 외국인 지분율의 z점수

지분율의 이 구간 평균·표준편차를 내고 현재가 몇 σ 떨어져 있는지 본다.

| 종목 | 현재 | 평균 | σ | z |
|---|---|---|---|---|
| 삼성전자 | 46.67% | 50.10% | 1.54%p | **-2.23** |
| SK하이닉스 | 51.00% | 53.98% | 1.53%p | **-1.95** |

외사가 KOSPI 반도체 섹터에 대해 "-2 s.d. below the long-term mean" 이라고 한 것을
두 종목 단위로 재현한 셈이다.

**중요한 단서**: 표본이 387일이라 여기서 말하는 '평균' 은 **장기 평균이 아니라 이 구간의 평균**이다.
외사는 2000년 이후를 쓴다. 수집이 쌓이면 밴드가 넓어져 z 가 완화될 수 있으므로,
이 숫자를 "역사적 극단" 으로 확대해석하면 안 된다.

## 32. 좌수로 "개인이 팔았다" 를 판정할 수 있나 — 없다

세 지표가 각각 다른 질문에 답하는데, 하나로 셋을 대신하려다 틀리기 쉽다.

| 질문 | 지표 |
|---|---|
| 개인이 팔았나 | **투자자별 순매수**(§27) |
| 자금이 상품에서 빠졌나 | **좌수**(§23.2) |
| 시장에 주는 충격은 | **AUM·레버리지 익스포저**(§31.1) |

### 32.1 실측 — 부호가 어긋난 날이 46%

단일종목 레버리지 14종에서 `개인 순매수` 와 `좌수 변화` 의 **부호가 같은 날**을 셌다.

- 관측 **211쌍** 중 부호 불일치 **97쌍 = 46%**
- 예: 2026-07-09 KODEX SK하이닉스 레버리지 — 개인이 2.9백만주 **순매도**했는데 좌수는 3.6백만주 **증가**
- 2026-07-15 — 개인 19.6백만주 순매도, 좌수 3.6백만주 증가

**좌수 감소는 개인 매도의 필요조건도 충분조건도 아니다.**

- **필요조건 아님**: 개인이 팔아도 다른 투자자가 받으면 좌수는 그대로거나 오히려 는다.
  개인의 매도는 **유통시장** 거래라 소유자만 바뀐다.
- **충분조건 아님**: 기관·외국인이 판 것이 환매로 이어져도 좌수는 준다.
  좌수는 **모든 투자자를 합친 순(net) 결과**라 **누가** 팔았는지 말하지 않는다.

### 32.2 그래도 좌수가 무의미하진 않다

§27.4 에서 잰 대로 좌수는 개인 순매수를 **3거래일 뒤에** 따라간다(lag 3 상관 +0.72, 14종 중 13종 동일 부호).
당일 상관이 -0.04 인 것과 위 46% 불일치는 같은 사실의 두 표현이다.
좌수는 **지연된 순(net) 확인용**이지 실시간 판정 도구가 아니다.

## 33. 규모보다 회전이 먼저 식는다

레버리지 ETF 를 시장 대비 비율로 보면 무엇이 얼마나 줄었는지가 분명해진다.

| 지표 | 고점 | 현재 | 변화 |
|---|---|---|---|
| AUM | 37.9조 (06-22) | 20.3조 | **-46%** |
| AUM / 시가총액 | 0.51% | 0.37% | -0.14%p |
| 레버리지 익스포저 | 75.7조 (06-22) | 40.6조 | **-46%** |
| 익스포저 / 시가총액 | 1.02% | 0.75% | -0.27%p |
| 거래대금 | 25.6조/일 (06-24) | 8.5조 (최근5일평균) | **-67%** |
| 거래대금 / 시장 전체 | **46.4%** (07-21) | **22.9%** | **-23.5%p** |

**거래대금이 AUM 보다 더 크게 줄었다**(-67% vs -46%). 고점에는 이 상품군이 시장 전체 거래대금의
**46%** 를 차지했다. 변동성을 만든 것은 잔고가 아니라 **회전**이었고, 회전이 먼저·더 크게 식는다.

주의 둘. ETF 는 유가증권시장에 상장돼 그 거래대금이 **시장 합계에 포함**되므로 이 비율은
별도로 더해지는 몫이 아니라 **비중**이다. 그리고 시총 대비 비율의 분모는 **자유유통이 아닌 전체
시가총액**이라, free float 기준을 쓰는 외사 수치보다 작게 나온다(§31.1).

### 33.1 국내만 보면 절반을 놓친다 — 홍콩 CSOP

삼성전자·SK하이닉스에 걸린 단일종목 레버리지는 국내 상장분이 전부가 아니다.
홍콩 CSOP 이 같은 두 종목으로 상품을 낸다. 합쳐야 실제 익스포저가 나온다.

| 2026-08-06 | AUM(조) | 익스포저(조) | 비중 |
|---|---|---|---|
| 국내 단일종목 레버리지 14종 | 7.54 | 15.07 | 47% |
| 국내 단일종목 인버스 2종 | 0.14 | 0.28 | 1% |
| 홍콩 CSOP SK하이닉스 (7709) | 7.09 | 14.38 | 44% |
| 홍콩 CSOP 삼성전자 (7747·7347) | 1.39 | 2.77 | 9% |
| **합계** | **16.15** | **32.50** | 100% |

**홍콩이 국내보다 크다**(52%). 특히 SK하이닉스는 **7709 한 종목이 7.09조**로 국내 단일종목
레버리지 전체와 맞먹는다. 국내만 세면 이 종목의 레버리지를 절반쯤 놓친다.
USD→원 환산은 그날 환율, 홍콩 익스포저는 CSOP 이 공시하는 명목(ContractValue)이다.

### 33.2 ETF 시장 안에서의 크기 — 덩치는 작고 거래는 크다

전체 ETF 거래대금이 필요해 네이버 `api/sise/etfItemList` 의 전 종목 스냅샷을 합산한다.
**과거를 주지 않으므로 매일 받아 `data/etf-market.json` 에 누적**한다(CSOP 좌수와 같은 방식).

- 전체 ETF **1,160종**, 거래대금 **15.93조**, 시가총액 **445.9조**
- 국내 단일종목 레버리지·인버스: 거래대금 **0.92조 = ETF 시장의 5.8%**
- 같은 상품군 AUM 은 ETF 시가총액의 **1.7%**

**덩치는 1.7%인데 거래는 5.8%** — 회전율이 다른 상품군과 자릿수가 다르다.
시장에 주는 영향이 AUM 비중보다 큰 이유가 여기 있다(§33 의 "회전이 먼저 식는다" 와 같은 이야기).

**단위 함정**: `amonut` 은 백만원, `marketSum` 은 **억원**이다(KODEX 200 으로 검산 — 거래대금
1.78조 = quant×nowVal, 시총 242,445억 = 24.2조). 이걸 틀리면 ETF 시총이 4.5조로 나와
단일종목 비중이 172% 같은 값이 된다. `selfcheck.mjs` 가 범위로 잡는다.

## 34. 해외 반도체 공매도 — 주기가 다른 두 계열

국내는 종목별 실제 공매도 잔고를 못 받아 대차잔고를 프록시로 쓴다(§16.1, §26.4).
미국은 **공매도 잔고가 직접 공표**되므로 프록시가 필요 없다. 대신 주기가 다른 두 계열을
섞지 않는 것이 관건이다.

| 계열 | 주기 | 소스 | 무엇인가 |
|---|---|---|---|
| 공매도 잔고(short interest) | **월 2회** (15일·말일 정산, +8영업일) | FINRA `consolidatedShortInterest` | 깔려 있는 잔고 |
| 일별 공매도 거래량 | **매일** | FINRA Reg SHO 일별 파일 | 그날 매도 중 공매도 비중 |

**"매일 업데이트" 는 거래량만 가능하다.** 잔고는 소스가 월 2회라 원천적으로 불가능하다 —
수집기는 매일 돌지만 잔고 값은 보름에 한 번 바뀐다. 리포트에 두 계열의 기준일을 각각 표시한다.

### 34.1 거래량 비중의 절대 수준을 읽으면 안 된다

공매도 거래량에는 **마켓메이커의 헤지성 매도**가 섞인다. 미국 대형주는 평시에도 40~50%가 흔하다.
그래서 절대 수준이 아니라 **같은 종목의 시계열 대비 z점수**로 본다.

2026-08-06 기준 (41거래일 표본):

| 종목 | 공매도 거래비중 | 20일 평균 | z | 잔고 변화(vs 06-30) |
|---|---|---|---|---|
| **MU** (마이크론, DRAM 순수주) | 53.1% | 42.1% | **+1.63** | **+14.3%** |
| TSM | 46.4% | 39.6% | +1.11 | +20.3% |
| SOXL (반도체 3X) | 58.4% | 59.3% | +0.12 | +9.2% |
| NVDA | 33.3% | 36.4% | -0.60 | +4.5% |
| ASML | 24.9% | 36.4% | **-1.83** | +13.5% |

**DRAM 쪽에 공매도가 몰린다** — MU 가 거래비중 z 와 잔고 증가율 모두에서 가장 두드러진다.
반면 ASML 은 거래비중이 가장 크게 빠졌다(z -1.83).

### 34.2 대상 선정 — DRAM ETF 는 실재한다 (2026-08-07 정정)

처음에 "DRAM 전용 ETF 는 미국에 없다" 고 적었는데 **틀렸다**. 확인 결과:

- **`DRAM` — Roundhill Memory ETF**, 2026-04-02 Cboe 상장. 세계 최초의 메모리 순수 테마 ETF 로
  DRAM·HBM·NAND·SSD 를 담는다. 상장 25거래일 만에 AUM 50억 달러를 넘겼다.
- **2배 레버리지가 둘** — `RAML`(Leverage Shares, 2026-07-23 상장), `RAM`(T-REX/Roundhill).

이건 곁가지가 아니라 **핵심**이다. 국내 삼성·하이닉스 단일종목 레버리지(§33.1)와 **같은 기초자산에
같은 방식으로 걸린 돈**이라, 국내만 보면 메모리에 걸린 레버리지·공매도를 절반만 보는 셈이 된다.

대상은 이렇게 나눴다.

| 묶음 | 티커 |
|---|---|
| 메모리 순수 테마 ETF | DRAM |
| 그 2배 레버리지 | RAML, RAM |
| 메모리 개별주 | MU(DRAM), SNDK(NAND), WDC·STX(스토리지) |
| 반도체 대형주 | NVDA, AMD, INTC, TSM, ASML, AVGO, QCOM, TXN, ARM |
| 반도체 ETF·레버리지 | SMH, SOXX, SOXL·SOXS(3배) |

### 34.3 메모리 쪽 결과 (2026-08-06)

- **메모리 계열 평균 z 0.27 vs 비메모리 -0.23** — 공매도가 메모리 쪽에 상대적으로 쏠려 있다
- **DRAM ETF: 공매도 잔고 +190.8%** (33.6백만주, vs 06-30 정산). 그런데 **일별 거래 비중은 38.7%로
  20일 평균 39.9%와 같다** — 매일 격하게 팔리는 게 아니라 **잔고가 쌓인 것**이다.
  이 두 계열을 안 나눴으면 못 봤을 구분이다.
- 개별주는 MU 가 z +1.63 으로 가장 높고, WDC +1.01, STX +0.68 로 스토리지도 같은 방향이다.

국내에도 메모리 테마 ETF 가 있다 — HANARO 미국AI메모리반도체TOP4+(시총 0.12조),
KoAct 글로벌AI메모리반도체액티브(0.11조). 다만 규모가 작아 수급 분석 대상으로는 아직 의미가 옅다.

## 35. 오늘의 종합 판정 — 페이지 최상단

리포트가 커지면서 "그래서 오늘은 어느 쪽이냐"를 답하는 데 다섯 파트를 다 읽어야 하는 상태가 됐다.
그래서 맨 위에 **매일 다시 계산되는 종합 판정**을 올렸다(`dailyVerdict()` in `analyze.mjs`).

### 35.1 왜 손으로 안 쓰는가

이 리포트는 매일 자동 갱신된다. 결론 문장을 손으로 써 두면 **하루 이틀 만에 본문과 어긋난다** —
그리고 어긋난 걸 아무도 모른다. 그래서 최상단 섹션에는 고정 문구가 하나도 없다.
판정도, 점수도, 한 줄 요약 문장도 전부 그날 데이터에서 조립한다.
`build.mjs` 는 `A.verdict` 를 렌더링만 한다.

### 35.2 방법

서로 다른 출처에서 오는 지표 **12개**를 각각 셋 중 하나로 판정한다.

| 판정 | 뜻 |
|---|---|
| 완화(`ok`) | 부담이 기준선 아래 |
| 중립(`watch`) | 기준선 부근 |
| 경계(`alert`) | 부담이 남아 있다 |

**기준선은 전부 "직전 사이클의 같은 지표"다.** "지금 신용 28조는 많은가" 같은 절대 수준에 대한
감(感)을 배제하기 위해서다. 시총도 거래대금도 그 사이 커졌으므로 절대액 비교는 대부분 틀린다.

세 축으로 묶는다.

| 축 | 묻는 것 | 지표 |
|---|---|---|
| 하방 | 지수가 더 빠지면 기계적으로 나올 물량이 있나 | 신용/시총(§8), 예탁금 대비 신용융자(§28), 마진콜 첫 문턱(§21), 반대매매/미수금(§31.2), 시장별 되돌림(§25) |
| 상방 | 되갚아야 할 공매도가 얼마나 남았나 | 대차 주수(§16.3), 대차/시총(§17), 해외 메모리 공매도(§34) |
| 군중 | 개인이 실제로 팔고 나갔나 | 단일종목 좌수(§23.7), AUM·익스포저(§30), ETF 시장 내 거래대금 비중(§33.2), 개인 순매수(§27) |

점수는 완화 +1 / 중립 0 / 경계 −1 의 단순 합이다.

### 35.3 가중치를 두지 않은 이유

**지표별 가중치는 전부 1이다.** 중요도 차이를 데이터로 정할 근거가 없기 때문이다.
"좌수가 예탁금 비율보다 2배 중요하다"고 쓸 수는 있지만 그건 계량이 아니라 취향이고,
한번 넣으면 판정이 그 취향에 끌려간다. 그래서 이 점수는 **방향의 우열이 아니라
"몇 개가 어느 쪽인지"의 집계**로만 읽어야 한다 — 총점보다 **어느 지표가 경계인지**가 정보다.

### 35.4 한 줄 요약도 조립한다

`headline` 은 축별 결과를 조건부로 이어 붙인다. 예를 들어 하방 축에 경계가 하나도 없으면
"아래쪽은 지수 문제만 남았다", 하나라도 있으면 그 지표 이름을 그대로 박는다.
템플릿은 고정이지만 **어느 가지를 타는지는 그날 데이터가 정한다**.

### 35.5 selfcheck 가 무엇을 막는가

최상단 결론이 본문과 다른 말을 하면 리포트 전체의 신뢰가 무너진다. 그래서 값 자체가 아니라
**본문 필드와의 일치**를 검사한다(`selfcheck.mjs`).

- 총점이 지표 상태의 합인가 (손으로 쓴 숫자가 섞이지 않았는가)
- 각 판정이 그 판정을 낸 본문 필드와 같은 방향인가 — 예: `etfUnits` 가 완화면
  `etf.unitsTrend.single.verdict` 가 반드시 `rolling` 이어야 한다
- 근거 문장에 `undefined`·`NaN` 이 섞이지 않았는가 (필드명이 바뀌면 여기서 죽는다)
- '오늘 움직인 것'의 모든 항목이 `daily.items` 에 실재하는가

### 35.6 한계

- **선행 지표가 아니다.** 12개 중 좌수(§27.4)처럼 3거래일 늦는 것이 섞여 있다. 각 지표의
  근거 문장에 지연 여부를 적어 뒀다.
- **지수 방향을 예측하지 않는다.** "물량이 어디에 얼마나 걸려 있나"만 답한다.
- **경계 개수가 곧 위험 크기는 아니다.** 경계 1개가 나머지 11개를 압도하는 상황이 있을 수 있다.
  그래서 총점만 크게 띄우지 않고 지표 12개를 근거와 함께 전부 펼쳐 둔다.

## 36. 국가별 포지셔닝 — 씨티 차트를 공개 데이터로 재현하기

외사 리서치의 **Weekly Futures Activity** 차트(신규 롱 / 신규 숏 / 롱 청산 / 숏 커버 + Net)를
나라별로 비교하는 그림이다. 재현했다. 다만 **도구를 바꿔야 했다**.

### 36.1 네 갈래의 정체는 잔고 변화의 부호다

마법이 아니다. 잔고가 늘면 신규 진입, 줄면 청산이고, 롱·숏은 계열을 나눠 보면 된다.

| 갈래 | 정의 | 방향 |
|---|---|---|
| 신규 롱 | 상장좌수 증가(설정) | 매수, 0 위 |
| 롱 청산 | 상장좌수 감소(환매) | 매도, 0 아래 |
| 신규 숏 | 공매도 잔고 증가 | 매도, 0 아래 |
| 숏 커버 | 공매도 잔고 감소 | 매수, 0 위 |

`Net = (좌수변화 − 공매도잔고변화) × 가격`. 이 항등식은 `selfcheck` 가 검사한다.

### 36.2 선물을 못 써서 ETF 로 바꿨다

원 차트는 지수 선물 미결제약정을 쓴다. **그 데이터는 익명으로 못 받는다.** 2026-08-10 에 전부 찔러 봤다.

| 소스 | 결과 |
|---|---|
| KRX 정보데이터시스템 | 403 |
| 네이버 선물 `siseJson` | 빈 배열(코드 네 개 시도) |
| SGX API | 파라미터 비공개(`SGX_4015`) |
| HKEX 일별 리포트 | 404 |
| JPX | HTML 페이지뿐 |
| CME 정산 API | 400 |
| stooq | JS 게이트 |

그래서 **미국 상장 국가 ETF** 에 같은 질문을 물었다. 둘 다 공개 데이터다.

- 롱 사이드 = **좌수 = 순자산 ÷ NAV** (iShares 제품 스크리너, 매일)
- 숏 사이드 = **FINRA 공매도 잔고** (월 2회 정산, 백필 가능)

**이건 같은 수가 아니다.** 선물은 헤지·차익 수요가 크고 ETF 는 자산배분 수요가 크다.
다만 외국인이 나라를 통째로 사고파는 주된 통로가 국가 ETF 라 **질문 자체는 같고**,
방향과 상대 순위는 비교할 만하다.

교차 검증이 됐다 — 2026-06-30~07-15 구간 한국 Net 은 **−21.9억달러**로,
씨티가 코스피200 **선물**에서 집계한 **−23억달러**와 부호·크기가 모두 가깝다.
다른 나라는 크기가 더 벌어진다(홍콩·호주). 도구가 다르니 당연한 일이고, 그래서
**절대액이 아니라 순위와 부호로 읽으라고** 본문에 적어 뒀다.

### 36.3 주간이 아니라 정산 구간이다

씨티는 주간으로 끊는다. FINRA 공매도 잔고는 **월 2회**(15일·말일, 8영업일 지연)라
주간으로 만들 수 없다. **없는 주기를 보간해 지어내지 않는다** — 정산 구간 그대로 쓴다.
구간 사이의 온도는 Reg SHO **일별 공매도 거래 비중**이 대신 보여준다(§34 와 같은 분리 원칙).

### 36.4 롱 사이드는 오늘부터 쌓인다

순자산·NAV 는 **과거를 주는 API 가 없다**. CSOP 좌수(§23.6)·투자자별 순매수(§27)와 같은 제약이다.
그래서 처음 돌리면 숏 사이드는 정산일 17개(8개월)가 있고 **롱 사이드는 수집 시작일부터**다.

없는 구간을 0 으로 채우지 않는다 — 0 은 "설정·환매가 없었다"는 **거짓 진술**이 된다.
`null` 로 두고 차트에서 막대를 아예 안 그린다. 워크플로가 매일 받으므로 다음 정산일부터 채워진다.

### 36.5 대상

씨티의 다섯 나라에 둘을 더했다 — 대만(반도체 비교군), 신흥국(벤치마크).

| 국가 | ETF | 씨티 대응 | 롱 사이드 |
|---|---|---|---|
| 일본 | EWJ | Nikkei 225 | O |
| 한국 | EWY | KOSPI 200 | O |
| 홍콩 | EWH | Hang Seng | O |
| 중국(대형주) | FXI | China A50 | O |
| 중국(A주) | ASHR | China A50 | **X**(Xtrackers — iShares 가 아니라 순자산 수집 경로가 없다) |
| 호주 | EWA | ASX 200 | O |
| 대만 | EWT | — | O |
| 신흥국 | EEM | — | O |

### 36.6 첫 결과 (2026-06-30 → 07-15)

한국 Net **−21.9억달러**로 8개국 중 최대 매도. 공매도 잔고 **+52.5%**(이 종목 과거 정산 구간 대비 **+2.4σ**)가
같은 구간 주가 **−15.0%** 와 겹친다 — **빠지는 와중에 숏이 새로 붙었다.** 차익실현이 아니라 방향성 베팅이다.

반대편은 홍콩(−22.8%)·일본(−3.6%)·대만(−3.7%)으로 되갚기 국면이다.

Net 순위에서는 뒤로 밀린다 — 증가율만 보면 크기를 놓친다.

## 37. 신용융자 — 시장별 겹쳐보기(체크박스 토글)

PART 1 의 첫 차트는 신용융자 **합계**에 코스피·코스닥 **지수**를 겹쳐 맥락만 보여준다.
코스피·코스닥 **신용융자 자체**를 서로 비교하는 차트는 없었다. 데이터는 이미 있었다
(`credit-split.json`, §8) — 차트가 없었을 뿐이다.

### 37.1 세 계열은 같은 소스, 다른 갱신 주기

`전체`(OS0026)는 오늘까지 나온다. `코스피`·`코스닥`은 FREESIS 에서 손으로 받아 올리는
분리 파일(§8) 기준이라 **1~2주 늦다**. 값 자체는 겹치는 날짜에서 완전히 같은 소스다 —
`전체` vs `코스피+코스닥` 합을 대조하면 오차가 xlsx 반올림만큼(±1백만원)만 나고,
`전체` 계열은 본문 시계열(`A.series.c`)과 정확히 같은 값이다. 둘 다 selfcheck 가 지킨다.

늦게 확정되는 코스피·코스닥을 억지로 오늘까지 늘리지 않는다 — 없는 날은 `null` 이라
차트에서 선이 그냥 끊긴다. 오른쪽 끝의 빈 구간은 데이터 누락이 아니라 그 지연이다.

### 37.2 켜고 끄는 체크박스 — 이 프로젝트 최초의 계열 토글

지금까지 다계열 차트는 전부 항상 다 겹쳐서 보여주기만 했다(범례는 색 설명일 뿐 동작이 없다).
이 차트가 처음으로 **계열을 골라 볼 수 있는** 차트다. 기본은 셋 다 켜짐 — 겹쳐 보는 게
목적이라 하나만 남기고 시작하지 않는다.

구현은 `chart-client.js` 에 `hidden = { 차트id: { 계열idx: true } }` 상태를 두고,
`draw()` 가 그리기 **직전**에 꺼진 계열을 걷어낸다. 그러면 눈금 범위·선·툴팁·구간요약이
전부 자동으로 켜진 계열만 본다 — 필터링 지점이 하나라 어디를 따로 손볼 필요가 없다.
마지막 하나는 끌 수 없다(다 꺼지면 빈 차트가 된다).

체크박스는 JS 로만 의미가 있어 기본은 `hidden` 속성(정적 SVG 는 항상 전부 겹쳐 보이므로
토글이 필요 없다)이고, `boot()` 가 지운다 — `.ic-bar`(구간 선택)와 같은 패턴이다.

이 메커니즘은 `seriesToggle()` 로 일반화해 뒀다. 다른 다계열 차트에도 같은 방식으로
붙일 수 있다(지금은 이 차트에만 붙였다 — 필요해지면 확장).

## 38. 모든 차트 대화형 + 고점/저점, 막대차트까지

지금까지 대화형(호버) 은 시계열 선 차트에만 있었고, 그중 일부는 정적 SVG 가 그리던 계열을
대화형으로 넘어가며 그대로 잃었다(§35 신용융자 이중축, §37 이전). 막대 차트(지수대별 신용융자,
월별 거래대금, 국가별 포지션)는 처음부터 대화형이 아니었다. 이번에 셋을 한 번에 고친다.

### 38.1 고점/저점 + 날짜 — 시계열 엔진 한 곳만 고쳐서 전체에 적용

`chart-client.js` 의 `draw()` 에 딱 한 번 넣었다. 지금 보이는 계열(구간 선택 + 계열 토글 반영)
기준으로 최댓값·최솟값과 그 날짜를 찾아 점 + 라벨로 찍는다 — 스택 차트는 개별 계열이 아니라
**합계**의 고점/저점을 찍는다(개별 레이어의 최고점은 의미가 없다). 라벨은 실제 DOM 에 넣은 뒤
`getBBox()` 로 폭을 재서 겹치면 위로 밀어낸다 — 빌드타임 추정(`lib/labels.mjs`, 글자당 상수)과
같은 문제를 풀지만 실측이라 더 정확하다.

이 한 곳을 고쳐서 기존 대화형 차트 전부(예탁금/신용융자/담보융자, 신용/시총 비율, 외국인
지분율 밴드, ETF AUM 분해, 대차잔고, 개인 순매수, 국가별 Net 추이 등 20개 이상)가 동시에
고점/저점을 얻었다 — 차트마다 손대지 않았다.

### 38.2 대차잔고·신용융자 이중축 — 빠졌던 코스피 선을 되살렸다

`lendingChart`/`timeSeriesChart` 는 대화형으로 바뀌면서 정적 SVG 가 그리던 코스피·코스닥
지수 선을 **떨어뜨렸다**(대화형 스펙에 신용융자/대차잔고 한 계열만 넣었었다) — 아무도 못
알아챈 조용한 회귀였다. 이제 코스피를 **보조축**(`axis2`)으로 되살렸다. 코스닥은 일부러
안 넣었다 — 정적 원본에서도 코스닥은 숫자 눈금이 없는 "자체 스케일"(모양만 보는 참고용)
이었다. 보조축은 하나뿐이라 코스피·코스닥 둘을 동시에 정확한 스케일로 태울 수 없고,
정밀 판독이 필요했던 건 애초에 코스피뿐이었다.

보조축 계열은 단위가 다르므로(조원 축 옆의 '코스피(p)') 툴팁·고점/저점·구간요약이 주축의
접미사·소수점을 그대로 물려받지 않게 별도 처리한다 — 안 그러면 "코스피 9,115**조원**"
같은 틀린 라벨이 나온다(실제로 한 번 나왔다가 잡았다).

### 38.3 범주형 막대 — 새 렌더러(drawBars)

지수대·월·국가처럼 **날짜가 아닌** 축은 시계열 엔진에 못 태운다(구간 선택 바가 날짜 비교를
하기 때문). `chart-client.js` 에 `kind:'cat'` 전용 렌더러를 새로 만들었다 — 그룹 막대
(월별 거래대금), 막대+보조축 선(지수대별 신용융자 누적 + 마진콜 레벨), 부호별 쌓기+다이아몬드
(국가별 포지션, §36) 세 형태를 한 함수로 지원한다. `interactiveBars()` 가 build.mjs 쪽 등록을
맡는다 — `interactive()` 와 짝이지만 구간선택 대상에서 빠진다(§ boot() 의 "전체 날짜" 수집에서
`kind==='cat'` 을 건너뛴다 — 안 그러면 카테고리 문자열을 날짜로 취급해 구간 바가 깨진다).

최고/최저 카테고리 라벨은 기본으로 켜져 있지만, 막대마다 이미 항상 숫자가 보이는 차트
(지수대별 신용융자, 국가별 포지션)는 중복이라 `markExtent:false` 로 끈다.

### 38.4 이번에 잘라낸 것 — 국가차트 부제목 한 줄

국가별 포지션 차트의 x축은 원래 두 줄(국가명 + 씨티 대응 지수명)이었다. `drawBars` 는 카테고리
라벨을 한 줄만 지원해서, 둘째 줄을 x축에서 빼고 **호버 헤더**로 옮겼다(`subLabels`) — 정보는
안 없어졌고, 바로 아래 표에도 그대로 있다. 지수대별 신용융자의 "평균매수/평균청산" 세로선
마커(§구 flowChart)도 대화형에서는 뺐다 — 같은 숫자가 바로 아래 본문(figcaption)에 이미
있어서, 차트에 못 넣어도 정보 손실은 없다.

## 39. 사이클 음영 복원 + 고점/저점 라벨 충돌 — §38 의 실사용 버그 두 개

§38 을 배포하고 실제로 써 보니 두 가지가 더 있었다.

### 39.1 음영(사이클 적립 구간)도 빠져 있었다

정적 SVG 는 늘 사이클 적립 구간에 음영을 깔았는데, `timeSeriesChart` 를 대화형으로 감쌀 때
그 밴드 정보 자체를 스펙에 안 넘겼다 — §38.2 에서 고친 "코스피 선 소실"과 같은 종류의
누락인데 이번엔 선이 아니라 배경이었다. `draw()` 에 `spec.bands`(구간 시작·끝 날짜 + 라벨)
를 받는 경로를 새로 추가했다. 라벨은 x축 날짜 라벨(y=ih+15) 한 줄 아래(y=ih+32)에 그리는데,
이 여백을 확보하려고 밴드가 있는 차트만 아래 여백을 30→46 으로 늘린다 — 안 그러면 라벨이
뷰박스 밖으로 잘린다.

### 39.2 고점 라벨끼리 겹치는 경우 — 위로만 밀면 못 피한다

외국인 지분율 차트에서 "+1σ 고" 와 "평균 고" 라벨이 같은 자리에 겹쳐 찍힌 게 실제로 보고됐다.
원인은 두 겹이었다.

1. **평균·±1σ 는 완전히 평평한 참조선이다.** 모든 날짜가 같은 값이라 "고점"이 사실상
   임의의 첫 점이고, 세 참조선이 전부 같은 자리(맨 왼쪽)에 라벨을 찍어 겹쳤다. 값이
   완전히 평평한 계열(`hi === lo`)은 고점/저점을 아예 안 찍도록 막았다 — 흔들리는 진짜
   계열(지분율)만 표시한다.
2. **충돌 회피가 위로만 밀었다.** 두 계열이 같은 날 같이 고점을 찍는 경우(신용융자·코스피
   둘 다 2026년 6월 하순에 고점) 는 드물지 않다. 그런데 라벨이 이미 차트 맨 위 여백에
   있으면 "위로 더 밀 자리"가 없어 충돌이 감지돼도 못 피하고 그대로 겹친 채 멈췄다
   (`y - 11 > minY` 가 처음부터 거짓이라 while 문 바디가 한 번도 안 돈다). 위가 막히면
   아래로, 아래도 막히면 다시 위로 — 방향을 뒤집어 보게 고쳤다.

### 39.3 처음 그릴 때 숨은 탭이면 getBBox 가 0 을 준다

기본 탭(PART 1) 이 아닌 파트는 `boot()` 가 처음 그릴 때 `display:none` 상태다. 그 상태에서
`getBBox()` 를 부르면 크롬은 폭 0 을 준다(실측 확인) — 그러면 충돌 회피가 모든 라벨을
"폭 0"으로 오인해 겹쳐도 못 잡아낸다. `getBBox` 가 0 을 주면 `lib/labels.mjs` 와 같은
글자당 상수 추정으로 대체한다. 나중에 그 탭을 클릭해도 차트를 다시 안 그리므로(탭 전환에
JS 리스너가 없다, 순수 CSS), 이 추정치가 최종 값이다 — 빌드타임 정적 라벨과 같은 수준의
정확도이지, 실측만큼 정밀하진 않다. 기본 탭(요약·PART 1)은 항상 실측을 쓴다.

## 40. 두 차트를 하나로 — 신용융자 시장별 + 지수

PART 1 첫 차트("신용융자 잔고와 지수 추이")는 신용융자 **합계**에 코스피·코스닥 **지수**를
겹쳐 맥락만 보여줬다. 범례에는 "코스닥(우, 자체 스케일)"이라고 써 놓고 실제로는 선을 안
그렸다(§38.2 — 보조축 하나로는 코스피·코스닥 두 지수를 동시에 정확히 못 태워서 코스닥을
아예 뺐다). 그 바로 아래엔 §37 에서 만든 "신용융자 — 시장별 겹쳐보기"(전체·코스피·코스닥
신용융자, 토글 가능)가 별도로 있었다.

두 차트가 사실상 같은 걸 두 번 보여주고 있었다 — 둘 다 "전체 신용융자"를 그렸고, 하나는
지수를 곁들였을 뿐이다. 그래서 합쳤다.

**지금의 PART 1 첫 차트** = 전체·코스피·코스닥 신용융자(조원, 토글 가능, 기본 전체 켜짐)
+ 코스피 지수(보조축, 점선, 늘 켜짐) + 사이클 적립 구간 음영. 코스닥 지수는 뺐다 —
자체 스케일이라 원래도 숫자로 못 읽었는데, 이제 **코스닥 신용융자**(실제 숫자로 읽히는
계열)가 그 자리를 대신하니 정보가 준 게 아니라 늘었다. §37 의 별도 차트는 지웠다.

데이터는 `A.creditByMarket.series`(§37) 를 그대로 쓴다 — 이제 이 배열에 `idx`(코스피
지수) 필드도 들어 있다(전체·코스피·코스닥 신용융자와 나란히, 같은 raw.series 순회에서
만들어지니 따로 조인할 필요가 없다).

**정적 SVG(인쇄·메일·JS 꺼짐)도 똑같이 4계열을 그린다** — 예전엔 대화형과 정적이 서로
다른 걸 보여주는 순간들이 있었다(§38.2, §39.1 이 그런 사례). 이번엔 처음부터 같은 데이터,
같은 4계열로 맞췄다. 다만 계열 색은 CSS 클래스(`.ln-kq` 등)를 재사용하지 않고 직접
`stroke` 로 지정한다 — `.ln-kq` 는 원래 "자체 스케일 참고용" 의미로 점선이 박혀 있어서,
이제 **실제 숫자로 읽는** 코스닥 신용융자에 그대로 쓰면 의도치 않게 점선이 됐다.

## 41. §39 의 "고쳤다"가 안 고쳐졌던 이유 — 상수 두 개를 더 틀렸다

§39 를 배포한 뒤에도 실제 화면에서 겹침이 계속 보고됐다. 두 개를 더 놓치고 있었다.

### 41.1 줄 간격 11 은 이 프로젝트가 이미 틀렸던 값이다

`lib/labels.mjs`(빌드타임 라벨 배치)의 주석은 이렇게 적혀 있다: *"lh 기본값 13은 눈대중이
아니다 — 9px 한글 라벨의 실제 상자 높이가 12.27이다. 10으로 뒀더니 11.5 간격이 남아
0.77px씩 겹쳤다."* §38 에서 대화형용 충돌 회피를 새로 만들면서 **같은 실수를 다시** 했다 —
줄 간격 상수로 11 을 썼다. 실측하면 같은 9px 라벨의 상자 높이가 11.72 다. 11 < 11.72 라서
"충돌 아님" 판정이 나는 두 라벨이 실제로는 0.7px 겹쳐 있었다. 13 으로 바꿨다 — 이미 이
저장소가 알고 있던 값을 재사용했을 뿐이다.

### 41.2 "저" 라벨의 시작점이 이동 가능 범위 밖에 있었다

`zeroBase` 차트(레버리지 ETF 그룹별 AUM 등)에서 값이 0 에 가까운 여러 계열이 비슷한 날
바닥을 찍으면, "저" 라벨의 **처음 놓이는 자리**(점보다 13px 아래)가 이미 내가 정한 이동
가능 범위(`maxY = 플롯 바닥 - 4`)를 벗어나 있었다. 위로 밀어도, 아래로 밀어도 둘 다
"범위 밖"이라 판정돼 **한 걸음도 못 움직이고 그 자리에 그대로 남았다** — 여러 라벨이
전부 시작점에 눌러앉아 겹쳤다. `maxY` 를 플롯 바닥보다 살짝 아래(x축 날짜/카테고리 라벨
바로 위까지)로 넓혔다 — "저" 라벨은 원래도 자기 점보다 아래에 놓이도록 설계돼 있어서,
플롯 테두리를 살짝 넘어가는 게 정상이다.

### 41.3 검증 방법을 바꿨다

이전 검증(§39)에서 "고쳤다"고 보고했던 건 **거짓 양성**이었다 — 중심점 거리 기반의 느슨한
판정(`|y1-y2|<10`)을 썼는데, 이번 겹침은 그보다 미묘해서 걸러지지 않았다. 이번엔 **각 라벨의
실제 사각형(bbox)이 기하학적으로 겹치는지**를 직접 계산해서 확인했다 — 한 페이지의 모든
탭, 모든 차트, 라벨 98개 전부를 이 방식으로 다시 훑어 겹침 0건을 확인했다.

또, 브라우저의 `location.reload()` 가 **file:// 문서에서 인라인 스크립트 변경분을 항상
새로 반영하지는 않는다**는 것도 이번에 알게 됐다(탭이 이전 버전의 스크립트를 계속 들고
있었다 — 체크박스 상태까지 그대로 복원됐다). 앞으로 로컬 파일을 다시 확인할 때는
`location.reload()` 대신 **다른 origin 을 한 번 거쳐서 돌아오는 방식**으로 강제 재로딩한다.

## 42. 안 겹쳐도 지저분할 수 있다 — 계열당 하나씩 찍던 걸 그만뒀다

§41 로 겹침은 없앴는데 "그래도 지저분하다"는 피드백이 왔다 — 맞는 말이었다. 계열이 4~5개인
차트(레버리지 ETF 그룹 AUM 등)는 계열마다 고점·저점을 다 찍으면 라벨이 8~10개가 된다.
안 겹치게 밀어내는 데는 성공했지만, 애초에 **한 차트에 라벨 10개가 떠 있는 것 자체가
"눈에 확 들어오는" 그림이 아니다.** 겹침 회피는 필요조건이었지 충분조건이 아니었다.

바꾼 것: 계열이 **셋 이상**이면 첫 번째 계열(그 차트의 대표 지표 — 대체로 "전체"처럼
합계나 헤드라인 값)만 고점/저점을 찍는다. 나머지 계열의 정확한 값은 여전히 마우스오버로
바로 나온다 — 차트에 늘 박아 둘 필요가 없다. 계열이 둘 이하(지표 하나 + 지수 보조축처럼)면
그대로 다 찍는다 — 라벨 4개까지는 이미 안 겹치고 안 지저분하다.

효과: 5계열 AUM 차트 10개 → 2개, 4계열 신용융자 차트 8개 → 2개. 라벨 폰트도 9px·굵게에서
8.5px·중간 굵기로 살짝 낮췄다 — 존재감을 줄여서 라벨이 "이 차트의 결론"이 아니라 선을 보조하는
정보로 보이게 했다.

## 43. 라벨끼리는 안 겹쳐도 선과는 겹친다 — 배경판을 깔았다

§42 로 라벨 개수를 줄인 뒤에도 "전체 저" 라벨이 코로나 폭락 저점 부근에서 선 그림 위에
얹혀 읽기 힘들다는 지적이 왔다. 원인은 명확했다 — 그 지점은 **여러 계열이 같은 시점에
같이 바닥을 찍는 곳**(2020년 3월, 시장 전체가 무너진 날)이라, 라벨을 아무리 위아래로
밀어도 옆 계열의 선이 항상 근처에 있다. 라벨-라벨 충돌 회피(§39, §41)는 이 문제를 애초에
풀 수 있는 도구가 아니었다 — 그건 다른 *라벨*을 피하는 로직이지 다른 *선*을 피하는 로직이
아니다.

그래서 접근을 바꿨다. 선을 피해 다니는 대신, 라벨 뒤에 배경색 판(`.mk-bg`)을 깔아
**무엇이 뒤에 있어도 항상 읽히게** 한다 — 차트 라이브러리들이 흔히 쓰는 방법이다.
텍스트보다 먼저 그려야 뒤에 깔리므로, 최종 위치가 정해진 뒤 `insertBefore` 로 텍스트
바로 앞에 끼워 넣는다. 페이지 배경색(`var(--bg)`)에 살짝 투명도를 줘서 완전히 딱딱해
보이지 않게 했다.

곁들여 라벨과 점 사이 거리도 늘렸다(고점 -8→-11, 저점 +13→+19) — 배경판이 있어도
점에 너무 붙어 있으면 여전히 복잡해 보인다.

## 44. 방향 수급 — 옵션을 붙이려다 현·선물 동조로 정착한 기록

**질문**: 지금까지의 지표는 전부 잔고(신용·대차·좌수)다. 잔고는 부담의 **크기**를 재지만
**방향**은 못 잰다. 향후 방향에 누가 어느 쪽으로 베팅하고 있는지를 매일 잡을 수 없나?

**첫 시도 — 옵션(풋/콜 비율·VKOSPI)**: 실패. 소스가 전부 막혀 있다.
- KRX 정보데이터시스템(data.krx.co.kr) — 익명 POST 가 전부 `LOGOUT`. 세션 쿠키를 받아도 같다.
- KRX Open API — 무료지만 키 발급에 로그인이 필요하다. 자동 파이프라인에 남의 계정을 넣지
  않는다는 원칙(§27 의 KRX 항목과 같은 이유)으로 제외. **키를 직접 발급받아 GitHub secret 으로
  넣으면 이 절을 옵션까지 확장할 수 있다** — 그때를 위해 경로만 적어 둔다.
- 네이버 옵션 투자자별(investorDealTrendDay sosok=04/05) — 표 구조만 남고 행이 비어 있다.

**정착 — 외국인 현·선물 동조**: 같은 질문("방향에 누가 베팅하나")에 답하는 살아 있는 소스가
네이버 투자자별 매매동향이다. 코스피 현물(01)·코스닥 현물(02)·K200 선물(03)의 일자별
투자자별 순매수를 페이지당 10영업일씩 준다. 페이징으로 1년 이상 백필이 된다 —
`fetch-direction-flows.mjs` 30페이지 한 번으로 2025-05 부터 쌓았고, 매일 3페이지면 공백이 메워진다.

**검증**: 매 행이 zero-sum 이다 — 개인+외국인+기관계+기타법인 = 0 (누군가 사면 누군가 판다).
파싱이 한 칸이라도 밀리면 이 합이 깨지므로 fetcher 가 행 단위로 검사해 어긋난 행은 버리고,
selfcheck 는 날짜 정렬·누적 검산·동조 판정의 일관성을 다시 확인한다.

**읽는 법**: 외국인이 현물과 선물을 **같은 쪽**으로 밀면 방향 베팅이다(동시 매수 = 위,
동시 매도 = 아래). **엇갈리면** 한쪽이 헤지·차익일 가능성이 커서 방향으로 읽으면 안 된다 —
엇갈림 상태에서는 "동조로 돌아서는 쪽이 다음 방향"이라는 관찰만 남긴다. 판정(§35)에는
'방향 — 외국인 베팅' 축으로 들어간다: 동시 매도 = 경계, 엇갈림 = 중립, 동시 매수 = 완화.

**한계**:
- 선물은 **계약수**라 금액이 아니다. 현물(억원)과 직접 합산·비교할 수 없어 부호(방향)만 쓴다.
- 옵션이 주는 정보(기대 변동성의 가격, 꼬리 위험의 값)는 이 구도에 없다.
- 누적 순매수 차트는 수집 시작일(2025-05-26)부터의 상대값이다. 그 이전 누적분은 모른다.

## 45. 신용융자 분리 계열, 다시 자동화를 시도했으나 — 검증에서 걸렸다

**계기**: §8 이후 몇 주가 지나며 `credit-split.json` 이 조용히 2주 넘게 낡아 있었다 —
전체(OS0026)는 매일 갱신되는데 유가증권/코스닥 분리는 xlsx 수동 재다운로드를 잊어서 멈춰 있었다.
`fetch-lending.mjs`(§16.2)가 같은 `getMetaDataList.do` 엔드포인트로 대차거래추이를 뚫은 전례가
있어, 같은 방법(빠진 파라미터 tmpV40/tmpV41/tmpV72 채우기)이 신용공여 잔고 추이에도 통할지
다시 시도했다.

**시도 1 — OBJ_NM 재추측**: §8 표에 있던 `STATSCU0100000070BO` 를 tmpV40/41/72 를 채워 다시
쳐 봤더니 이번엔 `null` 이 아니라 실제 숫자가 왔다 — 처음엔 성공한 줄 알았다. 8/29 값이
크로스통계 OS0026 대비 정확히 10배 차이가 나서(총계=유가증권+코스닥 항등식도 성립) 잠깐
"이거다" 싶었다. 그런데 **2020년 데이터로 같은 배율을 대조하니 10배가 아니라 5배였다** —
연도마다 배율이 다르다는 건 단위 환산 문제가 아니라 **애초에 다른 지표**라는 뜻이다
(대차거래추이 때와 달리, 이번엔 우연히 자릿수가 비슷해 보이는 별개 계열을 잘못 짚은 것).
같은 방식으로 `STATSCU0100000060/080/090/100/110/120/130/150BO` 도 훑었지만 전부 구조가
다르거나(날짜 아닌 종목명이 오는 등) 크로스통계와 배율이 안 맞았다.

**시도 2 — 헤드리스 브라우저로 실제 요청 캡처**: `fetch-lending.mjs` 를 뚫었던 원래 방법
그대로 재현하려 했으나 `freesis.kofia.or.kr` 로의 브라우저 접속 자체가 WAF 에 막혔다
("Web firewall security policies" 차단 페이지). §8 표의 "eXBuilder6 앱이 렌더를 미뤄 실패"와는
다른, 더 앞단의 차단이다.

**결론 — 자동화 보류, 대신 지연을 놓치지 않는 안전장치를 넣었다**: 검증 안 된 숫자를
밀어넣는 것은 지금처럼 며칠 늦는 것보다 나쁘다 — 틀린 시장별 분해가 맞는 것처럼 보이는
게 최악이다. 그래서:
1. `daily.freshness` 에 '신용융자 분리(유가증권/코스닥)' 항목을 추가했다 — `status.json` 과

2. 분리가 **적용은 됐지만** 전체 대비 14일(정상 지연 상한 "1~2주"를 넘는 선) 이상 벌어지면
   `splitBox` 가 별도 경고를 띄운다 — 이전에는 분리가 아예 없을 때만 경고했다. 이번처럼

### 45.1 그래도 며칠은 안 끊기게 — 마지막 비율로 추정치를 채웠다

§45 를 쓴 뒤 "네이버 되잖아, pf-dash-a3k9m 의 macro.html 에는 나온다"는 지적을 받았다.
확인해 보니 그 프로젝트도 실제 코스피/코스닥 **분리** 데이터를 구한 게 아니었다 —
네이버 증시자금추이(§45 가 이미 확인한 그 소스)가 주는 건 **총액뿐**이고, 그 프로젝트는
총액에 **월별로 손으로 시드해 둔 고정 비율**(`KR_CREDIT_SERIES`, 2026-06 이후 갱신 안 됨)을
곱해 코스피/코스닥으로 "쪼개서" 보여주고 있었다. 실측이 아니라 추정이고, 그 사실이
화면에 드러나 있지도 않다. 참고할 만한 방법이었지만 그대로 베끼면 같은 문제(추정을
실측처럼 보여줌)를 이 프로젝트에도 들여오는 것이다.

그래서 같은 아이디어를 **투명하게** 적용했다. `creditByMarket.series` 를 만들 때, 분리
파일의 마지막 실측일(`splitThrough`) 이후 날짜는:

- 전체(OS0026, 매일 갱신)를 마지막 실측일의 **유가증권 비중**(예: 79.3%)으로 그대로 나눠
  코스피/코스닥을 채운다.
- 그 행에 `estimated:true` 를 단다.
- 리포트 캡션이 "여기부터는 추정"이라고 명시하고, 적용한 비율 수치까지 그대로 보여준다(§35 의
  "0으로 채우면 거짓말이 된다"·"롱 사이드 없으면 null" 과 같은 원칙 — 추정이라는 사실 자체를
  숨기지 않는다).

**의도적으로 남긴 단순화**: 실측/추정 구간을 선 스타일(실선/점선)로 나누지 않았다 — 이 차트
(§39~§43 에서 라벨 겹침을 여러 번 고친 그 차트)에 세그먼트별 스타일링을 넣으려면
`chart-client.js` 의 path 생성 로직을 계열당 구간별로 쪼개야 해서 리스크가 크다. 지금은
캡션 텍스트로만 구분한다 — 그래프만 보고 캡션을 안 읽으면 추정 구간인지 모른다는 한계가
남는다. 필요해지면(예: 추정 구간이 실측보다 훨씬 길어지면) 계열을 실측/추정 두 개로 쪼개
점선 처리를 붙일 것.

**비율이 얼마나 안정적인가**: §8.1 에서 이미 확인했듯 유가증권/코스닥 비중은 사이클 안에서
급격히 안 바뀐다 — 그래도 사이클이 바뀌거나 한쪽 시장에 쏠린 급락이 오면 비율 자체가
움직인다. 그 움직임은 분리 파일을 다시 받아 실측으로 교체하기 전까지는 이 추정치에
반영되지 않는다.

## 46. 합계 AUM 차트가 "너무 이상했던" 이유 — 정적과 대화형이 다른 그림이었다

**지적**: PART 3 첫 차트(레버리지 ETF 합계 AUM)가 계속 이상하다. 선 5개가 뒤엉키고,
"단일종목 레버리지 2X 저 0.0조원 25.01.02" 같은 무의미한 라벨이 떠 있고, 아래 요약에는
"+2138.0%" 같은 숫자가 달렸다.

**원인은 하나였다**: 정적 SVG(`stackChartStatic`)는 쌓은 면적으로 그리는데, 대화형 래퍼
(`stackChart`)가 `stack:true` 를 안 넘겼다. JS 가 살아 있으면 정적을 걷어내고 대화형이
그 자리를 차지하므로(§37 구조), 사용자가 실제로 보는 건 **선 5개짜리 전혀 다른 차트**였다.
색도 래퍼가 자체 palette 를 써서 아래 범례(정적용 색)와 어긋났다. 파생 증상들:
- 상장 전 값이 0/결측인 계열(단일종목·인버스)이 선으로 그려지며 바닥에 깔린 선 + 수직 점프.
- 비-stack 경로의 고점/저점 마킹(§42)이 첫 계열(단일종목)에 붙어 "저 0.0조원"을 찍음.
- 구간 요약이 계열별 시작→끝 %를 다는데, 상장 직후 0.1조에서 시작한 계열은 +2138% 가 됨 —
  수학적으로 맞지만 "상장 시점 잡음"이지 정보가 아니다.

**고친 것**:
1. `stackChart` 가 `stack:true` + keys 의 색·투명도를 그대로 넘긴다 — 이제 대화형도 정적과
   같은 쌓은 면적이고, 고점/저점은 stack 경로가 합계에만 찍는다(라벨 2개).
2. 정적의 '단일종목 상장' 세로 기준선을 폭 0 밴드로 넘겼다 — 대화형 밴드는 최소 1px 로
   그려져 같은 효과가 난다.
3. `sliceByRange` 가 `line`/`opacity` 를 승계하지 않던 버그 수정 — 구간을 좁히는 순간
   AUM 분해 차트(stack + 합계 겹선)의 합계선이 면적으로 바뀌던 잠복 버그였다.
4. stack 차트의 구간 요약은 **합계에만 %** 를 달고 계열별로는 시작→끝 값만 남겼다.

**같이 넣은 것(사용자 요청)**: 단일종목 상세 표에 홍콩 CSOP 3종 행(시점별 좌수는 일별
히스토리에서, 홍콩 거래일이 달라 직전 거래일 값), 그리고 삼성전자/SK하이닉스 **2X 좌수
합계 표**(5월말/지수 고점/6월말/최저/최근 × 국내/홍콩/합산). 좌수 합은 상품마다 1좌 크기가
달라 금액 합이 아니라 물량 추세의 근사다 — 표가 그 단서를 직접 단다. CSOP 의 가격·AUM
분해는 비워 뒀다: NAV 가 달러 기준이라 환율이 섞여 국내식 Δln 분해가 성립하지 않는다.

## 23.7 CSOP 과거 NAV — "403이라 못 받는다"가 틀렸었다

**계기**: 국내+홍콩 합산 AUM 차트(핵심 요약)의 홍콩 선이 2026-08(수집 시작)부터만 있어

**§23.6 의 기록이 틀린 지점**: "과거 시계열 엔드포인트(ChartData)는 403" — 경로를 잘못
짚은 것이었다. `/cmsApi/NAV/ChartData` 같은 추측 경로는 404/403이 맞지만, 상품 페이지가
실제로 쓰는 공통 차트 스크립트(`config/js/lai_functions.js` — 상품 전용 JS 가 아니라서
§23.6 때는 안 읽었다)를 브라우저로 열어 보니 진짜 엔드포인트는:

```
POST /cmsApi/performanceView/LI/Performance/ChartData
body {"ticker":"7709 HK","fundId":"HK-SKHY-2L","beginDate":"YYYYMMDD","endDate":"YYYYMMDD"}
```

이고 상장일부터의 **일별 좌당 NAV(USD)** 를 한 번에 준다. fundId 는 slug 대문자.
(참고: `/cmsApi/performance/product` 는 1M/3M/YTD 요약만 주는 다른 엔드포인트다.)

**복원 방식**: 총 NAV(AUM)가 아니라 좌당 NAV 만 오므로, SDW 백필 구간(2025-10~2026-07)은
`총 NAV ≈ 좌당 NAV × 등록기관(SDW) 발행좌수` 로 복원한다(`navSrc:"chart-api"` 표시).
등록기관 좌수는 CSOP 신고좌수와 5~20% 어긋날 수 있으므로(7/31 실측 829M vs 984M, §23.6)
이 구간의 AUM 은 근사치다 — 리포트 캡션에 그대로 적었다.

**환율**: 조원 환산에 필요한 USD/KRW 도 상장일까지 백필했다 — 네이버 시장지표 API 를
페이지 단위로 넘기며 20251016 이전이 커버될 때까지 받는다(이미 커버돼 있으면 1페이지만).

**합산 차트의 구멍**: 홍콩과 한국의 휴장일이 달라 날짜를 정확히 맞추면 국내만 열린 날마다
선이 끊긴다 — 홍콩의 직전 거래일 값을 이월하되 7일 한도를 뒀다(그 이상 벌어지면 진짜 결측).

**같이 고친 것**: "홍콩이 국내보다 크다" 박스가 조건 없이 박혀 있었다 — 8/19 폭락으로
실제로는 국내 6.94조 vs 홍콩 6.60조로 역전된 날에도 그대로였다. 비교 결과에 따라
문구가 바뀌게 했고, 홍콩 NAV 기준일이 국내보다 하루 늦다는 단서를 달았다. 단일종목 상세
표에는 종목별 합계 행(국내 2X + 홍콩 2X, 원화 AUM 합)을 추가했다.
