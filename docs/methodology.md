# 지수대별 신용융자 누적과 반대매매 진행률 추정 — 방법론

## 1. 목적

두 가지를 수치로 답한다.

1. 코스피 지수대별로 신용융자가 얼마나 쌓였는가
2. 그중 반대매매(마진콜)가 얼마나 진행되었고, 얼마가 남아 있는가

비교 대상은 삼성자산운용 투자리서치센터의 House View 점검 자료
「7.29일 급락 코멘트: 신용매수 반대매매 추정」(2026-07-29)이다.
그 자료는 Quantiwise(유료 단말)를 썼으나, 여기서는 공개 소스만으로 같은 결과를 만든다.

## 2. 원 자료 방법론의 역설계

원 자료에는 계산식이 없다. 본문 서술과 차트 값을 제약조건으로 두고 규칙을 맞춰나갔다.

### 2.1 버킷 폭 = 500p

본문 "코스피 5,000-6,000p 사이 신용융자 매수 7.2조원"과
차트의 인접한 두 막대(4.00 + 3.23 = 7.23)가 일치한다. 따라서 막대 하나는 500p다.

### 2.2 마진콜 계수 = 0.84

신용융자는 매수한 주식 전체가 담보다. 자기자금 40 + 융자 60으로 100을 매수했다면,
평가액 `P`에 대해 담보평가비율은 `P / 60`이다. 담보유지비율 140%를 만족하는 하한은

```
P / 60 >= 1.40   ->   P >= 84
```

즉 매수 지수 대비 **-16%**에서 마진콜이 발생한다. 계수는 `담보유지비율 × 융자비율 = 1.40 × 0.60 = 0.84`.

원 자료의 서술 세 곳이 모두 이 계수로 설명된다.

| 원 자료 서술 | 계산 |
|---|---|
| 7.27 종가 6,756 → "7,500-8,000대 신용 매수분까지 청산 추정" | 8,000 × 0.84 = 6,720 |
| 7.28 종가 6,024 → "약 -1.1조원이 금일 청산" | 7,500 × 0.84 = 6,300 이 깨짐 → 7,000-7,500 버킷 |
| 7.29 종가 5,663 → "추가 -1조원 반대매매 위험" | 7,000 × 0.84 = 5,880 이 깨짐 → 6,500-7,000 버킷 |

차트의 우축 「상단기준 마진콜 레벨」은 각 버킷 **상단** 지수에 계수를 곱한 값이다.

### 2.3 배분 규칙 = 양(+)의 순증만 누적 (gross)

세 가지 후보를 실측으로 대조했다.

| 규칙 | 설명 | 결과 |
|---|---|---|
| LIFO | 잔고 감소일에 높은 지수 버킷부터 차감 | 고지수 버킷이 0이 되어 원 자료(7,500-8,000 = 1.28조)와 불일치 |
| signed | 감소일 델타를 그날 버킷에서 차감 | 고지수 버킷이 음수가 되어 불일치 |
| **gross** | **증가일 델타만 그날 버킷에 적립** | **일치** |

`gross`가 맞다. 따라서 막대는 "**그 지수대에서 일어난 신용매수 규모**"이고,
"현재 그 지수대에 남아 있는 잔고"가 아니다. 이 구분이 해석에서 중요하다(§5 참조).

### 2.4 기간 = 연초 이후

버킷 4,500p 이상은 코스피가 2026년에 처음 도달한 구간이라 기간을 어떻게 잡아도 값이 같다.
반면 4,000-4,500 버킷은 기간에 민감하다. 시작일을 훑어 원 자료 값(0.36조)에 맞춘 결과:

| 시작일 | 4,000-4,500 버킷 |
|---|---|
| 2025-01-01 | 3.19조 |
| 2025-12-01 | 1.27조 |
| **2026-01-01** | **0.34조** ← 원 자료 0.36조 |
| 2026-02-01 | 0.00조 |

따라서 기간은 **연초 이후**다. 2025-12-31 잔고를 기준선으로 삼아 그 다음 영업일부터 델타를 잡는다.

### 3.1 엔드포인트를 찾은 과정

FREESIS 통계 화면은 eXBuilder6 SPA다. 브라우저 창을 띄우지 않으면 레이아웃 측정값이 0이라
앱이 렌더되지 않고, 각 통계 서비스가 쓰는 제네릭 서브미션
(`/CommSubmit/egovXbuilder.do`)은 `MAPPER`/`QRY` 값을 알 수 없어 호출이 불가능했다.

대신 '크로스 통계' 앱은 지표별 전용 엔드포인트를 쓴다.

- `POST /crossStatsCustom/STATCRSIDXIDINFOBO.do` — 지표 카탈로그(코드 + sqlKey)
- `POST /crossStatsCustom/STATCRS0600000011BO.do` — 지표 시계열 조회

요청 DataMap 이름이 `data`이므로 평범한 JSON 바디로 그대로 호출된다.

```json
{"data":{"serviceId":"STATCRS0600000011","tmpV1":"D",
         "tmpV45":"20260101","tmpV46":"20260729",
         "tmpV108":"OS0026,OS0025","sqlKey":"STATCRS0600000010VM021,STATCRS0600000010VM020"}}
```

`tmpV1`은 자료주기로 일별은 `D`다(`RD`를 넣으면 빈 배열이 온다).
미공표 구간은 `"null"` 문자열로 내려오므로 숫자로 읽히는 값만 취한다.

검증: `20260728` 신용융자 = 33,194,040 백만원 — FREESIS 메인 화면 표기와 일치.
코스피 종가는 네이버 금융 일별 시세와 교차 확인했다(7/27 6,755.75 / 7/28 6,023.66 / 7/29 5,663.24).

## 4. 사이클 분할

코스피 레벨이 국면마다 완전히 달라서, 전 기간을 같은 절대 지수 버킷으로 묶으면 의미가 없다.
2021년 고점은 3,305p, 2026년 고점은 9,115p다. 그래서 적립과 청산을 사이클 단위로 끊는다.

| | 2020–21 사이클 | 2025–26 사이클 |
|---|---|---|
| 적립 구간 | 2019-12-31 ~ 2021-12-31 | 2024-12-31 ~ 최신 |
| 청산 판정 | ~2023-01-31 | ~최신 |
| 버킷 폭 | 100p | 500p |
| 지수 고점 → 저점 | 3,305 → 2,155 (-34.8%) | 9,115 → 5,663 (-37.9%) |
| 신용융자 고점 | 25.65조 (2021-09-13) | 38.63조 (2026-06-24) |
| 실측 청산 | -9.84조 (-38.4%) | -5.96조 (-15.4%) |
| 상태 | **완결** | 진행 중 |

버킷 폭은 고정하지 않고 사이클의 지수 범위에서 자동으로 고른다.
버킷이 20개를 넘지 않는 가장 촘촘한 값을 쓴다(`pickWidth`).
2020–21은 범위 1,847p → 100p(19칸), 2025–26은 6,821p → 500p(15칸)가 선택된다.
후자가 원 자료의 500p와 일치한다.

2020–21 사이클은 청산까지 끝났으므로 **모델의 검증 사례**가 된다(§6).

## 5. churn 보정

양의 순증만 누적하면(원 자료 방식) 같은 자금이 들어왔다 나갔다 할 때 두 번 세어진다.
창이 길수록 심하다. 2020–21 사이클은 gross 합계가 35.40조인데 신용융자 고점은 25.65조로,
약 10조가 중복 계상이다. 원 자료는 창이 7개월(연초 이후)이라 이 문제가 작았다.

버킷이 알려주는 것은 지수대별 **분포**이므로, 분포는 그대로 두고 합계만 실제 순증에 맞춰
균등 스케일한다.

```
순증        = 신용융자 고점 - 적립 기준선 잔고
보정계수    = 순증 / gross 합계
보정 버킷   = gross 버킷 x 보정계수
```

| | gross 합계 | 순증 | 보정계수 |
|---|---|---|---|
| 2020–21 | 35.40조 | 16.44조 | 0.46 |
| 2025–26 | 39.16조 | 22.82조 | 0.58 |

보정 전후를 리포트 표에 함께 싣는다. 원 자료 재현 검증(§2.5)은 조건을 맞추기 위해
보정 없는 gross 기준을 그대로 쓴다.

## 6. 계산 절차

```
for 각 사이클 (적립구간, 청산판정구간):
    폭 = pickWidth(적립구간 지수 범위)

    for 각 영업일 d (적립 기준선 다음 날 ~ 적립 종료일):
        delta = 신용융자[d] - 신용융자[d-1]
        if delta > 0:
            버킷[floor(지수[d] / 폭) * 폭] += delta

    보정계수 = (신용융자 고점 - 기준선 잔고) / 버킷 합계
    판정지수 = 청산판정구간의 최저 지수

    for 각 버킷 b:
        마진콜레벨(상단기준) = b.상단 * 0.84
        마진콜레벨(전량)     = b.하단 * 0.84
        진입 = 판정지수 < 마진콜레벨(상단기준)
```

판정지수는 **그날까지의 최저 지수**를 쓴다. 반대매매는 한 번 발생하면 되돌아오지 않으므로,
지수가 반등해도 이미 터진 물량은 복구되지 않는다. 그날 종가로 판정하면
지수 반등 구간에서 누적 노출이 줄어드는 잘못된 결과가 나온다.

### 6.1 완결된 사이클에서의 검증

2020–21 사이클은 청산이 끝났으므로 모델 추정과 실측을 직접 대조할 수 있다.

| | 값 |
|---|---|
| 보정 모델 마진콜 진입 추정 | 8.85조 |
| 실측 청산 (25.65조 → 15.81조) | 9.84조 |
| 오차 | 1.00조 (실측의 10%) |

보정 전 gross 기준은 19.05조로 실측의 두 배 가까이 나온다. 보정이 필요한 이유이자,
보정 후에는 마진콜 기반 추정이 실제 청산의 대부분을 설명한다는 근거다.

## 7. 해석상 주의점

### 7.1 버킷 값은 '잔존 잔고'가 아니다

`gross` 누적이므로 이미 청산된 물량도 버킷에 남아 있다.
버킷 합계는 그 사이클에 **신용매수가 일어난 규모**이고, 현재 잔고와는 다른 개념이다.
"마진콜 진입 4.72조"는 "그 지수대에서 매수된 4.72조가 마진콜 조건을 만족하는 상태"라는 뜻이다.

### 7.2 결제일 기준 시차

신용융자는 결제일 기준이라 급락 당일 청산이 즉시 반영되지 않는다.
실제로 급락일 7/28 잔고는 전일 32.74조 → 33.19조로 **증가**했다.
모델과 실측의 차이는 (a) 결제일 시차, (b) 투자자의 추가 담보 납입,
(c) 마진콜을 피하려는 자발적 축소에서 온다.

### 7.3 두 벤치마크가 다른 방향을 가리킨다

현 사이클에서 마진콜 모델은 노출을 4.72조로 보는데 실측 청산은 이미 5.96조다.
강제 청산으로 설명되는 몫보다 실제 감소가 크다는 뜻이고, 자발적 축소가 섞여 있다고 읽는 게 자연스럽다.

반면 2021 사이클의 청산률(-38.4%)을 현 사이클 신용 고점(38.63조)에 적용하면
총 -14.82조가 풀려야 하고, 현재까지 -5.96조이므로 **잔여 -8.86조**가 남는다.

두 벤치마크는 근거가 다르므로 한쪽만 취하지 않고 병기한다.

### 7.4 반대매매금액(OS0025)은 검증값이 아니다

금투협이 공표하는 반대매매금액은 **위탁매매 미수금**(미수거래)에 대한 반대매매다.
7/28 기준 139억원 수준으로, 신용융자 청산 추정치(조 단위)와 자릿수가 다르다.
**신용융자 반대매매는 공표되지 않는다.** 원 자료가 이를 *추정*한 이유도 같다.
따라서 이 지표는 추정치의 검증값이 아니라 독립적인 스트레스 축으로만 쓴다.

### 7.5 그 외

- 공표되는 것은 일별 **순증감**뿐이어서 같은 날의 총매수와 총청산을 분리할 수 없다.
- 담보유지비율은 증권사·계좌·종목별로 130~170%로 다르다. 리포트의 민감도 표를 함께 볼 것.
- 종목별 신용잔고는 지수와 독립적으로 움직일 수 있어, 지수대 배분은 시장 전체 근사다.

## 8. 유가증권/코스닥 분리 — 적용됨

금투협은 신용거래융자를 **전체 / 유가증권 / 코스닥**으로 나눠 공표한다
(`신용공여 잔고 추이` 서비스의 그리드 헤더 H002/H003/H004로 확인).
프로그램으로 뚫린 크로스통계 API에는 '전체'(OS0026)만 노출되어, 분리 계열을 프로그램으로
받으려 여러 방식을 시도했으나 전부 막혔다.

| 시도 | 결과 |
|---|---|
| `POST /meta/getMetaDataList.do` + `{"dmSearch":{"OBJ_NM":"STATSCU0100000070BO",...}}` | 날짜 골격은 정상, 값 컬럼 전부 `null` |
| 자료주기 코드 6종(`D`/`RD`/`RM`/`00`/`01`/`1`) | 모두 동일하게 `null` |
| 세션 쿠키(JSESSIONID) 확립 후 재시도 | 동일 |
| `unit` 파라미터 최상위/중첩 5종 | 응답이 항상 `"unit":""` 로 회신, 동일 |
| `/{모듈}/{BO}.do` 패턴 12종 | 오류 페이지 |
| 통계 화면을 브라우저로 렌더 | eXBuilder6 앱이 `document.hidden` 상태에서 렌더를 미뤄 실패 |

결국 통계 화면에서 직접 내려받는 경로로 확보했다.
FREESIS > 주식 > 신용공여현황 > 신용공여 잔고 추이 에서 자료주기 `일`, 2010-01-01~최신으로
내려받은 xlsx(`data/신용공여 잔고 추이.xlsx`, 1,623행)를 `scripts/ingest-split.mjs` 로 파싱했다.

파서는 의존성 없이 세 형식을 자동 판별한다 — 진짜 xlsx(zip), HTML 표에 `.xls` 확장자가 붙은 형식,
CSV/TSV. 컬럼 위치는 `전체 = 유가증권 + 코스닥` 이 성립하는 조합을 60행 투표로 찾으므로
헤더 줄 수나 컬럼 위치가 밀려도 잡힌다.

**zip 압축 해제에서 한 번 막혔다.** 이 환경의 `tar`(Git Bash 기본, PATH 우선순위 상단)는 GNU tar라
gzip/xz 압축만 읽고 ZIP 컨테이너 포맷(xlsx는 zip이다) 자체를 못 연다. 게다가 `C:\Users\...` 형태의
경로를 `host:path` 원격 문법으로 오인해 `--force-local` 없이는 그 단계에서도 막힌다.
Windows 내장 `tar.exe`(`%SystemRoot%\System32\tar.exe`, bsdtar 기반)는 zip을 그대로 읽으므로
절대경로로 그걸 명시 호출해 해결했다.

**교차검증**: 파싱한 '전체' 컬럼과 기존에 크로스통계로 받아둔 OS0026 을 1,618영업일 전부 대조 —
**불일치 0일, 최대 오차 0백만원**. 완전히 일치한다.

코스닥은 지수가 세 자리라 버킷 폭이 자동으로 50p 근처로 잡힌다.

## 9. 실행

```bash
node scripts/fetch-index.mjs    # 네이버 코스피·코스닥 일별(장중 최신)  -> data/{kospi,kosdaq}-daily.json
node scripts/fetch-kofia.mjs    # 금투협 FREESIS 일별 11개 지표      -> data/kofia-daily.json
node scripts/ingest-split.mjs   # (선택) 신용공여 분리 계열 xlsx     -> data/credit-split.json
node scripts/fetch-lending.mjs  # 대차거래추이(공매도 프록시)         -> data/lending-balance.json
node scripts/analyze.mjs        # 사이클 x 시장 배분 + 마진콜 판정    -> data/analysis.json
node scripts/selfcheck.mjs      # analysis.json 불변식 검사 (선택)
node scripts/build.mjs          # 웹 리포트                          -> index.html
node scripts/build-email.mjs    # 메일 클라이언트용 리포트           -> email.html
```

`ingest-split.mjs` 만 xlsx 가 있을 때 돌리면 된다(§8). 원본이 그대로면 다시 돌릴 필요가 없고,
`analyze.mjs` 가 결과 json 이 없으면 해당 분석을 조용히 건너뛴다.
대차거래추이는 예전에 xlsx 였으나 지금은 `fetch-lending.mjs` 가 API 로 받는다(§16.2.1).

`index.html`은 데이터와 차트(SVG)를 모두 품고 있어 외부 의존성이 없다. `file://`로 열어도 그대로 보인다.
`email.html`은 같은 데이터를 메일 렌더러가 견디는 방식(전부 inline style, table 레이아웃, SVG 없음)으로 다시 굽는다.

리포트는 방향이 반대인 두 축으로 나눠 놓았다.

| 탭 | 질문 | 내용 |
|---|---|---|
| PART 1 신용잔고 | 얼마나 더 **하락**할 수 있나 | 반대매매 잔여(§10~15, §17, §18) |
| PART 2 공매도·숏커버링 | 얼마나 더 **상승**할 수 있나 | 대차 되갚기 잔여(§16, §20) |
| ALL 전체 | 둘 다 | 두 파트를 이어서 표시 |

PART 1 안에서 **사이클별 상세는 다시 탭으로 나뉜다.** 두 사이클은 지수 레벨이 3,305p 와 9,115p 로
완전히 달라(§4), 세로로 이어 붙이면 어느 쪽 숫자를 보고 있는지 헷갈린다.
진행 중인 사이클이 기본 선택이고, 탭 라벨에 각 사이클의 지수·신용 고점→저점을 같이 적어
전환하지 않고도 규모 차이를 알 수 있게 했다.

`index.html` 의 탭은 라디오 버튼 + 형제 선택자만 쓴다 — 스크립트가 없어 `file://` 에서도 그대로 동작하고,
인쇄할 때는 모든 탭이 펼쳐진다. 메일에는 탭이 없으므로 `email.html` 은 PART 1 / PART 2 머리말로 나눈다.
배분·판정 로직은 `scripts/lib/buckets.mjs` 에 모여 있어 사이클과 시장에 상관없이 같은 코드를 쓴다.

### 9.0 자동 갱신

`.github/workflows/update.yml` 이 평일 19:30 KST(장 마감 후)와 다음날 08:30 KST 에
위 파이프라인을 그대로 돌린다. `workflow_dispatch` 로 수동 실행도 되고,
`scripts/**` 나 워크플로 파일이 바뀐 push 에서도 돈다 — 파이프라인을 고치면 바로 결과가 나온다.
문서만 고친 커밋으로는 돌지 않는다.

받아오는 계열은 `fetch-kofia.mjs` 의 11개 지표(지수·시총·거래대금·신용융자·반대매매금액·
위탁매매미수금·투자자예탁금·예탁증권담보융자) + 네이버 코스피 + 대차거래추이로, 전부 자동이다.

두 가지가 이 워크플로의 핵심이다.

- **selfcheck 가 게이트다.** `analyze.mjs` 다음에 `selfcheck.mjs` 가 실패하면 커밋도 push 도 하지 않는다.
  계산이 조용히 깨진 채 배포되는 경로를 막는다.
- **바뀐 게 있을 때만 커밋한다.** `git status --porcelain` 이 비면 그냥 끝낸다.
  이걸 성립시키려고 `fetch-kofia.mjs` 의 `fetchedRange` 를 '요청 종료일'이 아니라
  '실제 데이터 범위'로 바꿨다 — 요청 종료일을 적으면 새 데이터가 없는 날에도 파일이 매일 달라져
  빈 커밋이 쌓인다.

남은 수동 구간은 **유가증권/코스닥 분리 신용공여 xlsx**(§8) 하나뿐이다. 사이클 단위로만 쓰이는
계열이라 자주 갱신할 필요가 없고, 파일을 갱신해 커밋하면 다음 실행부터 자동으로 반영된다.
대차거래추이는 §16.2.1 에서 API 경로를 찾아 자동화에 들어왔다.

**상태 확인 경로.** 저장소가 private 이라 Actions 로그를 URL 로 열 수 없다.
그래서 `scripts/status.mjs` 가 배포되는 `status.json` 에 실행 날짜·계열별 반영일·selfcheck 결과를 남긴다.
`ranOn` 이 며칠째 그대로면 워크플로가 멈춘 것이다.
시각이 아니라 날짜만 적는 이유는 실행할 때마다 파일이 달라져 의미 없는 커밋이 쌓이는 것을 막기 위해서다.
데이터가 그대로이고 `status.json` 만 바뀐 날은 커밋 메시지를 `Refresh status (no new data ...)` 로 구분한다.

### 9.1 조회 종료일은 '오늘'이다

두 `fetch-*` 의 종료일 기본값은 처음엔 날짜 상수(`'20260729'`)로 박혀 있었다. 그 상태로 다음 날 그냥 다시 돌렸더니

## 11. 청산 국면의 지수대별 분포

적립과 대칭으로, 일별 **감소분**을 그날 지수대에 배분한다(`accumulateOutflow`).
"어느 지수대에서 실제로 청산이 일어났는가"를 본다. 적립과 같은 폭을 쓰므로 같은 축에 나란히 놓을 수 있다.

적립 쪽과 달리 churn 보정을 하지 않는다. 감소분 합계는 실측 잔고 변화와 직접 대응하기 때문이다.

### 2020–21 사이클의 청산 (2021-09-13 ~ 2023-01-11)

총유출 **22.00조**, 순감소 **9.84조**. 차이는 청산 국면에도 신규 매수가 계속 섞였기 때문이다.
청산 국면 자체가 churn을 크게 동반한다는 뜻이고, "신용잔고 감소분 = 반대매매 규모"로 읽으면 안 되는 이유다.

| 코스피 구간(p) | 청산액(조) | 비중 |
|---|---|---|
| 2,100–2,200 | 1.68 | 8% |
| 2,200–2,300 | 2.77 | 13% |
| 2,300–2,400 | 2.93 | 13% |
| 2,400–2,500 | 3.31 | 15% |
| 2,500–2,600 | 0.79 | 4% |
| 2,600–2,700 | 2.19 | 10% |
| 2,700–2,800 | 2.00 | 9% |
| 2,800–2,900 | 1.16 | 5% |
| 2,900–3,000 | 4.03 | 18% |
| 3,000–3,100 | 0.64 | 3% |
| 3,100–3,200 | 0.51 | 2% |

청산이 특정 지수대에 몰리지 않고 2,100~3,000p 전 구간에 퍼져 있다.
가장 큰 덩어리(2,900–3,000p, 4.03조)는 하락 초기 구간이고, 그 다음이 2,400–2,500p(3.31조)로 바닥 근처다.
즉 고점 직후의 1차 이탈과 바닥에서의 투항이 양쪽에 있다.

금액가중 평균은 매수 2,656p → 청산 2,585p로 -2.6%다.
다만 적립 창(2020~2021)이 코로나 저점부터 시작해 낮은 지수대 적립을 많이 포함하므로,
이 숫자를 평균 손실률로 읽으면 안 된다.

## 12. 잔여 청산 규모 추정

근거가 다른 벤치마크 네 개를 놓는다. 하나로 수렴하지 않으므로 점 추정 대신 범위로 본다.
이미 청산된 양은 5.96조(신용 고점 38.63조의 15.4%)다.

| 벤치마크 | 근거 | 총 청산 | 잔여 |
|---|---|---|---|
| 2021 청산률 대입 | -38.4% × 38.63조 | 14.82조 | **8.86조** |
| 지수 낙폭 대비 탄성 | 탄성 1.10 × 현 낙폭 -37.9% | 16.14조 | **10.18조** |
| 마진콜 모델(보정) | 지수 5,663p 기준 진입 4.72조 | 4.72조 | 이미 충족 (1.24조 초과) |
| 신용/시총 비율 정상화 | 2023 저점 0.720% × 현 시총 5,326조 | 0.28조 | 이미 충족 (5.68조 초과) |

**잔여 추정 범위 0 ~ 10.18조.**

### 12.1 범위가 넓은 이유 — 레버리지 강도

위쪽 두 벤치마크는 직전 사이클과 레버리지 강도가 같다고 가정한다. 신용/시총 비율은 그렇지 않다고 말한다.

| 시점 | 신용융자 | 시가총액 | 비율 |
|---|---|---|---|
| 2021-09-13 (신용 고점) | 25.65조 | 2,698조 | **0.951%** |
| 2022-09-30 (지수 저점) | 17.16조 | 2,007조 | 0.855% |
| 2023-01-11 (신용 저점) | 15.81조 | 2,196조 | **0.720%** |
| 2026-06-24 (신용 고점) | 38.63조 | 7,439조 | **0.519%** |
| 2026-07-28 (현재) | 33.19조 | 5,326조 | **0.623%** |

시가총액은 코스피+코스닥 합계(FREESIS OS0008 + OS0009, 억원 → 백만원 환산).

현 사이클은 신용 고점에서도 0.519%로 2021년 고점 0.951%의 절반 수준이었다.
지금 0.623%로 올라온 것은 신용이 늘어서가 아니라 **시가총액이 더 빨리 줄었기 때문**이다.
그리고 현재 0.623%는 이미 2023년 저점 0.720%보다 낮다.

따라서 "2022년처럼 -38% 풀려야 한다"는 전제는 이 사이클에 그대로 적용되지 않는다.
절대 금액(38.63조)은 사상 최대지만 시장 규모 대비로는 과열이 아니었다.

### 12.2 잔여 위험은 시간이 아니라 지수 경로에 달려 있다

마진콜 모델 기준으로 현재 지수(5,663p)에서는 추가 노출이 열리지 않는다.
지수가 더 내려가야 새 구간이 마진콜에 들어온다.

### 12.3 한계

- 네 벤치마크 모두 과거 한 사이클(2020–21)에 기댄 외삽이다. 표본이 하나다.
- 시가총액 비율은 상장사 구성 변화(신규 상장, 대형주 편입)에 영향을 받는다.
- 마진콜 모델은 강제 청산만 센다. 현 사이클에서 실측 청산(5.96조)이 모델 노출(4.72조)을
  이미 넘은 것은 자발적 축소가 섞였다는 신호이며, 이 몫은 모델로 예측되지 않는다.
- 어느 벤치마크도 투자 판단의 근거로 쓰기에 충분하지 않다. 규모의 자릿수를 잡는 용도다.

## 13. 마진콜 사다리

"지수대가 얼마로 가면 얼마가 풀리는가"를 직접 답하는 표다. 시나리오 테이블(§12.2)이
0.95/0.90/0.80... 같은 임의의 상대 하락률로 지수를 골랐다면, 사다리는 실제 버킷 경계(marginHigh)
그 자체를 문턱으로 쓴다. 더 정확하고, 이미 계산해둔 값이라 추가 가정이 없다.

### 13.1 계산

안 터진 버킷(`triggered=false`, 즉 판정지수 >= marginHigh)만 골라 `marginHigh` 내림차순으로 정렬한다.
정의상 안 터진 버킷은 `marginHigh <= 판정지수` 이므로, 지수가 더 떨어질 때 가장 먼저 터지는 것은
`marginHigh` 가 판정지수에 가장 가까운(=가장 큰) 버킷이다. 그 다음, 그 다음... 순서로 사다리를 이룬다.

```
remaining = buckets.filter(안터짐).sort(marginHigh 내림차순)
cum = 0
for b in remaining:
    cum += b.보정된_금액
    사다리.push({ 문턱: b.marginHigh, 증가: b.보정된_금액, 누적: cum })
```

## 14. 거래대금 대비 규모

조원 단위 금액은 그 자체로는 크기 감이 안 온다. "그 시장이 평소 하루에 사고파는 돈의
몇 배/몇 %인가"로 바꿔야 시장이 그 물량을 얼마나 부담스러워할지, 청산이 주가를 얼마나
더 밀어낼 잠재력이 있는지 가늠할 수 있다.

### 14.1 데이터와 기준선 두 개

FREESIS 크로스통계에서 KOSPI/KOSDAQ 거래대금(OS0011/OS0012, 억원, 일별)을 추가로 받았다.
억원 → 조원은 `/10000`. '전체' 시장은 코스피+코스닥 거래대금 합계로, 신용융자 '전체'가
유가증권+코스닥 합계인 것과 기준을 맞춘다.

기준선을 하나가 아니라 **두 개** 쓴다.

- **그 시대 정상 평균(baseline)**: 청산 국면이 시작되기 직전 20거래일 평균. 2021년의
  사건을 2026년 거래대금 규모로 재단하면 시장이 그사이 커진 몫까지 섞여 "그때 그 사건이
  그때 기준으로 얼마나 컸는가"를 왜곡한다. 실제로 코스피 전체 기준 그 시대 정상 평균은
  2021년 26.85조/일, 2026년 64.69조/일로 2.4배 차이가 난다. 사이클은 각자 자기 시대와
  비교해야 한다.
- **오늘 기준(current)**: 데이터 마지막 날 기준 최근 20거래일 평균. 앞으로 남은 사다리는
  '오늘' 시장이 그 물량을 받아낼 수 있는지를 봐야 하므로 이건 항상 최신값을 쓴다.

이미 벌어진 청산(§14.2)은 baseline과, 아직 안 벌어진 사다리(§14.3, 앞의 §13)는 current와 대조한다.

### 14.2 과거 청산이 거래대금에서 차지한 비중

| | 2020–21 사이클 | 2025–26 사이클(진행 중) |
|---|---|---|
| 청산 국면 총유출(gross) | 22.00조 | 6.83조 |
| 그 국면 총거래대금 | 6,091.84조 | 1,041.93조 |
| 총유출 / 총거래대금 | **0.36%** | **0.66%** |
| 그 시대 정상 하루 대비 배수 | 0.82배 | 0.11배 |
| 그 국면 거래대금, 정상 대비 | **65%** | **70%** |

두 가지가 눈에 띈다.

1. **강제 청산이 거래대금에서 차지하는 비중 자체는 작다.** 총유출이 그 기간 전체 거래대금의
   1%도 안 된다. 신용융자 청산은 총거래량 관점에서는 작은 흐름이고, 가격을 직접 짓누르는
   주된 힘이라기보다 하락의 방아쇠나 촉매에 가깝다고 보는 게 근거에 맞다.
2. **청산 국면의 거래대금은 정상보다 오히려 줄어 있었다(65~70%).** 패닉으로 거래량이
   폭증한 게 아니라 유동성이 마른 채로 하락이 진행됐다는 뜻이다. 유동성이 얕을 때는
   같은 매도 물량도 가격에 더 크게 부딪힌다 — 총유출 비중은 작아도 실제 가격 충격은
   표면 수치보다 컸을 수 있다.

### 14.3 남은 사다리가 오늘의 유동성에서 차지하는 비중

| 시장 | 남은 사다리(보정) | 오늘 하루 평균 거래대금 | 배수 |
|---|---|---|---|
| 전체 | 18.10조 | 41.54조 | 0.44배 |
| 유가증권 | 15.04조 | 35.66조 | 0.42배 |
| 코스닥 | 1.03조 | 5.88조 | 0.18배 |

남은 물량 전부가 터져도 하루 거래대금의 절반이 안 된다. 시장이 하루 만에 소화할 수 있는
규모라는 뜻이지, 가격 영향이 없다는 뜻은 아니다 — 실제 매도는 하루에 분산되지 않고
급락 며칠 사이에 몰리며, §14.2 가 보여주듯 그런 국면엔 유동성 자체가 이미 얇아져 있다.

### 14.4 한계

- 거래대금은 매수·매도 양측을 어떻게 집계하는지(편도/양도) 명확히 공표되지 않는다.
  이 비율은 근사치이며, 실제 매도 대금만 따로 뽑은 값보다 분모가 크게(비율이 작게)
  잡혔을 가능성이 있다.
- 청산 물량이 그 거래대금 중 얼마가 실제로 매도 주문이었는지는 관측할 수 없다.
  총유출(gross)은 신용융자 잔고 감소분이지 체결된 매도 주문 금액이 아니다 — 담보
  추가납입으로 신용을 상환한 경우도 잔고 감소로 잡히지만 시장에서 매도가 일어나지 않는다.
- '오늘 기준' 평균은 지금 이미 급락·고변동성 국면의 거래대금이라, 평상시보다 높게
  잡혀 있을 수 있다(§14.2 처럼 반대로 낮게 나올 수도 있다 — 방향은 국면마다 다르다).
  사다리의 배수는 그 시점 유동성 상태에 따라 오차가 크다.

## 15. 월별 지수·거래대금 비교

두 사이클의 신용 고점이 속한 해(2021 / 2026)를 골라, 그 해 1~12월(2026은 데이터가 있는 달까지)
평균 지수와 평균 거래대금을 나란히 그린다.

### 15.1 왜 지수를 1월=100으로 지수화하는가

코스피(2021년 2,964~3,259 / 2026년 4,780~8,484)와 코스닥(2021년 934~1,043 /
2026년 794~1,156)은 원 지수 그대로 겹치면 코스닥이 코스피 대비 4~7배 눌려서 거의
평평한 선으로 보인다. 두 시장의 **등락률**을 비교하려는 목적에는 절대 수치가 아니라
"그 해 1월 대비 몇 %인가"가 맞는 축이다. 이는 §14 에서 거래대금과 지수처럼 스케일이
다른 두 지표를 억지로 이중축(그래프 하나에 y축 두 개) 에 우겨넣지 않고 차트를
나누거나 공통 기준으로 지수화하는 것과 같은 원리다 — 이 프로젝트의 다른 차트(예:
신용융자 잔고 vs 코스피)는 이미 만들어 둔 이중축 구성을 그대로 쓰지만, 이번처럼
같은 성격의 두 시계열(지수 대 지수)을 비교할 때는 이중축보다 지수화가 왜곡이 적다.

거래대금은 두 시장 모두 조원 단위로 스케일이 비슷해(2021년 코스피 9.9~26.1조 /
코스닥 9.4~15.7조, 2026년 코스피 26.4~51.2조 / 코스닥 6.2~15.6조) 원 단위 그대로
한 축에 놓아도 왜곡이 없다.

### 15.2 결과 요약

| | 2021년 | 2026년(1~7월) |
|---|---|---|
| 지수 등락(월평균 기준) | ±8%p 이내에서 완만한 등락 | 1월 100 → 6월 177.5(코스피) → 7월 148.1로 급락 |
| 거래대금 추이 | 1월부터 12월까지 꾸준히 우하향(26.1조→9.9조, 코스피) | 6월 정점(51.2조) → 7월 급감(35.9조) |
| 지수-거래대금 관계 | 따로 움직임(거래대금이 지수보다 먼저·독립적으로 감소) | 동행(같은 달에 정점, 같은 달에 급락) |
| 코스닥 전환점 | 대체로 코스피와 유사한 시점 | 코스피보다 한 달 빠른 5월에 선행 정점 |

2026년 7월(하락월) 거래대금이 6월(정점월) 대비 코스피 -30%, 코스닥 -39% 급감한 것은
§14.2 "청산 국면 거래대금이 정상 대비 65~70%"라는 계산을 월 단위로 눈으로 보여준다 —
패닉으로 거래량이 폭증한 게 아니라, 마니아가 꺾이면서 유동성 자체가 함께 빠진 것이다.

코스닥이 5월에 먼저 정점을 찍고(코스피는 6월) 거래대금도 5월 15.56조에서 7월 6.16조로
반토막난 것은 §8.1(코스닥 청산률 -38.3%, 유가증권 -13.5%)과 시점이 정확히 들어맞는다 —
코스닥은 유가증권보다 한 달 먼저 무너지기 시작해 더 빨리, 더 깊게 청산됐다.

### 15.3 한계

- 월평균은 그 달 안의 일별 변동을 뭉갠다. 특히 6월처럼 정점과 급락이 겹친 달은
  월평균 하나로 "정점"과 "무너지는 중"이 섞여 대표값의 해석력이 떨어진다.
- 2026년은 7개월치뿐이라 2021년(12개월)과 계절성 비교는 할 수 없다.
- 지수화는 등락률 비교에는 적합하지만 절대 수준(코스피가 코스닥보다 몇 배 큰 시장인지)은
  가려 버린다. 절대 수치는 표에 원 지수·원 거래대금으로 같이 실었다.

## 16. 공매도(대차잔고) 추이와 숏커버링

### 16.1 왜 대차잔고를 프록시로 쓰는가

한국은 공매도가 거의 전량 '차입 후 매도' 구조라(무차입 공매도는 원칙적으로 금지),
공매도 잔고와 대차잔고(주식 대차거래 잔고)는 사실상 같은 풀을 가리킨다.
그런데 KRX는 **종목별 순보유잔고**(대량보유자 신고 의무 기준, 지분 0.5% 이상만 공표)만
공표하고, **시장 전체 합계 공매도 잔고는 공표하지 않는다**. 그래서 대차잔고를 표준 프록시로 쓴다.

한계도 명확하다: 대차거래는 공매도 외에 ETF 설정/환매, 차익거래, 배당락 대비, 의결권 확보 등
다른 목적으로도 일어난다. 대차잔고 변화 전부가 공매도 포지션 변화는 아니다.

### 16.2 데이터 확보

FREESIS `대차거래추이`(STATSCU0100000140)도 신용융자 분리(§8)와 같은 이유로
크로스통계 API에는 없고, `getMetaDataList.do` 직접 호출도 날짜 골격만 오고 값은
전부 `null`이었다(같은 증상, 같은 결론 — 그리드 값은 이 경로로 못 받는다).
통계 화면에서 일별·2010-01-01~최신으로 내려받은 xlsx(`대차거래추이.xlsx`, 4,102행)를
`scripts/ingest-lending.mjs`로 파싱했다.

파일 구조: 헤더 4줄 + 데이터, 컬럼은 `일자 | 체결(주수) | 상환(주수) | 잔고 주수 | 잔고 금액`,
단위는 `[단위 :백만원, 일주]`(금액=백만원, 주수는 그대로). `구분` 컬럼 없이 이미 시장
전체 1행/일이었다(내려받을 때 '전체' 기준으로 조회됨).

파싱 로직은 신용융자 분리 때 만든 xlsx 리더를 `scripts/lib/xlsx.mjs`로 뽑아내 재사용했다
(zip 해제·HTML표·CSV 세 형식 자동판별, `pickFile()`이 `data/`와 프로젝트 루트를 모두 뒤진다 —
사용자가 다운로드 파일을 프로젝트 루트에 두는 경우가 많아서다).

### 16.2.1 API 경로를 찾아냈다 — 파라미터 누락이 원인이었다

2026-07-31 에 다시 파고들어 자동화에 성공했다. 결론부터: **엔드포인트는 처음부터 맞았고,
파라미터가 모자랐다.**

먼저 막힌 길을 전부 확인했다.

| 시도 | 결과 |
|---|---|
| 크로스통계 지표 카탈로그 88개 전수 조회 | 대차거래 **없음** (신용대주 OS0028 은 있음) |
| `/stat/FreeSIS.do` 에 쿼리스트링 GET | WAF 차단. 네비게이션은 POST 전용 |
| 엑셀 다운로드 엔드포인트 | 존재하지 않음 — `download()` 은 **이미 렌더된 HTML 표**를 `excelexport.jsp` 로 재직렬화한다 |
| 앱 정의 파일 `/ui/app/*` | WAF 차단 |
| `document.visibilityState` 패치 후 SPA 부팅 | 실패. eXBuilder6 는 실제 페인트 프레임을 요구한다 |

그래서 헤드리스 브라우저(Playwright)로 `/stat/main.do` 에 직접 들어가
`goPage('MSIS10040000000000','STATSCU0100000140')` 를 호출했더니 앱이 정상 렌더됐다
(프레임셋을 거치지 않는 것이 요령이었다). 그 상태에서 앱이 보내는 **요청 본문을 그대로 캡처**했다.

```json
POST /meta/getMetaDataList.do   (application/json)
{"dmSearch":{"tmpV40":"1000000","tmpV41":"1","tmpV1":"D",
             "tmpV45":"20260430","tmpV46":"20260730","tmpV72":"",
             "OBJ_NM":"STATSCU0100000140BO"}}
```

이전 시도가 값 대신 `null` 만 받은 이유가 여기서 드러난다 — `OBJ_NM` 만 보내고
`tmpV40`(최대 행수)·`tmpV41`(페이지)·`tmpV72`(종목, 빈 값=전체)를 빠뜨렸다.
세 개를 채우자 평범한 `fetch` 한 번으로 전 구간이 온다. **브라우저는 규격을 알아내는 데만 필요했고,
알아낸 뒤로는 필요 없다** — Playwright 의존성은 제거했고 프로젝트는 다시 외부 패키지 0 이다.

응답 형태:

```
{ unit:"", dsmHeader:"",
  ds1:[ {TMPV1:일자, TMPV2:구분, TMPV3:체결주수, TMPV4:상환주수,
         TMPV5:잔고주수, TMPV6:잔고금액(백만원)}, ... ] }
```

최신일이 먼저 오는 내림차순이고, **마지막 두 행은 '합계'/'평균' 요약**이라 일자가 숫자가 아니다.
`/^\d{8}$/` 로 걸러낸다.

검증: API 산출물과 기존 xlsx 산출물을 대조했더니 **4,096행 전부 일치, 불일치 0**이었다.
`scripts/ingest-lending.mjs` 와 커밋된 xlsx 는 규격이 바뀔 때를 대비한 폴백으로 남겨 두었다.

덧붙여 대차거래는 **T+1 공표**라, 당일 장중에 그날 잔고를 받을 수는 없다.
2026-07-31 시점의 최신 관측일은 07-30 이었다.

### 16.3 숏커버링 판정 방법

날짜별로 지수 등락률(Δidx%)과 대차잔고 등락률(Δbal%)을 계산해 네 조합으로 나눈다.

| 조합 | 해석 |
|---|---|
| 지수↑ 잔고↓ | 숏커버형 — 숏이 밀리며 사서 갚는 압력이 지수를 밀었을 수 있다 |
| 지수↓ 잔고↓ | 동반 청산 — 신용융자처럼 위험자산 전반이 축소되는 국면 |
| 지수↓ 잔고↑ | 신규 숏 추정 — 하락에 베팅하는 물량이 늘고 있다 |
| 지수↑ 잔고↑ | 리스크온 — 대차잔고 증가가 반드시 약세 베팅은 아니다(차익거래 등) |

숏커버링 후보일은 '지수↑ 잔고↓' 날짜 중 `Δidx% × (-Δbal%)`(두 등락폭의 곱, 둘 다 클수록
점수가 커진다)로 순위를 매긴다. 판정 구간은 신용융자 분석과 같은 사이클 창을 쓰되,
잔고 자체의 지역 고점(이번 사이클은 2026-06-15)부터 시작한다 — 잔고가 실제로
꺾이기 시작한 지점이라야 '거기서부터 풀렸다'는 서술이 맞는다.

### 16.4 결과 (2026-07-30 기준)

- 대차잔고 역대 최고 195.30조(2026-06-15) → 현재 133.41조(2026-07-30), **-31.7%**
- 같은 창에서 신용융자(전체)는 -15.4% — **대차잔고가 신용융자보다 두 배 가까이 빠르게 풀렸다**
- 잔고 고점(6/15)은 신용융자 고점(6/24)보다 9일, 지수 고점(6/22)보다도 7일 더 일찍 왔다 —
  대차잔고가 신용융자·지수보다 먼저 꺾인 선행지표였을 가능성
- 잔고 고점 이후 하루 단위 조합: 동반 청산이 압도적으로 많고, 숏커버형(지수↑잔고↓)은
  전부 6월 중(급락 시작 전)에 몰려 있다 — **급락이 시작된 6/22 이후로는 뚜렷한 숏커버링 랠리가 아직 없다**

### 16.5 한계

- 대차잔고는 공매도 전용이 아니다(§16.1). 변화 전부를 숏 포지션 변화로 읽으면 과대해석이다.
- "오늘 시장이 급등한다"는 실시간 장중 정보는 이 데이터에 없다. FREESIS는 EOD 공표라
  하루 이상 지연되고, 이 분석의 마지막 관측일(2026-07-30)도 여전히 하락일이었다.
  다음에 데이터를 갱신하면 이 판정 로직이 그날을 자동으로 잡아낸다.
- 대차잔고와 신용융자는 서로 다른 시장 참여자(기관/외국인 vs 개인 신용거래)가 주로
  쓰는 통로라, 두 지표의 디레버리징 속도 차이를 곧바로 '누가 더 급했는가'로
  해석하기는 이르다.

## 17. 예탁금과 2차 레버리지 채널

### 17.1 왜 신용융자만 보면 안 되는가

§1~16 은 전부 **신용융자(OS0026)** 한 채널만 봤다. 원 자료가 그 채널을 다뤘기 때문이다.
그런데 금투협은 같은 크로스통계에서 두 계열을 더 공표한다.

| 계열 | 코드 | 성격 |
|---|---|---|
| 투자자예탁금 | OS0021 | 증권계좌에 들어와 있으나 아직 주식이 아닌 **대기자금** |
| 예탁증권담보융자 | OS0027 | 보유 주식을 담보로 받은 대출. 신용융자와 별개의 **2차 레버리지 통로** |

셋을 같이 놓아야 "레버리지가 감당 가능한가"를 볼 수 있다. 단위는 셋 다 백만원이라 `/1e6` 하면 조원이다.

### 17.2 결과 (2026-07-29 기준)

| 기준점 | 예탁금 | 신용융자 | 담보융자 | 총 레버리지 | 커버리지 |
|---|---|---|---|---|---|
| 2021 신용 고점 (2021-09-13) | 70.41조 | 25.65조 | 19.36조 | 45.01조 | 2.74배 |
| 2023 신용 저점 (2023-01-11) | 44.35조 | 15.81조 | 18.58조 | 34.39조 | 2.81배 |
| 2026 신용 고점 (2026-06-24) | 136.55조 | 38.63조 | 26.35조 | 64.98조 | 3.53배 |
| **현재 (2026-07-29)** | **109.59조** | **33.00조** | **25.52조** | **58.51조** | **3.32배** |

커버리지 = 투자자예탁금 ÷ 신용융자. 낮을수록 '빚 대비 실탄이 없다'는 뜻이다.
역대 최저 2.08배(2018-10-10), 최고 7.13배(2020-04-01, 코로나 폭락 직후 현금이 몰린 시점).

두 가지가 드러난다.

**(1) 디레버리징은 신용융자 채널에서만 일어났다.**
신용 고점(6/24) 이후 신용융자는 -14.6% 줄었는데 예탁증권담보융자는 **-3.2%** 에 그쳤다.
합친 총 레버리지로는 64.98조 → 58.51조, **-10.0%** 다.
신용융자만 보면 청산이 꽤 진행된 것처럼 보이지만 개인 레버리지 전체로는 그 절반 수준밖에 풀리지 않았다.
담보융자는 담보유지비율 기준이 신용융자와 달라 같은 지수 하락에도 강제 청산이 늦게 걸린다.
**§13 의 마진콜 사다리는 이 25.52조를 세지 않는다** — 사다리는 신용융자 채널의 하한이다.

**(2) 이 사이클은 2021년보다 실탄이 두껍다.**
커버리지는 2021년 신용 고점에서 2.74배였는데 이번 고점에서는 3.53배였고 지금도 3.32배(역대 78백분위)다.
§12.1 의 신용/시총 비율 결론("이번 사이클은 2021년만큼 과열된 적이 없다")과 방향이 같다.

### 17.3 한계

- 커버리지가 높다는 것이 **그 예탁금이 실제로 매수에 쓰인다**는 뜻은 아니다. 대기자금은 관망 자금이기도 하다.
  급락 국면에서 예탁금이 늘어나는 것은 오히려 '주식을 팔고 현금으로 앉아 있다'는 신호일 수 있다.
- 예탁증권담보융자의 담보유지비율·청산 트리거는 공표되지 않는다. 신용융자와 같은 0.84 계수를 적용할 근거가 없어
  이 채널에 대한 마진콜 사다리는 만들지 않았다. 그래서 §17 은 규모만 제시하고 청산 추정은 하지 않는다.
- 예탁금은 주식·채권·파생 전체의 대기자금이라 전액이 주식 매수 여력은 아니다.

## 18. 미수금 → 반대매매 전이

### 18.1 기계적으로 기대되는 것

위탁매매미수금(OS0024)은 결제하지 못한 외상 매수다. 결제일 D+2 까지 채우지 못하면
증권사가 반대매매(OS0025)로 처분한다. 그렇다면 미수금은 반대매매의 **2영업일 선행지표**여야 한다.
실제로 그런지 상관계수로 확인했다 — 미수금`[t]` 대 반대매매`[t+시차]`.

### 18.2 결과 — 선행하지 않는다

| 시차 | 전 구간(2010~) | 2025년 이후 |
|---|---|---|
| **0일** | **0.220** | **0.731** |
| 1일 | 0.210 | 0.730 |
| 2일 | 0.190 | 0.624 |
| 3일 | 0.176 | 0.592 |

상관은 **시차 0일**에서 가장 높고, 시차가 늘수록 단조 감소한다. D+2 규칙과 어긋나 보이지만,
금투협이 두 계열을 같은 **공표일** 기준으로 싣기 때문으로 읽는 것이 자연스럽다 —
미수금 잔고와 그에 대한 반대매매가 같은 날짜 라벨에 붙는다.

**결론: 이 데이터로 "미수금을 보고 이틀 뒤 반대매매를 예측"할 수 없다. 둘은 같은 날의 동시 지표다.**

전 구간 상관 0.220 이 낮은 것은 국면마다 절대 규모가 달라서다(2010년대와 2026년의 미수금 스케일이 다르다).
최근 구간(2025년 이후)만 보면 0.731 로 뚜렷하다.

### 18.3 전이율과 현재 수준

전이율 = 반대매매`[t]` ÷ 미수금`[t]`. 이상치에 끌려가지 않게 중앙값을 쓴다.

- 전이율 중앙값 **4.2%** — 미수금 대부분은 반대매매까지 가지 않고 결제된다.
- 현재 미수금 **1.20조**(2026-07-29), 최근 60일 평균 1.34조의 **90%**. 경보 수준이 아니다.
- 역대 상위: 2.15조(2026-03-05), 2.10조(2026-03-06), 2.07조(2026-06-25), 1.92조(2026-05-19), 1.83조(2026-06-04).
  상위 5일이 전부 2026년이다 — 이번 사이클의 거래 규모 자체가 과거와 다른 수준이라는 뜻이다.

### 18.4 한계

§7.4 를 다시 강조한다. 이것은 **미수거래**에 대한 반대매매다.
**신용융자 반대매매는 공표되지 않는다.** §1~13 의 추정치를 검증하지 않는다.

## 19. 공표 시차와 장중 지수

FREESIS 는 EOD 공표라 최신일이 하루 이상 늦다. 신용융자는 결제일 기준이라 지수보다 또 1~2일 늦는다(§7.2).
그래서 리포트 맨 위에 교차검증 소스(네이버 금융 일별 시세)의 최신 지수를 같이 싣는다.

2026-07-31 실행 시점 기준:

- FREESIS 최종 공표 **5,594p**(2026-07-30)
- 네이버 **6,361p**(2026-07-31) — **+13.73%**

본문의 모든 계산은 FREESIS 최종 공표일 기준이다. 장중에 돌리면 네이버 계열의 마지막 행은 종가가 아니라
진행 중인 값이므로 그렇게 표시한다.

**반등은 이미 터진 물량을 되돌리지 않는다.** 마진콜 판정은 그날까지의 **최저 지수** 기준이라(§6),
지수가 되돌아와도 이미 청산된 신용은 돌아오지 않는다. 반등이 막는 것은 **추가** 청산뿐이다 —
§12.2 에서 말한 "잔여 위험은 시간이 아니라 지수 경로에 달려 있다"의 반대 방향 사례다.

§16.5 에 적어둔 "다음에 데이터를 갱신하면 판정 로직이 그날을 자동으로 잡아낸다"는 아직 유효하다.
7/31 은 FREESIS·대차거래 공표 전이라 §16 의 숏커버링 판정에는 아직 들어오지 않았다.

## 20. 숏커버 여력 — 얼마나 더 되갚아져야 하는가

### 20.1 왜 이 계산이 §12와 대칭인가

대차잔고가 줄어든다는 것은 빌린 주식을 **사서 갚는다**는 뜻이다. 곧 매수 압력이다.
§12에서 신용잔고를 두고 "얼마나 더 팔려야 하나"를 벤치마크 범위로 봤다면,
여기서는 대차잔고를 두고 "얼마나 더 사야 하나"를 같은 방식으로 본다.
벤치마크가 하나로 수렴하지 않는 것도 §12와 같아서, 점 추정이 아니라 범위로 제시한다.

### 20.2 벤치마크 네 개 (2026-07-30 기준, 잔고 133.41조)

| 벤치마크 | 목표 잔고 | 잔여 커버 | 일거래대금 대비 |
|---|---|---|---|

## 22. 자동 갱신을 러너에서 성립시키기까지

로컬에서 되는 스크립트가 GitHub 러너에서 안 되는 경우가 있었다. 저장소가 private 이라
Actions 로그를 URL 로 볼 수 없어, **진단 자체를 배포되는 `status.json` 에 실어** 원인을 좁혔다.
같은 상황이 다시 오면 이 순서를 그대로 쓰면 된다.

### 22.1 진단 경로를 먼저 만든다

1. 소스 하나가 실패해도 나머지는 갱신되게 한다(`|| ERR="$ERR <이름>"`). 전부 죽이면 아무것도 안 남는다.
2. 실패한 소스 이름을 `status.json` 에 싣는다 → **어느 소스인지** 확정.
3. 실패 메시지를 한 줄(`LENDING_FAIL ...`)로 찍고 `grep` 으로 집는다.
   노드 기본 예외 출력은 코드 프레임과 스택이 앞에 붙어, 잘라 담으면 정작 필요한 부분이 날아간다.
4. 메시지에 status·본문 길이·content-type·**파싱 실패 이유와 그 위치의 실제 글자**를 넣는다.

### 22.2 실제로 나온 답 — `######`

대차거래추이 응답에서 서버가 **자릿수를 넘는 값을 `######` 로 내보낸다**. 엑셀식 오버플로 표기이고
유효한 JSON 토큰이 아니라 `JSON.parse` 가 깨진다.

```
Expected ',' or '}' after property value in JSON at position 25675
부근: "TMPV4":2113695464,"TMPV5":112685######,"TMPV6":5695820084
```

걸린 곳은 연도별 **합계/평균 요약 행**이었고, 그 행들은 어차피 일자가 숫자가 아니라 버린다.
그래서 값 자리의 `###...` 만 `null` 로 바꿔 파싱한다(문자열 안의 `#` 은 건드리지 않는다).

이 값이 로컬에서는 안 나오고 러너에서만 나온 이유까지는 확인하지 못했다.
서버 쪽 포맷 결정에 요청 환경이 섞여 들어가는 것으로 보이나 근거가 없어 단정하지 않는다.
어느 쪽이든 무해화가 맞는 대응이다 — 요약 행은 쓰지 않기 때문이다.

### 22.3 그전에 걸렸던 것

- **응답 크기**: 16년치를 한 번에 요구하면 424KB 다. 연 단위로 끊어 받는다(`fetch-kofia.mjs` 와 같은 이유).
- **워크플로 YAML**: 한 줄 `run:` 안의 `': '` 를 YAML 이 키 구분자로 읽어 워크플로 전체가 파싱 실패했다.
  블록 스칼라(`|`)를 쓴다. `selfcheck.mjs` 가 이 패턴을 잡는다(§9.0).

### 22.4 확인된 최종 상태

```json
{ "ranBy": "github-actions", "fetchErrors": null, "selfcheck": "passed",
  "dataThrough": { "지수·거래대금": "20260730", "신용융자·예탁금": "20260730",
                   "대차잔고": "20260730", "교차검증 지수(네이버)": "20260731" } }
```

## 23. PART 3 — 레버리지 ETF 수급과 지수 영향

PART 1·2 는 **잔고**를 본다. 얼마가 쌓여 있고 얼마가 풀릴 수 있는가.
PART 3 은 **매일 강제로 나가는 매매**를 본다. 레버리지 ETF 는 잔고가 그대로여도
기초자산이 움직이면 목표 배수를 맞추려고 그날 안에 사거나 판다. 축이 다르다.

### 23.1 소스를 고르기까지

| 후보 | 결과 |
|---|---|
| KRX 정보데이터시스템 `getJsonData.cmd` | 세션 쿠키(JSESSIONID)를 붙여도 400 `LOGOUT`. OTP 경로는 에러 HTML, `download_csv.cmd` 는 403. 봇 차단으로 판단하고 포기했다 |
| 네이버 ETF 개별 페이지 | 상장좌수 항목이 없다(NAV 만 있다) |
| 네이버 `api/sise/etfItemList.nhn` | 전 종목 목록·현재 시총·NAV. **EUC-KR** 이라 `res.json()` 으로 읽으면 한글이 전부 깨져 이름 규칙이 하나도 안 맞는다. `TextDecoder('euc-kr')` 로 디코딩한다. 유니버스 구성에 쓴다 |
| 다음 금융 일별시세 | **행마다 `listedSharesCount`.** 46행 중 43일이 서로 다른 값이라 현재값 복사가 아니라 진짜 일별 좌수다. 채택 |

좌수가 왜 결정적인가: AUM 은 좌수 × 가격이다. AUM 이 줄어도 좌수가 그대로면 **환매가 아니라 값이 빠진 것**이다.
"정리되었는가" 는 좌수로만 답할 수 있다.

### 23.2 AUM 분해

```
Δln AUM  =  Δln 좌수  +  Δln 가격
            (유출입)      (가격효과)
```

좌수 ↓ = 실제 환매(디레버리징). 좌수 → 이고 가격 ↓ = 물량은 남아 있음.
좌수 ↑ 이고 가격 ↓ = 하락 중 유입, 가장 위험한 조합.

`selfcheck.mjs` 가 세 항의 항등식과 `AUM = 좌수 × 종가` 를 매 실행 검사한다.

**AUM 은 순자산총액이 아니라 종가 × 좌수다.** 일별 NAV 소스를 못 구했다.
괴리율(시장가 vs NAV)만큼 오차가 있고, 레버리지 상품은 급변동 구간에서 이 괴리가 커진다.

### 23.3 리밸런싱 요구액

레버리지 배수 L 상품은 목표 노출을 유지하려고 매일 방향성 매매를 한다.

```
필요 매매액(t) = L(L − 1) × AUM(t−1) × r(t)        r = 기초자산 당일 수익률
  2X  : 계수 2   (오르면 사고 내리면 판다)
  -2X : 계수 6   (인버스가 3배 크다)
```

둘 다 부호가 r 과 같다 — **둘 다 추세를 증폭한다.** 인버스라고 반대로 작용하지 않는다.
규모가 작다고 인버스를 빼면 안 되는 이유다. `selfcheck.mjs` 가 부호 일치를 전 행에서 검사한다.

기초자산 수익률은 삼성전자·SK하이닉스 실제 종가에서 잡는다. 그래서 리밸런싱 계산은
**단일종목 상품만** 센다 — 섹터·지수형은 기초지수를 따로 받아야 하는데 그 소스가 없다.
빠진 만큼 아래 숫자는 하한이다.

### 23.4 지수 영향 — 무엇을 말하고 무엇을 말하지 않나

말하는 것 두 가지.

1. **거래대금 대비 비율** — 리밸런싱 필요액이 그날 그 종목 거래대금의 몇 %인가
2. **산술 기여** — 코스피 등락 중 두 종목이 설명하는 몫 = 시총비중 × 종목수익률

말하지 않는 것: **가격충격 계수.** 1조를 사면 지수가 몇 p 오르는지는 이 데이터로 알 수 없다.
PART 2 에서 숏커버 여력을 지수 상승폭으로 환산하지 않은 것과 같은 이유다(§20.4).

### 23.5 반증

"레버리지 ETF 때문이었다" 를 주장으로 두지 않으려면 아래를 같이 봐야 한다.

- **대조군**: 지수형 레버리지(예전부터 있던 물량)와 섹터형을 같은 창에서 비교한다.
  단일종목형만 좌수가 급증했고 섹터형은 오히려 환매됐다면, 그건 '레버리지 일반'의 이야기가 아니다.
- **상장 전후**: 삼성전자·SK하이닉스의 평균 일중 진폭을 2025년 / 2026년 상장 전 / 상장 후로 나눠 본다.
  진폭 상승이 상장 전에 이미 시작됐다면 ETF 는 유일한 원인이 아니다.
- **리밸 수요 ~ 진폭 상관**: 상위 20% 날과 나머지 날의 평균 진폭을 비교한다.

리포트는 이 셋을 전부 싣는다. 상관이 약하게 나오면 약하다고 쓴다.

### 23.6 홍콩(CSOP) — 자동화되기까지

`7709`(SK Hynix 2x)·`7747`(Samsung 2x)·`7347`(Samsung -2x)은 상품 페이지가 값을 JS 로 채워
정적 fetch 로는 빈 `<span>` 만 온다. 내부 API(`website-api.csopasset.com/cmsApi/NAV/product`)에
`fundCode`·`productCode`·slug 등 짐작 가는 파라미터를 다 넣어 봤지만 전부 500 이었다.
처음에는 브라우저로 열어 읽은 시점 스냅샷으로 때웠다.

풀린 경로는 파라미터 추측이 아니라 **페이지가 로드하는 상품 전용 JS 를 읽는 것**이었다.
상품 페이지는 `asset/lai/js/hk-skhy-2l.js` 같은 전용 스크립트를 `$.getScript` 로 불러오고,
그 안에 요청이 통째로 있다:

```js
url: webApi + "/cmsApi/NAV/product",  method: "POST",
data: JSON.stringify({ "productName": FundName })
// FundName = 'CSOP SK Hynix Daily Max (2x) Leveraged Product'  ← 상품 전체 영문명
```

키가 코드가 아니라 **상품 전체 영문명 문자열**이라 추측으로는 맞출 수 없었던 것이다.
이 바디로 POST 하면 통화별(HKD/USD) 행에 `NAV`(1좌)·`AUM`(총순자산)·**`Shares`(좌수)**·
`ContractValue`(스왑 명목 익스포저)·기준일이 온다. Node 에서 Origin 헤더만 붙이면 그대로 동작한다.

`scripts/fetch-csop.mjs` 가 이걸 매일 받아 두 파일을 쓴다.

- `data/csop-snapshot.json` — 최신 스냅샷. analyze 가 읽는다. **자동 생성이므로 손대지 말 것.**
- `data/csop-daily.json` — 기준일별 히스토리. CSOP 의 과거 API(ChartData)는 403 이라
  운용사 쪽 백필은 불가능하다 — CSOP 행은 2026-08-02 수집 시작 이후부터 쌓인다.

**과거 좌수는 다른 문에서 열렸다 — HKEXnews CCASS 조회(SDW).** 홍콩 상장 종목은
`www3.hkexnews.hk/sdw/search/searchsdw.aspx` 가 과거 12개월까지 날짜별 보유내역을 열어 두고,
응답 요약의 "Total number of Issued Shares/Warrants/Units" 가 **그 날짜 기준 발행좌수**다
(날짜별로 실제로 변하는 것을 7/31=829M, 7/26=840M, 6/16=707.5M 로 확인했다).
ASP.NET 폼이라 GET 으로 `__VIEWSTATE` 를 받고 날짜·종목코드로 POST 한다. 휴장일을 요청하면
서버가 날짜를 바꿔 돌려주므로, 응답에 박힌 날짜가 요청과 다르면 버린다.
`scripts/backfill-csop-units.mjs` 가 상장일(2025-10-16)부터 이 방법으로 백필했다(재실행하면 갭만 채운다).

**좌수의 기준이 셋이라는 것을 알고 읽어야 한다.** 7/31 하루에서 실측한 값:

```
등록기관 발행좌수(SDW)   829M   ← 백필 행(src:hkex-sdw)이 쓰는 값
CSOP 신고좌수(딜링일)    984M   ← 일별 수집 행이 쓰는 값
CCASS 보유총량          1,048M
```

창출·환매가 T+2 로 결제되는 동안 세 값이 벌어진다(평시엔 1% 안쪽: 6/16 은 707.5 vs 716.4).
그래서 히스토리에는 2026-08-01/02 이음새에 단차가 있을 수 있다. 5일 변화율 같은 추세 판정에는
지장이 없지만, 하루 단위 창출·환매량을 이 계열의 인접일 차분으로 읽으면 안 된다.

남은 한계 둘. (1) 조회 키가 상품명 문자열이라 **상품이 개명되면 조용히 깨진다** — 실제로
2026 년에 'Daily' → 'Daily Max' 개명이 있었다. `selfcheck.mjs` 의 NAV×좌수≈AUM 항등식과
워크플로의 `fetchErrors=csop` 가 그때의 경보다. (2) SDW 는 12개월 창이라, 이번에 백필해 둔
구간은 다시 만들 수 없는 기록이 된다 — csop-daily.json 을 지우면 복구 못 하는 날이 생긴다.

## 24. PART 4 — 다음 주 수급 전망

### 24.1 이 절이 답하는 질문과 답하지 않는 질문

답하는 것: **지수가 X% 움직이면 어떤 물량이 기계적으로 따라 나오는가.**
답하지 않는 것: **지수가 어디로 갈 것인가.**

수급은 방향을 만들지 않는다. 방향이 정해진 다음에 그 방향을 얼마나 증폭하느냐를 정할 뿐이다.
그래서 이 절은 예측이 아니라 **사전 기록**이다. 다음 주 숫자를 미리 적어 두면, 실제 움직임이
나온 뒤에 "수급이 원인이었나" 를 사후에 판정할 수 있다. 그게 이 절의 용도다.

### 24.2 세 축

| 축 | 계산 | 출처 |
|---|---|---|
| 레버리지 ETF 강제 매매 | 상품별 `L(L−1) × AUM × 시나리오 수익률` 합계 | PART 3 |
| 아래로 열리는 물량 | 마진콜 사다리 문턱까지의 거리(%)와 그때 열리는 금액 | PART 1 |
| 위로 나오는 물량 | 대차잔고 수준과 직전일 변화, 잔여 커버 여력 | PART 2 |

시나리오는 **지수 등락률을 종목 등락률의 대용치**로 쓴다. 삼성전자·SK하이닉스가 코스피 등락의
60~80% 를 설명하므로(§23.4) 쓸 만한 근사지만, 두 종목이 지수와 따로 놀면 어긋난다.
`selfcheck.mjs` 가 시나리오의 대칭성(±X% 에 부호만 반대인 같은 금액)과 부호를 검사한다.

### 24.3 과거 유사 국면(base rate)

2010년 이후 코스피 일별에서 조건을 만족한 날의 **다음 5거래일 수익률 분포**를 낸다.
조건은 낙폭(20거래일 −15%/−20%)과 급등일(+3%/+8%), 그리고 둘의 교집합이다.

표본이 10개 미만인 줄은 리포트에서 흐리게 표시한다 — **그건 근거가 아니라 일화다.**
실제로 이번 데이터에서 조건부 분포는 전 구간 기준선과 크게 다르지 않았다.
즉 "급락 뒤 반등" 이라는 조건만으로 다음 주 방향은 갈리지 않는다. 그렇게 쓴다.

### 24.4 제도 일정

계산으로 나오지 않는 유일한 입력이다. 외사 리포트에서 옮겨 적고 `analyze.mjs` 의 `EVENTS`
상수에 날짜와 함께 둔다. 세 건 모두 레버리지 재축적을 어렵게 만드는 방향이라, 하방 증폭기를
약화시키는 동시에 상승 탄력도 같이 줄인다 — **방향보다 진폭에 먼저 영향을 준다.**

### 24.5 외사 수치와의 대조 (`data/street-anchors.json`)

원문 PDF 는 제3자 저작물이라 저장소에 넣지 않는다(`.gitignore` 의 `*.pdf`, §2.5 와 같은 처리).
대조에 필요한 수치만 출처·발간일과 함께 옮겨 적는다. 사람이 새 리포트를 읽고 갱신한다.

여기서 **우리 계산과 갈리는 지점이 하나 있고, 그게 이 절에서 가장 중요한 관찰이다.**

세 하우스 모두 레버리지 ETF AUM 반토막(US$50~53bn → US$26bn)을 디레버리징의 진척으로 읽는다.
그런데 PART 3 의 좌수 분해로는 그 감소가 거의 전부 **가격효과**이고 좌수는 오히려 늘었다.
J.P. Morgan 도 같은 관찰을 적어 두었다 — 자금 유입은 계속 플러스라는 것이다(21 Jul 2026, Figure 9).

```
AUM 기준  : 고점 대비 반토막  ->  "정리가 끝나간다"
좌수 기준  : 오히려 증가       ->  "물량은 그대로 남아 있다"
```

두 척도가 반대 방향을 가리킨다. 어느 쪽을 보느냐가 다음 국면의 판단을 가른다.
이 리포트는 좌수를 기본으로 본다 — AUM 은 가격이 섞여 있어 수급 지표로 쓰기에 부적절하기 때문이다.

### 23.7 매일 보는 지표 하나 — 좌수가 꺾였는가

PART 3 에서 나온 결론이 하나로 줄면 이것이다: **AUM 이 아니라 좌수를 봐라.**
AUM 은 가격이 섞여 있어 "정리됐는지" 를 못 알려준다. 좌수가 꺾이는 날이 진짜 환매의 시작이다.

그래서 이 지표는 리포트를 열자마자 보이는 자리(핵심 요약 맨 위)에 고정으로 올렸고,
`status.json` 에도 실었다 — 사이트를 열지 않고도 확인할 수 있게.

판정 규칙은 5거래일 변화율 하나다. 단순하게 둔 이유는, 규칙이 복잡하면 매일 볼 수 없기 때문이다.

| 5일 변화 | 판정 | 뜻 |
|---|---|---|
| > +1% | `building` 아직 쌓이는 중 | 디레버리징은 시작되지 않았다 |
| −1% ~ +1% | `flat` 정체 | 증가가 멈췄다. 꺾이는 길목일 수 있다 |
| < −1% | `rolling` 꺾였다 | 여기서부터가 진짜 환매다 |

같이 싣는 보조 숫자: 전일/5일/10일 변화, 최대 좌수 대비, 그 최대가 며칠 전인지, 연속 감소일.
**연속 감소일을 따로 세는 이유**는 하루 반짝 감소를 꺾임으로 읽지 않기 위해서다.

`selfcheck.mjs` 가 판정과 5일 변화율이 어긋나지 않는지, 최대값이 최신값보다 작지 않은지를 검사한다.

## 25. 시장별 되돌림 진척 — 합계가 가리던 결론

PART 1 의 청산률은 유가증권+코스닥 **합계**다. 그런데 이번 사이클에서 두 시장은 정반대로 움직였고,
합계는 그 둘을 평균 내 어느 쪽 이야기도 하지 못한다. 실제로 합계 청산률 −16.8% 는
코스닥의 −38.3% 와 코스피의 −13.5% 를 섞은 값이다. 그래서 시장별로 따로 계산해 리포트에 실었다
(`analysis.json` 의 `divergence`, PART 1 "같은 사이클을 두 시장이 다르게 지나고 있다").

### 25.1 왜 청산률만으로는 부족한가

고점 대비 청산률(`unwindPct`)은 **고점**을 기준선으로 잡는다. 고점이 얼마나 비정상이었는지를
묻지 않으므로 "원래대로 돌아왔나" 에는 답하지 못한다. 그래서 기준선이 다른 지표를 셋 더 놓았다.

| 지표 | 기준선 | 답하는 질문 |
|---|---|---|
| `unwindPct` 고점 대비 청산률 | 사이클 고점 | 고점에서 얼마나 빠졌나 |
| `retracedPctOfBuild` 쌓은 것 대비 되돌림 | **사이클 시작 잔고** | 이번에 쌓은 것을 얼마나 토해냈나 |
| `multipleOfStart` 현재/시작 배수 | 사이클 시작 잔고 | 시작 수준으로 돌아왔나 |
| `ratioVsPrevTrough` 신용/시총 ÷ 직전 저점 비율 | **직전 사이클 저점** | 지난번 바닥만큼 내려왔나 |

네 지표가 같은 방향을 가리킬 때만 "끝났다" 고 말한다. 코스닥은 넷 다 같은 쪽이다 —
쌓은 것의 95% 반납, 잔고가 시작의 1.04배, 청산률 −38.3% 가 직전 사이클 완주치 −36.9% 를 넘음,
신용/시총이 직전 저점의 0.80배. 코스피는 넷 다 반대쪽이다(17%, 2.83배, 완주치의 32%, 1.27배).

### 25.2 시장별 신용/시총 — 두 시장을 서로 견주지 않는다

분모는 시장별 시가총액이다(`OS0008` 유가증권, `OS0009` 코스닥. 억원 단위라 ×100 하면 백만원).
전체 비율(§8)은 두 시장이 섞여 이 질문에 답하지 못하므로 따로 만들었다.

**수준을 시장 간에 직접 비교하면 안 된다.** 코스닥은 평시에도 코스피의 서너 배다
(직전 저점끼리 2.304% vs 0.440%). 그래서 각 시장을 **자기 과거**와만 견줬다.

두 가지 편향을 알고 읽어야 한다.

1. 분모인 시가총액이 급락으로 빠르게 줄어 비율이 실제보다 **높게** 보인다. 즉 코스피가 저점 비율
   위에 있다는 판정은 그만큼 **보수적**이고, 코스닥이 저점 아래라는 판정은 그만큼 **더 강하다**.
2. 신용융자는 결제일 기준이라 잔고 기준일이 지수보다 하루 늦다. 급등락 직후에는 이 하루가 크다.

### 25.3 남은 여지

`toPrevTroughJo` = 현재 잔고 − (직전 저점 비율 × 현 시총). 음수면 0 으로 자른다.
코스피 5.63조, 코스닥 0조다. 이것은 **강제 청산 예측이 아니라 정상화 기준선까지의 거리**다 —
마진콜 사다리(§13)와 달리 트리거가 없고, 지수가 더 빠지면 새 물량은 별도로 열린다.

`selfcheck.mjs` 가 항등식(쌓은 것 = 고점 − 시작, 되돌린 것 = 고점 − 현재, 비율 = 잔고 ÷ 시총)과
판정 일관성(저점 비율 아래 ⇔ 남은 여지 0 ⇔ `doneMarkets` 포함)을 검사한다.
